# Browser Use｜让 AI Agent 在网页中持续执行任务 🌐

- Source｜来源：browser-use/browser-use GitHub Repository
- Type｜类型：开源 AI 项目产品化分析 / Browser Agent / Web Automation / Agent Framework
- Link｜链接：https://github.com/browser-use/browser-use

Browser Use 是一个让 AI Agent 操作网页并完成多步骤任务的开源项目。

它关注的不是单次抓取网页内容，也不只是把点击、输入和滚动封装成几个工具，而是让模型在真实浏览器环境中持续观察页面、选择动作、处理反馈并推进目标。

浏览器是大量数字任务的共同入口。搜索资料、填写表单、操作后台、比较商品、下载文件和检查页面，都依赖网页中的连续交互。传统自动化通常要求开发者提前编写稳定脚本，Browser Agent 则尝试让用户直接描述目标，由 Agent 根据当前页面动态决定路径。

从产品视角看，Browser Use 值得关注的地方不是“AI 会点击网页”，而是它把浏览器操作组织成一个可持续的任务执行过程。

> 浏览器工具提供动作，Browser Agent 还需要理解目标、维护会话、判断进展，并在页面变化或操作失败后找到继续路径。

---

## What It Is｜它是什么 🧩

Browser Use 官方将项目描述为让网站能够被 AI Agents 使用，并通过自然语言自动完成在线任务。

用户或开发者可以为 Agent 提供任务和浏览器环境，Agent 根据页面状态调用浏览器动作，再观察新的页面结果。这个过程会重复进行，直到任务完成、达到步骤限制，或因为失败和权限边界停止。

这与传统脚本自动化有明显区别。固定脚本预先知道页面元素、操作顺序和成功条件，适合结构稳定、重复频率高的流程。Browser Agent 面对的是目标明确但路径可能变化的任务，例如跨多个页面收集信息、处理不确定弹窗，或根据中间结果决定下一步去哪。

项目还围绕浏览器会话、持久工具和恢复循环持续演进。会话可以保存页面、标签页、Cookie 和登录状态，让后续任务在同一浏览器环境中继续。不过，浏览器状态被保留不代表 Agent 自动理解之前的全部任务；产品仍需要区分页面状态、对话上下文和长期记忆。

Browser Use 同时存在开源框架与托管服务。开源仓库提供可自行运行和二次开发的 Browser Agent 能力，云服务则进一步提供托管浏览器、会话管理和运行基础设施。分析项目时需要区分两者，不能把云端产品能力全部视为开源仓库的默认组成。

## Why It Matters｜为什么值得关注 💡

很多 Agent 产品的行动能力受限于工具接口。

当目标系统提供清楚 API 时，Agent 可以通过结构化参数完成查询和操作。这种方式可靠、容易验证，但接入每个新系统都需要开发和维护专用工具。现实中还有大量网页没有适合 Agent 的 API，或用户只是希望快速验证一个自动化想法，不愿先建设完整集成。

浏览器提供了一种通用入口。只要用户能够通过网页完成任务，Agent 就有机会沿着相似路径参与。这使产品可以覆盖更多长尾网站和临时流程，也缩短了从需求描述到自动执行的距离。

但通用性会把稳定性问题带到运行时。页面结构可能变化，登录状态可能失效，弹窗可能遮挡目标，加载时间也不固定。Agent 需要判断自己是否到达正确页面、动作是否生效，以及失败后应该重试、返回还是换一条路径。

因此，Browser Agent 的产品价值不只取决于单步操作准确率。更重要的是它能否在多步骤任务中保持方向、识别停滞、保存有效进展，并让用户在关键时刻理解和控制执行。

## Core Product Structure｜核心产品结构 ⚙️

### Task｜把自然语言转成任务边界

用户通常从一句目标开始，例如查找符合条件的信息、完成某段后台流程，或访问多个页面比较结果。

一个好的任务入口不能只接收文字，还需要帮助用户明确范围、最终交付和可执行权限。“帮我处理这些订单”可能涉及读取、修改和提交多个层级；产品需要知道哪些动作允许自动进行，哪些必须等待确认。

任务越开放，Agent 可选择路径越多，运行成本和风险也越高。产品可以在开始前展示理解后的目标和限制，让用户纠正范围，而不是等 Agent 进入错误网站后再处理。

### Browser Session｜把浏览器状态变成工作空间

Browser Agent 的执行依赖会话状态。当前网址、标签页、Cookie、登录信息和页面中间状态都会影响下一步。

持续会话让多步骤任务不必每次重新登录，也支持用户在同一环境中追加后续目标。但会话同时包含敏感信息。产品需要说明状态保存多久、由谁访问、任务结束后是否销毁，以及用户能否查看和主动终止。

会话还提供了人工接管的基础。用户可以在 Agent 暂停时进入同一个浏览器完成验证码、登录或高风险确认，再把控制权交回系统，而不是重新建立全部上下文。

### Observe and Act｜观察与行动循环

Agent 需要把页面压缩成足以判断的状态，再选择点击、输入、滚动、导航或提取等动作。

页面观察不能只依赖文本。控件可用状态、当前焦点、弹窗和加载反馈都可能决定动作是否安全。另一方面，把整个页面的所有细节持续发送给模型，会增加成本并稀释真正相关的信息。

因此，Browser Agent 的关键能力之一是选择当前步骤需要的页面表示，让模型获得足够信息，又不会在复杂 DOM 和视觉内容中失去目标。

### Recovery Loop｜从页面变化中恢复

网页任务很少完全按预期路径运行。元素位置变化、网络延迟和意外页面都会让预设步骤失效。

恢复循环需要识别失败类型：动作没有执行、页面尚未加载、进入了错误路径、权限不足，还是目标本身已经无法完成。只有原因发生变化时，重试才有价值。

成熟产品还应保留已经获得的结果。Agent 即使无法完成最后一步，也可以交付已收集信息、当前页面状态和具体阻塞原因，避免把部分成果与失败任务一起丢弃。

## Use Case｜适用场景 📌

Browser Use 更适合目标清楚、需要跨页面操作，但网页路径存在一定变化的任务。

在研究和信息整理中，Agent 可以访问多个公开页面、提取指定内容并形成比较结果。与纯网页抓取相比，它能够根据页面交互继续深入，但也需要更严格的来源记录和内容验证。

在业务后台中，Agent 可以帮助查找记录、填写草稿和整理重复信息。涉及最终提交、批量修改或删除时，应将动作停在人工确认之前。

在网页测试中，用户可以用任务语言描述真实流程，让 Agent 访问页面、尝试操作并记录异常。这种方式适合发现探索性问题，但不能替代确定性的自动化回归测试。

在个人自动化中，持续浏览器会话可以完成预约、监测和跨网站整理。不过，只要涉及账号、支付、隐私数据或服务条款，产品就需要限制域名、凭据范围和可执行动作。

对于页面稳定、流程高频且业务影响较大的任务，传统 API 或确定性脚本通常更合适。Browser Agent 可以先验证流程价值，但不应因为接入方便就永久替代更可靠的系统集成。

## Product Insight｜产品观察 🔍

Browser Use 最重要的产品启发，是通用浏览器能力正在从“自动化工具”变成“Agent 运行环境”。

传统浏览器自动化主要由开发者编写步骤，产品价值来自脚本稳定重复。Browser Agent 把部分路径选择交给模型，用户从配置步骤转向描述目标。这降低了初始门槛，也把不确定性从设计阶段移到了执行阶段。

因此，Browser Agent 产品不能只展示最终结果。用户需要看到任务当前处于哪个网站、已经完成什么、正在等待什么，以及是否可以暂停和接管。实时预览、步骤摘要和关键动作确认不是附加装饰，而是通用执行能力能够被信任的基础。

它与仓库已有内容也有明确区别。

Playwright MCP 关注如何把浏览器能力通过 MCP 提供给 AI，重点是工具连接和可调用动作。Computer Use 讨论 Agent 如何进入任意图形界面，以及视觉操作的通用风险。Firecrawl 则更偏向把网页内容转换成适合 LLM 和 RAG 使用的数据。

Browser Use 的独立位置在于完整 Browser Agent：它把任务、浏览器会话、动作循环和恢复机制组织在一起，重点是网页目标如何被持续推进。相邻能力可以成为它的基础，但不能替代任务层的运行管理。

## Trust and Control｜信任与控制边界

网页同时是 Agent 的操作环境和不可信信息来源。

页面中的文字可能包含误导模型的命令，广告和弹窗可能改变视觉焦点，登录状态还可能让 Agent 接触私人数据。Browser Agent 不能把当前网页中的所有内容都视为可信指令，而需要保持用户目标、产品规则和页面数据之间的边界。

权限也不能只用“允许访问浏览器”表达。产品可以限制可访问域名、可使用账号、允许的下载和上传范围，以及发送、购买、删除等高影响动作。用户授权的是一个具体目标，不是让 Agent 获得浏览器内所有账户的无限控制权。

执行记录应该说明关键动作与结果证据。用户不需要阅读模型的全部内部推理，但需要知道 Agent 访问了什么、改变了什么，以及最终结论基于哪些页面。

当任务使用托管浏览器时，还需要说明 Cookie、文件、截图和运行记录如何保存。开源部署提高了控制空间，但实际数据边界仍取决于模型提供商、浏览器基础设施和日志配置。

## Reusable Value｜可复用价值 🔁

设计 Browser Agent 时，可以先把动作分成观察、可撤回编辑和不可逆执行。公开页面浏览与信息提取可以更自动化，表单草稿需要展示结果，发送、购买和删除则必须设置明确确认。

每个任务还应定义成功证据。查找信息需要保留来源和条件，填写表单需要检查字段，提交操作需要确认页面或后台状态已经变化。Agent 不能只因为动作序列走到最后，就宣布任务成功。

持续会话应被视为独立产品对象。用户需要看到会话归属、登录状态、当前任务、保留时间和终止入口。任务上下文与浏览器状态要分开管理，避免系统保留了账号状态，却无法解释前一次操作目的。

评估时除了最终成功率，还应观察平均步骤、无效重复、人工接管点、页面变化后的恢复能力和高风险动作拦截情况。这些指标比单次点击准确率更接近真实产品质量。

## Productization Direction｜产品化方向 🚀

### Supervised Browser Workspace｜可监督浏览器工作区

产品可以把任务目标、实时页面、步骤摘要、结果和确认请求放在同一个工作区。用户无需观看每次点击，但可以随时理解状态并接管。

### Reusable Web Skills｜可复用网页能力

高频网站的稳定路径、字段规则和异常经验可以沉淀为可复用能力，让 Agent 不必每次重新探索。能力需要与站点版本、权限和评估结果绑定，避免过期步骤在后台持续失败。

### Browser Task Operations｜浏览器任务运营

团队可以集中观察任务成功率、失败页面、平均成本和人工介入原因，把 Browser Agent 从一次性 Demo 变成可以持续改进的运行系统。

Browser Use 展示了网页自动化从固定脚本走向目标驱动 Agent 的可能性。

它真正需要解决的不是如何让 AI 点击更多页面，而是如何让一个开放任务在不断变化的网页环境中保持方向、验证结果，并让用户始终拥有停止和接管的能力。
