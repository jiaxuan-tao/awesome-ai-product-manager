# REA｜让 AI Agent 基于证据理解软件实现 🔎

- Source｜来源：morluto/rea GitHub Repository / Official Documentation
- Type｜类型：开源 AI 项目产品化分析 / Reverse Engineering / Agent Tools / MCP / Software Investigation
- Link｜链接：https://github.com/morluto/rea

看到一个值得学习的软件功能时，我们往往能够描述它的外观，却不一定理解它为什么这样工作。

搜索结果为什么按这个顺序出现，复制内容为什么能够保留特殊格式，一个桌面操作究竟发生在界面层还是本地进程，这些问题单靠截图和体验记录很难回答。直接让模型猜测实现方式，又容易得到一套听起来合理、实际缺少依据的解释。

REA，全称 Reverse Engineer Anything，是一个把软件分析工具连接到 AI Agent 的开源项目。它让 Agent 可以围绕具体问题调查程序与应用，并根据工具返回的信息继续验证判断。

从产品视角看，这个方向的价值在于，把“参考一个功能”推进为一条有依据的学习路径：明确问题，收集证据，区分已知与推断，再为自己的项目形成独立实现与验收要求。

---

## What It Is｜它是什么 🧩

REA 通过 MCP 向 Agent 提供软件调查能力，也提供 CLI 入口。官方项目覆盖原生二进制、JavaScript 与 Electron 应用、网站等分析对象，并根据目标连接不同分析工具。

这里的 Agent 负责提出问题、选择下一步和解释结果；REA 负责把调查动作与分析结果组织成可调用接口；底层引擎则承担反汇编、反编译或其他具体分析工作。这种分工让通用模型可以参与专业调查流程，而不必凭空推测程序内部结构。

原生程序的深入分析可能需要 Hopper、Ghidra 或 IDA 等环境，不同目标的依赖与能力范围并不相同。安装工作流指引也不等于所有引擎已经可用，实际使用需要确认目标、运行环境和工具支持。

原生分析返回的伪代码与汇编不能视为原作者源码。可见结构、恢复出的关系和模型给出的解释，也需要根据证据分别判断。这是理解这类产品能力边界的起点。

---

## Why It Matters｜为什么值得关注 💡

AI 编程降低了尝试一种实现的成本，但没有自动解决“我们是否理解了需求和参考对象”的问题。

如果只依据界面描述生成代码，原型可能很快具有相似外观，却忽略行为细节。例如，复制一个内容块时，用户需要的可能包括格式、链接和多种粘贴目标之间的兼容性。只实现复制纯文本，虽然按钮可以点击，却没有覆盖原来值得学习的体验。

调查工具的价值，是帮助团队把模糊的“做一个类似功能”拆成可以验证的问题。哪些行为已经观察到，哪些关系可以从代码中找到依据，哪些部分仍然不可见，这些信息会直接影响需求范围与开发方案。

REA 值得关注，也因为它展示了一种专业工具进入 Agent 的方式。自然语言成为调查入口，结构化工具提供事实材料，模型负责组织追问和说明。最终效果取决于这些环节能否保持证据联系，而不只是回答是否流畅。

对个人 AI 产品实践而言，这类流程可以帮助减少盲目试错。先理解目标行为和限制，再决定需要实现什么，通常比不断要求模型“再像一点”更容易形成可维护的产品。

## Core Capability｜核心能力 ⚙️

### Targeted Investigation｜围绕问题缩小调查范围

复杂应用包含大量代码和资源。把所有内容一次性交给模型，既增加成本，也容易让分析偏离真正关心的功能。

REA 的[JavaScript 应用工作流](https://github.com/morluto/rea/blob/main/docs/javascript-application-workflows.md)提供基于已有应用分析结果的功能追踪，可以从模块、字符串、路由或 IPC 通道等线索出发，查看相关关系及其证据。

这给产品设计的启发是，调查应该有明确问题和停止条件。例如，目标可以是确认某个操作如何跨越界面与主进程，而不必先解释整个应用。结果应说明覆盖了哪些部分，以及哪些关系仍然不确定，帮助用户决定是否值得继续深入。

### Evidence Records｜让结论保留依据与限制

根据[CLI 与 Evidence 文档](https://github.com/morluto/rea/blob/main/docs/cli.md)，REA 的证据记录可以保留分析对象身份、来源位置、观察、推断与未解决发现，并支持保存、导出和比较。

同一文档还强调，命令完成时，结果仍可能包含部分证据、警告或未解决问题。因此，工具执行状态与调查结论需要分开判断。退出成功说明操作完成，不能自动推出软件机制已经被完整理解。

在产品界面中，这种区分应当继续保留。用户需要知道一句解释来自实际观察、静态关系，还是模型的进一步归纳。否则，再丰富的证据也可能被一段过度确定的总结掩盖。

### Static and Runtime Views｜从不同角度检验理解

静态分析关注程序材料中的结构与关系，运行时观察关注选定情境下实际发生的行为。两者能够提供互相补充的信息，但回答的问题不同。

例如，文件中存在一个模块，不代表某次操作实际使用了它；一次测试没有观察到网络请求，也不足以证明所有使用场景都完全离线。要判断功能行为，需要把目标版本、输入条件和观察范围一起保存。

REA 的[浏览器观察文档](https://github.com/morluto/rea/blob/main/docs/browser-observation.md)区分被动页面观察与执行交互的场景工具。这提醒上层产品，读取信息与驱动目标运行应有清楚入口，用户需要理解本次分析会对哪个环境产生什么影响。

## Use Case｜适用场景 📌

REA 适合围绕明确问题开展的软件研究、遗留系统理解和实现验证。分析对象应当是自己拥有或获得授权研究的软件与材料，调查范围也应与目标问题匹配。

在维护旧项目时，团队可能缺少完整文档，需要理解某个功能依赖哪些模块、数据从哪里进入、结果如何传递。调查材料可以帮助形成更准确的维护计划，并把原本只存在于个人经验中的知识保存下来。

在学习现有产品时，可以围绕一种行为建立观察与解释，例如输入如何被处理、界面操作如何连接本地能力，以及某项输出为什么具有特定格式。随后再根据自己的用户需求设计实现，而不是默认沿用参考产品的全部功能和结构。

在独立实现之后，团队还可以使用相同的输入与操作场景比较行为。比较的重点应是事先定义的目标，例如格式是否正确、边界输入如何处理、异常状态是否合理，而不是仅凭画面相似判断完成。

如果源码和文档已经完整可读，直接阅读、运行测试可能更高效。逆向调查需要额外工具、知识和时间，产品应允许用户选择成本更低的证据路径。

## Product Insight｜产品观察 🔍

REA 展示了 Coding Agent 工作流中一个值得独立设计的阶段：在修改或实现之前，先建立对目标系统的可验证理解。

它与仓库里的 OpenHands 分析形成分工。OpenHands 关注 Agent 如何推进开发任务；REA 的独立观察点是调查过程如何向开发提供可靠输入。Computer Use 关注通过图形界面执行操作，REA 则进一步把行为与程序材料联系起来，帮助解释为什么出现这些结果。

对用户来说，真正有价值的交付物通常不是一大份反编译输出，而是一份能够指导决策的调查结论。它应包含原问题、支持判断的证据、仍未确认的部分，以及这些发现如何影响自己的需求和实现方案。

这也改变了产品完成标准。一个工具可以分析成功，却没有回答用户的问题；一个回答可以写得完整，却主要建立在推断上。产品需要让完成状态与证据覆盖对应，而不是用结果长度或调用次数代表调查质量。

另一个细节是数据边界。官方说明分析在本地进行，但 Agent 仍然会接收工具结果，所用模型服务有自己的数据处理方式。因此，本地分析不能直接等同于所有信息始终留在设备上。选择调查目标时，需要明确哪些材料和结果可以进入模型上下文。

## Reusable Value｜可复用价值 🔁

这类流程可以复用为一份简洁的功能调查记录。首先说明用户问题与目标版本，接着保存输入条件、可重复操作和观察结果，再把证据支持的解释与待验证假设分开。

例如，要学习一种剪贴板体验，可以先列出需要支持的复制内容和粘贴目标，再比较不同条件下的行为。如果调查发现部分行为依赖平台能力，就应把平台差异写入需求与测试范围，而不是要求生成代码无条件达到相同效果。

随后，把调查结论转成自己项目的行为规格。规格定义用户能完成什么、输入输出如何对应、失败时如何反馈；具体代码由自己的环境与技术选择决定。这样，研究材料能够支持独立实现，也避免把参考对象的偶然结构变成不必要的设计约束。

最后保留反例和未知项。发现一条调用路径可以支持某个解释，却未必排除其他路径；未覆盖的状态需要继续测试，或者明确排除在首版范围之外。有限而清楚的结论，比表面完整但无法核验的说明更有复用价值。

## Productization Direction｜产品化方向 🚀

围绕 REA 这样的能力，可以形成面向开发与产品研究的调查工作台。用户以具体功能问题进入，系统逐步组织目标、证据、关系和未解决项，并把重要结论连接到原始材料。

另一个方向是从调查到行为规格的衔接。经过人工确认的发现，可以转成需求条目与测试场景；后续实现时，再逐条检查行为是否满足约定。调查与开发之间有明确交接，能够减少模型在长流程中把假设当事实传播。

版本差异分析也有独立价值。相同功能在不同版本中的变化，可以为维护、兼容和迁移提供线索。不过差异记录仍需保留比较条件，缺失信息不能直接当成没有变化。

这些是基于项目能力延伸的产品方向，不代表 REA 已经提供完整的需求、开发和验收管理系统。它的基础价值仍然在于，把专业调查工具与 Agent 的问题推进能力连接起来。

---

## Product Observation｜进一步观察

REA 让软件研究有机会进入更日常的 AI 工作流。用户提出具体问题，Agent 调用分析工具寻找线索，再依据结果决定继续调查还是形成结论。

这条路径是否可靠，取决于解释能否回到证据，以及不确定性是否在进入开发决策前被保留。自动化提高调查效率之后，产品仍然需要明确什么已经知道、什么还没验证，以及这些发现究竟支持哪些实现要求。

对 Vibe Coding 实践而言，值得学习的是这套从理解到验证的方法：先定义希望解决的用户问题，再借助工具研究可参考的机制，最终用独立实现与可重复测试检验结果。这样沉淀下来的，才是能够被后续项目复用的产品经验。
