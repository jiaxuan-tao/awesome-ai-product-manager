# Claude-mem｜让编程 Agent 接得上，也查得回 🧠

- Source｜来源：thedotmack/claude-mem 官方 GitHub 仓库 / 官方使用与架构文档
- Type｜类型：开源 AI 项目产品化分析 / Coding Agent / 会话接续 / 工作记录
- Link｜链接：https://github.com/thedotmack/claude-mem

一次编程任务结束时，最值得留给下一次会话的，未必是完整聊天记录。用户更想知道：上次为什么改这里，哪些方案试过但没用，测试到底跑了什么，还有哪一步没有完成。单看当前代码，往往能找到改动，却不一定能找回这些经过；重读整段对话，又可能花大量时间筛掉与当前任务无关的内容。

Claude-mem 把这类信息组织成可以跨会话找回的工作记录。它值得观察的不是记忆容量，而是怎样让下一次工作既不用从头摸索，也不把上一次的总结当成当前事实。本文基于项目公开资料分析，未安装或实测；下文案例与评估方法均为分析示例。

## What It Is｜它是什么 🧩

Claude-mem 是为编程 Agent 提供跨会话上下文的开源项目。以 Claude Code 集成为例，它通过会话和工具相关的钩子接收记录，由后台服务整理观察与摘要，并在后续会话提供已有项目背景。它不要求开发者在每次离开前手写一份交接文档，也不等于完整保存了执行现场。[钩子生命周期](https://docs.claude-mem.ai/architecture/hooks)

这里的「接续」与恢复一个暂停进程不同。新的 Agent 可以知道某次任务检查过哪些文件，但上次打开的终端、未保存的编辑和正在运行的服务，不会因为摘要被找回就自动恢复。历史记录让下一次会话有了排查入口，至于工作能从哪里继续，还要重新确认环境。

## Core Mechanism｜从摘要定位到原始记录 🔗

项目的检索方式有一个值得借鉴的取舍：先返回简短索引，再根据需要查看前后时间线、展开观察详情，必要时回查已保存的工具输入和输出。最后一层并非完整无损的归档，较大的记录可能被截断；不能因为存在回查入口，就假定每次工具执行都留下了足够证据。[分层检索说明](https://docs.claude-mem.ai/progressive-disclosure)

这几层回答的是不同问题。索引帮助定位「是否有过这件事」；时间线帮助判断「这是最初尝试，还是后来确认的方案」；工具记录则能在保留范围内回答「当时跑的是哪个命令，返回了什么」。如果只需要找到相关模块，一条简短观察就够了；如果准备据此跳过测试，就需要更具体的依据。

这种设计不是为了让新会话读得越多越好，而是把补充信息的成本留到真正需要的时候。一次测试的摘要不必默认占用大量上下文，但它最好能指向当时的命令、输出和会话。否则摘要一旦省略了条件，后面的 Agent 只能在重新排查与相信旧结论之间二选一。

## Use Case｜第二天继续修同一个问题 📌

假设昨天修复了记账应用的导出问题：旧数据缺少币种时，导出应保留原金额并标记未知，而不是默认套用当前币种。记录里写着「兼容旧记录，测试通过」。第二天用户要求增加按月份导出，相关文件已经被另一次修改调整过。

新会话可以利用昨天的记录快速定位导出逻辑，知道兼容旧数据是需要保留的约束。如果要判断昨天的测试覆盖了什么，可以回查当时执行的命令和输出。假如只跑了金额格式化的单元测试，就不能把那次成功解释成整个导出流程已经通过，也不能用它为新增的月份筛选背书。

真正的接续是沿着记录找到当前分支上的实现，确认原有约束没有被破坏，再针对新改动补足验证。这样既不用重新推导当初为什么不能默认币种，也不会跳过当前版本必须做的检查。节省的是寻找入口和还原决策的时间，不是省掉验证。

## Product Insight｜历史证据与当前事实要分开 🔍

「摘要写着已修复」「当时的测试输出支持该结论」「今天的代码仍然正确」是三个不同判断。第一项是生成的叙述，第二项有特定运行条件，第三项依赖当前代码和验证。记忆产品如果只把三者压成一条绿色状态，信息越好找，错误结论反而越容易被复用。

项目的本地查看器 My Work 提供了一个具体例子：进行中表示最近保存的工作状态，不代表 Agent 此刻还在运行；待检查表示父请求被明确报告完成；已检查则记录用户对某一版本做过检查，不等于系统证明结果正确。出现实质性的新更新时，旧的检查状态会失效。[My Work 状态说明](https://docs.claude-mem.ai/usage/my-work)

这个区分比增加一个进度数字更有价值。例如，用户昨天看过导出文件，今天 Agent 又改了格式，原来的检查就不应覆盖新结果。让「我看过什么版本」与「Agent 当前报告了什么」分别成立，才能避免工作台在结果改变后仍给出过时的完成暗示。

已有 T3 Code 文章关注的是如何从另一台设备接回执行环境；Claude-mem 的 T3 Code 集成则通过服务器侧受支持提供方的钩子记录和找回上下文。[集成说明](https://docs.claude-mem.ai/t3code-integration) 两件事可以配合，但打开同一台主机不是找回某次决策，找到一份历史记录也不是恢复运行中的任务。

## Product Boundary｜记录得下来，不等于应该一直留着 🛡️

能够回查工具记录，会提高核对能力，也意味着系统处理的可能不只是几句摘要。输入、命令输出或文件内容都可能带有不适合留存的信息。项目文档说明，可以用私密标签排除标记内容，也提供需主动开启的规则脱敏；这些措施针对记录链路，不意味着当前对话里的内容对模型不可见，也不能保证识别所有敏感信息。[私密标签](https://docs.claude-mem.ai/usage/private-tags) · [自动脱敏](https://docs.claude-mem.ai/usage/auto-redaction)

「本地查看」也不能概括所有功能的数据流向。官方文档把本地查看器与可选的历史分析步骤分开：前者读取已保存的数据，后者在用户选择提交后会把所选历史中的提示词及相关元数据发送给服务处理。评价这类工具时，应该针对具体入口确认采集、保存和发送的范围，而不是根据「本地记忆」四个字作整体判断。[查看器与历史分析说明](https://docs.claude-mem.ai/usage/my-work)

对接续中的 Agent，还要分清历史意图与本次授权。记忆里保存着「上次准备推送」，不代表上次真的推了，更不代表用户允许这次直接推送。旧记录可以帮助恢复讨论，却不能替代当前请求、工作区状态或对外操作所需的确认。特别是任务已换分支、用户已改口时，越容易召回旧计划，越需要让它保持在参考层。

## Reusable Value｜怎样判断接续是真的省事 🔁

可以用一组很小的对照任务评价这类工具。第一轮完成一次范围明确的修复，留下当时的分支、涉及文件与测试结果；随后改变其中一个条件，例如把修复留在旧分支，或让新版本的测试覆盖范围不同。第二轮只提出续做目标，观察 Agent 找回了哪些线索、重新核对了哪些条件，又有哪些内容仍需要用户解释。

比较时不只统计找回了多少条记录，而要看三类代价：重新定位问题用了多久；有多少旧结论被错误套用；用户为纠正这些判断又付出了多少沟通和返工。如果系统记住了更多细节，但更频繁地把上一次通过的测试当作当前结果，接续体验并没有改善。

没有记忆工具，也可以先把同样的方法落进项目文档：保留关键决定及其原因、可追溯的验证结果，以及尚未完成的步骤。项目约束可以进入维护文档，临时尝试可以留在工作记录。这样即使检索缺失，新的 Agent 仍知道去哪里找当前依据；记忆负责加速定位，不应成为唯一的信息来源。

## Productization Direction｜让接续记录带着适用条件 🧭

一个可延展方向，是让记录在被引用时同时带出来源、当时的分支或提交、是否经过人工确认，以及哪些信息还需要复核。对于「已经修复」这样的结论，可以直接把历史观察与当前版本并排呈现，提示用户或 Agent 先比对，而不是在找到关键词后自动更新任务状态。

另一个方向是把召回结果按下一步动作组织。用户刚回来时，先看到哪些决定仍可沿用、哪个问题需要重新确认，以及能去哪里查看证据；只有判断受阻时才展开原始记录。这是产品建议，不代表 Claude-mem 已经实现基于 Git 版本的自动失效判断。尤其是分支相同但工作区已改变时，仍需要实际检查。

## Product Observation｜进一步观察

Mem0 那篇讨论长期记忆如何成为产品能力，Claude-mem 这一篇关心的是具体工程工作如何留下可复用、可核对的过程。两者相邻，但评价标准不同：不是系统保存了多少历史，而是下一次能否找到正确的起点，认出哪些结论已经失效，并把需要重新验证的事项留给当前会话。

真正有用的接续，不是让 Agent 表现得好像从未离开，而是让它知道：上次做了什么、当时凭什么得出结论，以及今天应该先检查什么。
