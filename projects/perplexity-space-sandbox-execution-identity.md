# Perplexity SPACE｜让 Agent 请求找到正确的执行环境 🧩

- Source｜来源：Perplexity 官方 GitHub 仓库 / SPACE 官方文档 / Perplexity 官方技术博客
- Type｜类型：开源 AI 项目产品化分析 / Agent Sandbox / Execution Identity / Agent Infrastructure
- Link｜链接：https://github.com/perplexityai/SPACE

Agent 能运行代码，不代表它能可靠地完成任务。除了代码是否正确、权限是否合适，还需要确认：这次操作究竟发生在哪一个环境，读取和修改的是否仍是用户期待的那份状态。

Perplexity SPACE 提供了一个观察这一问题的具体样本。它让我们把注意力从“给 Agent 一个沙箱”，进一步移向执行过程中的环境连续性。

本文基于官方公开资料进行产品分析，没有实际部署 SPACE，也不构成独立安全审计。以下会区分项目已说明的机制与可以继续延展的产品设计方向，不据此对其他沙箱平台做安全排名。

---

## What It Is｜它是什么 ⚙️

SPACE 全称为 Sandboxed Platform for Agentic Code Execution，是一个通过 HTTP API 管理隔离代码执行环境的平台。它使用 Firecracker microVM，为应用提供 Linux 环境、命令执行、输出获取和沙箱生命周期管理。应用决定运行什么、保留什么结果；SPACE 负责环境及其进程和输出连接。[官方仓库](https://github.com/perplexityai/SPACE)

因此，它不是帮用户规划任务的通用 Agent，也不是输入需求就生成完整应用的工具。更合适的位置，是 Agent 应用背后的执行基础设施：上层产品组织任务，下层环境承接代码和文件操作。

这一区别影响选型。个人做一个简单内容生成工具，未必需要维护自己的执行平台；当产品允许不同用户上传文件、运行脚本，或让任务持续执行时，环境本身才会成为需要单独管理的产品对象。

---

## Why It Matters｜为什么值得关注 💡

设想一个数据分析 Agent：用户上传报表，系统准备环境，Agent 执行清洗，再继续生成图表。用户关心的是同一项分析是否在继续，而不是后台机器是否发生过变化。

以下是用于理解问题的示意场景，并非项目事故记录：第一次运行留下了中间文件，之后环境恢复到了另一台机器，但某个延迟请求仍读取旧运行实例。它可能成功返回内容，文件名也正确，却不属于当前这一步任务。

这种问题比直接报错更难被普通用户发现。界面上的“读取成功”容易被理解为拿到了正确资料，之后的模型推理还可能把过期结果整理成一份看似完整的报告。

从产品角度看，环境隔离和任务连续性回答的是不同问题。隔离关注操作不要越界；连续性还要关注操作是否基于当前状态。只要产品允许恢复长任务，就不能仅凭项目名称相同或连接成功，判断任务已经正确接续。

## Core Mechanism｜执行环境为什么还需要身份 🔗

### Sandbox Identity｜环境标识不等于运行实例

官方技术博客区分逻辑沙箱与实际运行实例：沙箱保留稳定标识，但恢复或迁移可能形成新的执行代次。请求携带绑定所选运行实例和访问范围的短期签名凭证，接收方在转发前将其与本地运行身份核对，而不只确认沙箱名称。[执行身份设计说明](https://www.perplexity.ai/en-GB/hub/blog/how-space-routes-requests-to-the-right-sandbox-execution)

对产品设计而言，这相当于区分“用户想继续哪个工作环境”和“这一步实际上由哪个实例处理”。前者方便用户理解任务，后者方便系统证明过程没有接错。两类信息需要关联，但不必把全部基础设施细节展示给用户。

### Connection Lifetime｜连接成功也不代表状态仍然有效

该设计还处理旧实例关联的长连接，并对符合条件的操作重新解析目标。它不是无限重试机制；身份更新传播存在窗口，旧凭证在过期或旧接收方获知实例退役之前，仍可能被旧实例接受。其信任假设包括控制面签发方、工作节点内核及本地管理服务，不覆盖节点 root 或特权集群管理员失陷。[机制及信任边界](https://www.perplexity.ai/en-GB/hub/blog/how-space-routes-requests-to-the-right-sandbox-execution)

这里的产品启发不是“断开就重连”，而是先判断断开是否代表执行对象发生变化。为了维持界面流畅而隐藏这种变化，可能让用户误以为任务一直在同一状态上推进。恢复体验应优先保证连续性的含义成立，再减少等待和操作成本。

## Use Case｜适用场景 📌

### Long-running Analysis｜需要接续状态的分析任务

对于包含上传、清洗、计算和导出的分析产品，中间状态决定后续步骤能否成立。产品需要定义哪些内容必须保留，哪些可以重算，以及恢复后应检查什么，而不是把“环境重新启动”直接等同于“任务继续成功”。

SPACE 的架构文档将沙箱、生命周期操作和命令流视为不同生命周期；操作被接受并不代表环境已就绪，环境状态也不等于命令退出结果。同一沙箱内的进程共享环境和文件系统，因此应用仍需决定哪些任务适合共享沙箱。[架构文档](https://github.com/perplexityai/SPACE/blob/main/docs/architecture.md)

这意味着多用户产品不能只增加一个执行按钮。任务与环境如何对应、结果归属如何记录、状态不确定时能否继续，都需要上层应用明确设计。

### Coding Agent｜跨步骤的软件开发任务

Coding Agent 的修改、测试和结果审查应能对应到同一份代码状态。如果恢复后读到了另一份工作目录，单独显示“测试通过”并不足以让人判断当前修改可用。

SPACE 可以作为这一类执行层的参考，但它不会代替代码审查或业务验收。产品仍需把代码版本、测试对象和输出文件关联起来。环境身份解决的是执行目标核对，不是生成内容必然正确。

## Product Insight｜产品观察 🔍

### 拒绝错误目标，也是正确完成任务的一部分

产品常把执行成功率看作越高越好，但不同失败需要不同解释。目标身份不一致时，拒绝执行可能正是应有行为。如果为了减少错误提示而放宽校验，就可能把本来可见的失败，变成难以发现的错误修改。

因此，体验指标不宜只统计请求是否成功，还应观察拒绝之后用户是否知道原因、任务是否保持原状态、恢复后是否仍能确认结果归属。不能把安全拒绝和普通服务故障混在一起，也不能把所有拒绝都视为无需处理的正常现象。

### 恢复任务，不等于重新执行一次

官方首次运行指南要求根据进程退出事件和结果判断执行是否完成，而不是只看连接关闭；命令输出流也不能直接当作永久日志。[命令执行指南](https://github.com/perplexityai/SPACE/blob/main/docs/first-sandbox.md)

对上层应用的推论是：连接恢复、环境恢复和业务重做应有不同语义。用户点击“继续”时，系统究竟是在查看原任务、接回当前环境，还是创建新的执行，需要能解释清楚。否则，技术层恢复连接，业务层却可能重复生成文件或误认历史输出。

仓库中的[重试与幂等性笔记](../notes/tools/tool-retry-and-idempotency.md)已讨论“是否重复做了一次操作”。本文补充的前提是“这一次操作落在哪里”。两者关联，但不能互相替代。

### 兼容接口不能代替迁移验证

SPACE 提供 E2B Compatibility Wrapper，但官方说明它是 SPACE 维护的兼容目标，测试覆盖特定 Python SDK 基线，并非对所有版本和 JavaScript SDK 的全面保证；部分生命周期名称的对应关系也有差异。[兼容层文档](https://github.com/perplexityai/SPACE/blob/main/docs/ecw.md)

因此，产品团队评估替换执行后端时，不能只看示例能否跑通。还需要验证实际使用的操作、状态语义和恢复结果。接口调用保持相似，并不自动意味着用户体验、成本结构和运维要求也保持不变。

## Reusable Value｜可复用价值 🔁

SPACE 对现有资料库的补充，不是再介绍一次沙箱的必要性。已有 [E2B 分析](./e2b-agent-sandbox-platform.md)关注隔离执行环境的整体产品价值，这里更值得沉淀的是执行对象核对与状态接续的观察方法。

分析类似产品时，可以沿三个层次检查：任务预期使用什么环境；系统实际选中了哪个运行实例；最终结果能否与该实例和输入状态关联。这样可以把笼统的“Agent 出错了”，拆成可以定位和讨论的产品问题。

测试也应覆盖变化中的环境。官方加固文档列有并发、恢复和令牌范围等测试，并明确部分覆盖依赖特定环境或测试身份；测试缺失不能解释成验证通过。[原生 API 加固说明](https://github.com/perplexityai/SPACE/blob/main/docs/native-api-hardening.md)

由此可以延展出更贴近任务的验收方式：恢复前后，用户看到的结果是否属于同一项工作；状态不明时，界面是否错误承诺完成；必要的执行记录是否足以帮助定位差异。这些是产品验收建议，不是本文已经执行过的测试结果。

## Productization Direction｜产品化方向 🚀

### Task Execution Receipt｜面向任务的执行凭据

一种可延展方向，是把任务、输入版本、环境实例、命令结果和产物位置组织成可查询记录。用户不需要理解每个基础设施标识，但应能确认“这份报告使用了哪次输入”“这次测试针对哪份修改”。这属于上层产品设计建议，不应当作 SPACE 已有完整业务界面。

### Recovery Review｜恢复前后的状态确认

另一方向是为高价值任务提供恢复摘要：说明恢复的是哪个任务、哪些状态已确认、哪些结果仍待核实。只有会改变工作结果的差异才需要用户关注，不宜把每次底层调度都变成确认弹窗。

### Compatibility-aware Operations｜把兼容性变成维护约束

版本文档将服务契约稳定性与兼容证据关联，并区分宿主升级和既有运行环境的兼容关系；其中的发布规划不能视作所有承诺已经实现。[版本与兼容策略](https://github.com/perplexityai/SPACE/blob/main/docs/versioning.md)

从产品化角度看，长期运行平台还需要回答：升级之后旧任务能否继续，保留的环境能否恢复，回退会影响什么。能够创建新环境，只证明了一条起点路径，不能替代这些存量任务的维护能力。

## Product Observation｜进一步观察

SPACE 的安装指南涉及 Linux x86_64、KVM 等基础条件，并非在个人电脑安装一个普通应用就能使用。[本地安装要求](https://space.docs.perplexity.ai/guide/installation.html) 对小型项目而言，先确定是否真的需要自建执行基础设施，通常比追随热点更重要。

这个项目值得记录的原因，是它让一个容易被界面隐藏的问题变得具体：Agent 的操作不仅要被允许，还要落在预期的环境和当前状态上。

当产品从单次生成走向持续执行，可靠性不只体现在模型回答和代码质量，也体现在一次任务经历中断、恢复和环境变化之后，系统是否仍能说明它在哪里执行、结果从哪里来，以及哪些状态尚不能确认。
