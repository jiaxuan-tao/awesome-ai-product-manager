# DSPy｜从手工 Prompt 调整到可评估的 AI 程序优化 🧪

- Source｜来源：Stanford NLP DSPy GitHub / DSPy Docs
- Type｜类型：开源 AI 项目产品化分析 / LLM Programming Framework / Prompt Optimization / Evaluation
- Link｜链接：https://github.com/stanfordnlp/dspy

DSPy 是一个用于构建和优化语言模型程序的开源 Python 框架。

它提出的方向不是继续手工雕琢越来越长的 Prompt，而是先声明任务需要什么输入和输出，再用可组合模块组织流程，并通过样本与评价指标优化程序中的提示和参数。

从产品视角看，DSPy 值得关注的不是某一种优化算法，而是它改变了团队讨论 AI 应用的方式。

> 当 Prompt 不再是只能依靠经验调整的文本，产品团队就必须更清楚地定义任务、样本和“什么叫更好”。

---

## What It Is｜它是什么 🧩

传统 LLM 应用经常从一段 Prompt 开始。团队把角色、任务、格式、示例和限制写进文本，根据几次输出不断修改措辞。

这种方式适合快速探索，但当应用包含分类、检索、生成、工具调用或多个模型步骤时，Prompt 会逐渐与代码、样本和业务规则纠缠。换模型、调整流程或增加字段，都可能要求重新手工调试。

DSPy 提供了另一种组织方式。

开发者通过 Signature 声明任务的输入和输出，通过 Module 决定任务采用直接预测、推理、工具使用或其他执行策略，再通过 Optimizer 根据训练样本和评价函数优化程序。

它并不是让 Prompt 消失。语言模型最终仍需要接收指令和示例，但这些内容可以由框架围绕任务结构和指标进行生成、选择或调整，而不是完全依赖人工逐句编写。

因此，DSPy 更接近一个 LLM 程序构建与优化层：团队描述任务接口、组合执行结构、提供评价依据，框架负责寻找更合适的模型行为配置。

---

## Why It Matters｜为什么值得关注 💡

AI 产品开发中有一个常见问题：团队知道某版 Prompt “感觉更好”，却很难说明它改善了哪些任务、牺牲了什么，以及换一批真实输入后是否仍然有效。

手工 Prompt 调整容易受到少量示例影响。产品人员看到一条失败结果，就增加一条规则；另一类输入随后变差，又继续补充例外。Prompt 越来越长，但系统为什么改善或退化反而更难解释。

DSPy 把注意力从措辞转向任务定义和评估依据。

如果团队希望优化客服工单分类，就需要说明输入是什么、输出包含哪些字段，并准备代表性工单与评分逻辑。如果要优化 RAG 回答，就需要决定准确性、完整性、引用依据和格式之间如何取舍。

这使产品判断进入优化过程。框架可以尝试不同指令或示例，但它无法替团队决定用户真正需要什么，也无法自动发现一个错误指标正在鼓励错误行为。

从这个角度看，DSPy 的价值不是“自动写出最佳 Prompt”，而是推动 Prompt 优化从个人经验走向可重复实验。

## Core Capability｜核心能力 ⚙️

### Signatures｜声明任务接口

Signature 用结构化方式描述语言模型任务的输入、输出和基本语义。

这种方式把产品要求从一整段自由文本中抽离出来。团队可以更明确地讨论：用户提供哪些信息，系统需要返回哪些字段，哪些结果类型应该受到限制，以及下游流程依赖什么。

对产品而言，清晰接口也有助于区分“模型应该生成什么”和“界面如何展示结果”。当输出结构稳定后，产品可以围绕状态、编辑、确认和错误提示设计更可靠的交互。

### Modules｜组织执行策略

Module 将任务声明与执行方式分开。同一个任务接口可以使用直接预测、分步推理、工具调用或由多个模块组成的流程。

这意味着团队可以在不完全重写产品要求的情况下比较不同实现策略。例如，一个问题回答任务可以先采用直接生成，后来增加检索或工具，但输入输出目标仍然保持清楚。

模块化的真正价值不是堆叠更多步骤，而是让每个步骤拥有相对明确的责任，便于单独评估和替换。

### Optimizers｜围绕指标优化

Optimizer 使用样本和评价函数寻找更适合当前程序的指令、示例或模型配置。

这一步把评估从发布后的检查，推进到构建过程本身。团队不只是先写 Prompt、最后看效果，而是让“什么算成功”持续参与程序优化。

但优化结果只会朝指标指向的方向变化。如果数据只覆盖常见问题，系统可能忽略少数但高风险的边界场景；如果指标只奖励答案相似度，模型可能得到看似接近参考答案、却缺乏依据的结果。

## Use Case｜适用场景 📌

DSPy 更适合任务边界相对明确、拥有代表性样本，并且可以建立评价方式的 AI 应用。

在信息抽取场景中，团队可以明确输入文档和输出字段，用字段准确率、完整性与格式有效性判断结果。相比反复要求模型“严格输出”，这种任务更容易形成稳定的优化闭环。

在分类和路由场景中，团队可以根据真实业务样本比较不同模型和策略，并重点检查错误分类带来的实际成本，而不是只看总体准确率。

在 RAG 应用中，优化对象可能同时包含检索、回答和引用。产品需要避免只提高某个局部分数，却让最终回答变得冗长、延迟增加或引用更难理解。

在 Agent 流程中，DSPy 可以用于优化某些可评估模块或整体行为，但多步骤任务还需要检查工具调用、轨迹、权限和真实环境结果。单一文本评分不能覆盖 Agent 是否真正完成了操作。

对于只有少量用户、需求尚未稳定的早期原型，建立数据集和优化流程可能比直接迭代更重。是否采用 DSPy，应取决于任务重复程度、质量压力和评估可行性，而不是框架是否流行。

## Product Insight｜产品观察 🔍

DSPy 最重要的产品启发，是 AI 应用优化的瓶颈会逐渐从“不会写 Prompt”转向“没有定义好任务和指标”。

当框架能够自动尝试提示和示例，团队仍然必须决定哪些用户输入具有代表性，失败的业务成本是什么，以及质量、延迟、成本和可解释性之间如何权衡。

它与 Prompt Versioning 解决的问题不同。Prompt Versioning 让团队知道线上使用哪一版、发生了什么变化以及如何回退；DSPy 关注如何利用样本和指标寻找候选配置。自动优化产生的结果同样需要版本记录、发布审核和回归验证，两者是连续环节，而不是替代关系。

它也不等同于 Agent Evaluation。Agent Evaluation 关注任务结果和执行轨迹如何被评判，DSPy 可以使用其中部分评价信号优化程序，但不会替产品定义授权是否正确、用户是否理解过程或一次真实副作用能否接受。

LangChain 更偏向连接模型、数据、工具和流程，DSPy 更强调任务声明以及围绕指标优化模型程序。它们都在推动应用从单次模型调用走向结构化系统，但切入点不同。

### 指标会成为产品配置

在传统产品中，需求文档描述功能应该怎样工作；在可优化的 AI 系统中，评价函数进一步影响系统会朝哪个方向学习。

因此，指标不是纯技术实现。产品团队需要参与定义不同错误的权重，识别不能被单一分数压缩的体验要求，并保留人工复核高风险样本的机制。

### 优化可能放大错误目标

自动优化容易给人一种“结果由系统客观选出”的感觉，但优化过程只忠于数据和指标。

如果训练样本不代表真实用户，优化后的程序可能只在测试集上表现更好。如果评价器本身由模型完成，还需要检查评分偏差、提示敏感性和与人工判断的一致程度。

成熟产品需要保留独立验证集、关键边界测试和线上反馈，避免优化器反复适应同一批样本。

### 模型可迁移不等于结果自动稳定

结构化任务和模块可以降低更换模型时的重写成本，但不同模型仍然拥有不同能力、价格、延迟和行为边界。

每次模型或优化策略变化都应重新评估。可迁移的价值是让实验更有结构，而不是保证任何模型都能产生相同结果。

## Reusable Value｜可复用价值 🔁

DSPy 为 AI 产品实践提供了一套可复用的优化思路。

首先，将任务表达为清楚的输入、输出和成功条件。不要从“写一段更强的 Prompt”开始，而要先说明用户交付什么、系统返回什么，以及结果将如何进入后续流程。

其次，建立代表真实使用场景的样本。数据不只包含标准成功案例，还应覆盖模糊输入、信息缺失、冲突要求和高成本错误。

再次，把评价拆成多个维度。准确性、完整性、格式、依据、延迟和成本可能无法由一个分数完全代表。对于关键任务，还需要保留确定性规则和人工判断。

然后，将优化结果视为候选版本。它需要与基线比较、经过独立回归测试，并记录所使用的数据、指标、模型和优化配置。

最后，连接线上反馈。用户修改、拒绝和任务失败可以转化为新的测试样本，但不能未经检查就直接进入优化集，否则噪声和异常行为也会被系统学习。

这套方法即使不使用 DSPy 也有价值。它帮助团队把 Prompt 调整从零散经验，转化成任务定义、实验、评估和发布组成的产品循环。

## Productization Direction｜产品化方向 🚀

### AI Program Workspace｜AI 程序工作台

产品可以让团队在同一空间管理任务接口、模块结构、样本集、指标和候选版本，并清楚展示一次优化改变了什么。

### Metric Design Assistant｜指标设计助手

平台可以帮助产品人员把自然语言质量要求拆成可执行评价维度，提示缺少的边界案例，并对比自动评分与人工判断之间的差异。

### Optimization Review｜优化结果审查

自动生成的新配置不应直接进入生产。审查界面可以比较基线与候选版本在不同场景下的表现，同时展示质量提升所带来的成本和延迟变化。

### Continuous Product Learning｜持续产品学习

线上失败、用户修订和支持记录可以进入待审核样本池。团队确认其代表性后，再用于回归测试和下一轮优化，让真实使用逐渐改善系统。

DSPy 展示了 LLM 应用从“手工写 Prompt”走向“声明任务并优化程序”的方向。

真正的产品价值不在于让优化完全自动化，而在于让每次改进都有明确目标、代表性证据和可追溯结果。模型负责生成，框架帮助实验，产品团队仍然负责定义什么值得被优化。
