# MCP Sampling｜让 Server 请求模型完成生成任务 🔄

- Source｜来源：Model Context Protocol Specification
- Type｜类型：AI 产品方法观察 / MCP Sampling / Server-initiated Generation / Model Control
- Link｜链接：https://modelcontextprotocol.io/specification/2025-11-25/client/sampling

MCP 通常被理解为 AI 应用连接外部工具和数据源的协议。

在这种关系里，Client 拥有模型，MCP Server 提供资源或工具。但有些 Server 在完成任务时，也需要模型参与判断、生成或处理信息。

MCP Sampling 为此提供了一种标准方式：Server 可以向 Client 发起模型生成请求，由 Client 使用自己可访问的模型返回结果。

这种设计让 Server 不必分别集成不同模型提供方，也不必直接持有用户的模型密钥。与此同时，模型选择、上下文使用和用户批准仍然保留在 Client 一侧。

从产品视角看，Sampling 的核心不是“Server 也能调用模型”，而是如何在 Server、Client、模型和用户之间重新分配控制权。

> Server 可以表达它需要什么模型能力，但不应自动获得用户的模型、数据和预算。

---

## What It Is｜它是什么 🧩

MCP Sampling 是 Server 向 Client 请求语言模型生成结果的协议能力。

Server 可以提交一组消息、可选的系统提示、模型偏好、上下文请求和最大输出长度。Client 接到请求后，根据自身能力和用户设置选择模型，再把生成结果返回给 Server。

这里存在一个重要边界：Server 提供的是请求和偏好，不是最终决定。

官方规范允许 Server 表达对成本、速度和智能程度的相对偏好，也可以提供模型名称提示，但 Client 可以根据自己可用的提供方进行映射，并保留最终选择权。Client 还可以修改或省略 Server 建议的系统提示，并决定是否加入其他上下文。

这使 Sampling 不只是一次远程模型调用，而是一种带有协商关系的生成请求。

---

## Why It Matters｜为什么值得关注 💡

如果没有 Sampling，一个需要模型能力的 MCP Server 通常要自行连接模型提供方。

这意味着 Server 开发者需要处理模型 SDK、密钥、费用、模型差异和数据策略。用户也可能被要求为每个 Server 重复配置模型账号，难以知道数据最终发给了谁。

Sampling 把模型访问集中到 Client。

Server 只描述任务，Client 使用用户已经配置的模型环境完成生成。这样，同一个 Server 可以在不同 Client 中使用不同模型，而不必绑定特定提供方。

这种结构也有利于统一治理。Client 可以集中记录 Sampling 请求、限制模型范围、控制预算，并在敏感任务前获得用户批准。

但能力集中也会扩大 Client 的责任。它不仅要决定是否接受请求，还要判断 Server 提供的消息是否可信、哪些本地上下文可以加入，以及一次生成是否可能继续触发工具和后续 Sampling 循环。

Sampling 值得关注，正是因为它把模型使用从 Server 内部实现变成了 Client 可管理的产品行为。

## Control Flow｜控制关系如何形成 ⚙️

### Server Requests｜Server 表达任务需要

Server 发起 Sampling 时，会提供完成当前任务所需的消息和参数。

例如，一个文档处理 Server 可以请求模型对读取到的内容进行分类，一个研究 Server 可以请求模型判断哪些线索值得继续探索，一个专业工具也可以请求模型把结构化结果转化成用户可读的说明。

Server 需要尽量说明请求目的和所需输出，而不是把所有内部状态直接交给模型。请求边界越清楚，Client 越容易判断是否合理。

### Client Decides｜Client 保留最终决定

Client 负责选择实际模型，并可以根据用户设置、组织政策和当前预算调整 Server 的偏好。

Server 可能更重视智能程度，但 Client 可以因为成本限制选择更轻量模型；Server 可能建议某个模型系列，但用户未必拥有对应访问权限。

这种抽象避免了 Server 把模型选择写死，也让模型替换不必改变 Server 的业务逻辑。

### User Controls｜用户理解并控制请求

官方规范建议 Client 实现用户批准控制，但产品不能把批准简化成频繁出现的“是否允许”弹窗。

用户需要理解哪个 Server 发起请求、为什么需要模型、会发送哪些数据、预计产生什么成本，以及请求是否会继续调用工具。

低风险、重复且边界稳定的请求可以根据用户设置自动执行；包含敏感内容、高成本模型或外部副作用的请求则需要更明确的确认。

### Results Return｜结果回到 Server

模型输出返回 Server 后，Server 可以继续处理结果。在支持工具使用的 Sampling 流程中，模型还可能提出工具调用，Server 执行后再发起下一次请求。

这让 Server 能够形成多轮模型与工具循环，也带来失控风险。产品需要设置迭代次数、时间和成本上限，并让失败能够中止，而不是允许请求无限继续。

## Use Case｜适用场景 📌

Sampling 适合 Server 拥有专业数据或工具，但需要模型完成非确定性判断的场景。

在文档处理场景中，Server 可以负责读取、解析和转换文件，再请求 Client 的模型进行摘要、分类或信息提取。文件处理逻辑留在 Server，模型选择和生成策略由 Client 管理。

在研究与数据工具中，Server 可以先获取信息，再请求模型判断结果是否完整、生成下一步查询或整理最终说明。它不需要为每位用户单独管理模型密钥。

在开发工具中，Server 可以读取代码分析结果，再请求模型解释问题或提出修改方向。但涉及实际修改、执行命令或提交代码时，仍然需要独立工具权限和用户控制。

如果任务只需要确定性计算，直接由 Server 完成更合适。Sampling 不应被用来替代普通代码逻辑，也不应因为接入方便就让每个 Server 随意增加模型调用。

## Product Insight｜产品观察 🔍

MCP Sampling 最重要的产品启发，是模型本身也可以成为由 Client 管理的共享能力。

过去，模型通常属于某个应用后端。Sampling 让多个 MCP Server 可以通过同一 Client 请求模型，同时不必知道用户具体使用哪个提供方。

这会推动 AI Client 从聊天界面进一步变成模型控制中心。它需要管理模型访问、成本策略、上下文边界、请求历史和用户偏好。

### 模型偏好需要转化成产品策略

成本、速度和智能程度不是纯技术参数，而是用户任务的不同取舍。

Client 可以根据任务类型建立策略：简单格式转换优先低成本，交互式任务优先低延迟，高价值分析才使用更强模型。Server 提供偏好，产品则需要结合用户目标做最终决策。

### Sampling 请求需要可解释

用户连接 MCP Server 时，往往关注它能访问哪些工具和数据，但 Sampling 还意味着 Server 可以消耗模型预算并影响上下文。

连接详情页应说明 Server 是否会请求 Sampling、可能使用哪些数据、是否包含工具循环，以及用户如何关闭或限制这种能力。

### 上下文不能默认全部共享

规范允许 Server 请求加入来自当前或其他 Server 的上下文，但 Client 可以忽略该请求。

产品应坚持最小必要原则。一个处理当前文件的 Server 不应默认获得所有已连接系统的上下文。跨 Server 数据组合需要清楚用途和权限依据。

这与 MCP Resources 的控制关系不同。Resources 由应用选择并读取外部上下文；Sampling 是 Server 请求使用 Client 的模型。它也不同于 Tools：Tool 让模型请求外部行动，Sampling 则让 Server 请求模型计算。Authorization 负责连接身份和访问范围，不能替代对每次模型请求的数据与成本判断。

## Reusable Value｜可复用价值 🔁

设计 Sampling 能力时，可以先建立请求说明。

每次请求至少应记录发起 Server、任务目的、输入来源、模型策略、最大输出和是否允许工具使用。这样，Client 才能执行策略、展示必要提示并在异常时追溯。

模型选择不应只依赖 Server 提供的名称。产品可以维护任务级模型策略，把质量、延迟、成本、数据地域和组织允许列表共同纳入判断。

上下文加入也需要独立控制。Server 请求哪些数据、Client 实际提供哪些数据，以及用户是否批准跨来源组合，应分别记录。

运行时还要设置三类边界：

1. **成本边界**：单次与累计 Token 或费用预算。
2. **执行边界**：最大轮数、工具调用次数和超时时间。
3. **数据边界**：允许进入请求的资源、会话和敏感信息范围。

评估 Sampling 体验时，可以观察请求批准率、拒绝原因、模型选择是否符合任务、循环是否按预期结束，以及用户能否理解费用和数据去了哪里。

## Productization Direction｜产品化方向 🚀

### Sampling Permission Center｜Sampling 权限中心

用户可以查看哪些 Server 被允许请求模型、当前使用什么策略、最近产生多少调用，并按 Server 或任务类型调整权限。

### Model Policy Router｜模型策略路由

Client 可以根据任务价值、延迟要求、隐私和预算选择模型，同时向 Server 返回实际使用结果，避免每个 Server 自行实现路由。

### Request Preview｜请求预览

高风险 Sampling 执行前，产品可以展示请求目的、数据来源、预计模型和成本，而不是暴露难以理解的原始协议参数。

### Loop Guard｜循环保护

对于会继续使用工具和再次 Sampling 的 Server，Client 可以设置最大轮数、费用和运行时间，并在接近边界时要求用户决定是否继续。

MCP Sampling 让 Server 可以复用 Client 已有的模型能力，降低了重复集成成本。

真正成熟的 Sampling 产品，不只是把请求转发给模型，而是让模型选择、上下文使用、费用和循环过程始终处在用户与 Client 可以理解和控制的边界内。
