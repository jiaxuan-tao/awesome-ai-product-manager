# MCP Tasks｜让长时间工具调用拥有可查询的任务状态 ⏳

- Source｜来源：Model Context Protocol Specification - Tasks
- Type｜类型：AI 产品方法观察 / MCP Tasks / Long-running Operations / Deferred Results
- Link｜链接：https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks

普通工具调用通常假设请求会在一次连接中完成：客户端发出调用，Server 执行操作，然后直接返回结果。

但很多 AI 任务并不适合这种模式。大规模文档处理、批量数据分析、长时间代码执行或外部系统作业可能需要几分钟甚至更久。连接可能中断，用户也未必愿意一直停留在当前页面。如果产品仍把它们当成一次同步请求，就很难表达任务正在运行、何时完成，以及稍后如何取回结果。

MCP Tasks 为这类情况提供了一种协议对象。它把一次耗时请求包装成具有独立标识和生命周期的任务，让请求方可以查询状态、等待延迟结果，并在支持时取消任务。

需要注意的是，MCP 官方规范目前仍将 Tasks 标记为实验性能力。它值得用于观察长任务如何进入协议层，但不能被描述成已经稳定普及的默认方案。

---

## What It Is｜它是什么 🧩

MCP Tasks 是对现有 MCP 请求的增强，而不是另一种独立工具类型。

请求方可以在支持任务模式的请求中加入 Task 参数。接收方不必等到真实操作完成后才响应，而是先返回一个包含 `taskId`、当前状态、更新时间和轮询建议等信息的任务对象。实际结果在任务完成后通过结果查询获得。

官方规范把 Task 描述为承载底层请求执行状态的持久状态机。它既可以用于客户端调用 Server 的工具，也可以在双方声明对应能力时，用于 Sampling 或 Elicitation 等方向的请求。

这种两阶段模式改变了结果关系：第一次响应说明“任务已经被接受”，并不代表业务操作已经成功；最终结果需要在任务进入完成状态后单独获取。

---

## Why It Matters｜为什么值得关注 💡

AI 产品正在从即时回答走向持续执行。一个 Agent 可能需要抓取多个网页、处理大量文件、运行代码、等待第三方作业，或者在用户暂时离开后继续工作。

如果这些操作没有独立任务身份，产品会遇到几个问题。页面关闭后难以重新找到运行状态；网络断开后不知道是否需要重新提交；调用超时可能被误认为业务失败；用户点击两次还可能创建重复作业。

Tasks 的价值，是把“某次工具调用仍在进行”变成可识别、可查询的协议状态。客户端不必依赖一个长期保持的请求，也不必把运行状态只存在前端内存中。

这对用户信任也很重要。产品能够区分任务已接受、正在处理、等待输入、已经完成、发生失败或被取消，而不是在所有情况下都显示一个没有含义的加载状态。

---

## Task Lifecycle｜任务生命周期如何工作 ⚙️

### Capability Negotiation｜能力协商

客户端和 Server 需要先声明是否支持 Tasks，以及哪些请求类型可以采用任务模式。工具还可以进一步说明某项调用要求、允许或禁止 Task 执行。

这避免了请求方假设所有工具都能异步运行。产品应根据能力协商选择同步调用还是创建任务，并在不支持时提供清楚降级，而不是让用户面对协议错误。

### Create and Track｜创建与跟踪

任务模式下，接收方先返回 Task，而不是直接返回最终业务结果。请求方保存 `taskId`，再通过状态查询或可选通知了解变化。

Task 状态应被理解为真实运行状态，而不是装饰性进度。产品不应根据经过时间虚构百分比，也不能因为已创建 Task 就向用户宣布工作完成。

### Retrieve Result｜获取结果

只有任务完成后，请求方才能获取对应操作的最终结果。这个结果仍应遵循原始请求的结果契约，例如工具调用的结构化返回、错误语义和来源信息。

因此，MCP Tasks 解决的是“结果何时可用”，而 Tool Result Contract 解决“结果具体代表什么”。两者处在同一链路的不同阶段。

### Cancel and Expire｜取消与过期

支持取消的实现可以让请求方停止仍在运行的任务。Task 还可以包含生命周期时间，用于管理任务状态和结果可以保留多久。

取消并不天然等于外部操作已经完全撤销。若任务已经触发第三方系统，产品仍需说明取消的是继续等待、后续处理，还是实际业务动作本身。

## Use Case｜适用场景 📌

MCP Tasks 适合执行时间明显超过普通交互请求、结果可以稍后获取，并且用户需要重新进入任务的操作。

在批量文档处理中，Server 可以先接受任务，后台完成解析、索引或摘要，再让客户端取回最终结果。用户可以离开当前页面，并在任务中心继续查看。

在代码和数据执行中，长时间测试、构建或批处理可以拥有独立任务状态。即使前端断开，系统也能根据 `taskId` 重新确认实际结果，而不是盲目再次执行。

在外部作业集成中，MCP Task 可以映射第三方系统已有的 Job。客户端看到统一任务状态，Server 负责连接外部作业生命周期。

对于几百毫秒就能稳定完成的读取或计算，创建 Task 反而增加查询和状态管理成本。产品应只在真正需要延迟结果时使用，而不是把所有工具调用都后台化。

## Product Insight｜产品观察 🔍

MCP Tasks 最重要的产品启发，是把长任务从一次“正在等待的请求”变成可管理对象。

用户不只是需要一个旋转图标，而是需要知道任务名称、创建时间、当前状态、预计产物、是否仍在推进，以及可以取消还是稍后回来。协议提供任务身份和状态，客户端负责把它们转化为可理解的任务体验。

它与相邻内容的边界也很明确。AI Product Latency Design 关注等待如何被用户感知；AG-UI 关注 Agent 运行事件如何进入前端；A2A 关注不同 Agent 之间如何交换任务；MCP Tasks 更具体地处理一次 MCP 请求如何变成可查询的延迟操作。

这些能力可以组合，但不能互相替代。拥有 Task 不代表界面已经清楚，能够展示进度也不代表底层任务可以在断线后恢复。

---

## Reusable Value｜可复用价值 🔁

设计长任务时，可以先定义任务契约：任务如何命名、最终交付什么、哪些状态对用户有意义、何时允许取消、结果保留多久，以及断线后如何重新进入。

还需要区分三个时刻：请求被接受、执行已经完成、业务结果已经验证。只有最后一个状态满足时，产品才能向用户承诺目标完成。

任务失败时，应保留足够上下文说明错误发生在哪个阶段，是否可以重试，以及重试会继续原任务还是创建新任务。对可能产生外部副作用的操作，还要避免用户因状态不清重复提交。

评估这类体验时，可以观察长任务恢复率、重复提交率、取消是否真正生效、结果过期后的处理，以及用户能否理解“等待输入”和“仍在运行”的区别。

## Productization Direction｜产品化方向 🚀

MCP Client 可以围绕 Tasks 建立统一任务中心，把来自不同 Server 的长任务按状态、来源和创建时间组织起来。用户能够查看、取消、重新打开结果，并知道每个任务连接了哪个外部系统。

Agent 平台还可以把同步与异步执行做成任务策略。根据预计耗时、外部依赖和用户是否需要停留，系统自动选择即时结果、渐进反馈或后台 Task，同时保留明确的降级路径。

可观测平台则可以连接 Task 生命周期、工具调用和最终结果，识别任务长期停留、频繁失败或结果无人领取的问题。

由于 Tasks 仍处于实验阶段，产品化时还应隔离协议变化，避免让业务数据结构直接依赖尚未稳定的字段。当前更适合小范围验证，而不是把所有关键流程一次性迁移到这一机制。

---

## Product Observation｜进一步观察

长任务不是更慢的普通请求，而是一类需要身份、状态、恢复和生命周期管理的产品对象。

MCP Tasks 展示了协议层如何开始承接这种需求。它的长期价值取决于规范稳定性和实现支持，但其中的产品判断已经清楚：当 AI 开始持续执行任务，结果不能只存在一次网络响应里。
