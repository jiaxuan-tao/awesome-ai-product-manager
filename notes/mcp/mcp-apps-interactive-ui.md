# MCP Apps｜让工具结果直接变成可交互界面 🧩

- Source｜来源：Model Context Protocol Official Extension / ext-apps GitHub Repository
- Type｜类型：AI 产品方法观察 / MCP Apps / Interactive UI / Tool Result Experience
- Link｜链接：https://github.com/modelcontextprotocol/ext-apps

MCP 让 AI 应用可以用相对统一的方式连接外部工具和数据源，但工具完成调用后，结果通常仍以文本或结构化数据返回。

这种方式适合简单查询。可当结果包含多组指标、需要用户填写参数、比较多个对象或继续完成一组操作时，纯文本会把大量理解和交互成本留给用户。客户端也需要为每一种工具单独开发展示组件，否则工具能力虽然连接成功，体验却仍停留在“返回一段结果”。

MCP Apps 是 Model Context Protocol 的官方可选扩展。它允许 MCP Server 在提供 Tool 的同时声明对应的交互界面资源，让支持该扩展的 Host 可以把图表、表单、仪表盘或其他操作界面直接渲染在对话中。

从产品视角看，它代表 MCP 从“标准化工具连接”进一步走向“标准化工具体验交付”：外部能力不只告诉 AI 自己能做什么，也可以提供用户理解和继续操作这项能力所需要的界面。

---

## What It Is｜它是什么 🧩

MCP Apps 采用 `Tool + UI Resource` 的组合方式。

Tool 仍然负责定义模型可以调用的能力、参数和返回结果；UI Resource 则包含与该工具关联的 HTML 界面。支持 MCP Apps 的 Host 在调用工具后，可以读取这个资源，并把界面放在受隔离的 iframe 中展示。

例如，一个数据分析 Tool 可以返回结构化指标，同时提供图表和筛选器；一个预算工具可以展示可编辑的分配面板；一个配置工具可以用表单承接参数修改，而不是要求用户继续用自然语言逐项描述。

界面与 Host 之间可以双向通信。Host 把工具结果和环境信息交给 View，用户在 View 中操作后，界面也可以通过 Host 请求其他工具或更新模型可见的上下文。

这里存在三个不同角色：Server 提供工具、数据和界面资源；Host 负责能力协商、隔离渲染和通信控制；View 负责具体展示与交互。三者共同形成体验，但任何一方都不能单独代表完整产品。

---

## Why It Matters｜为什么值得关注 💡

传统 MCP Server 的可复用重点主要在工具接口。同一个 Server 可以连接不同 AI Client，但每个 Client 如何展示结果，通常由客户端自行决定。

这会产生两种问题。

第一，工具作者知道结果最适合怎样被理解，却无法保证客户端拥有对应组件。复杂结果最终可能被压缩成表格文本、JSON 或一长段说明，用户仍需自己转换成下一步行动。

第二，客户端如果为热门工具分别开发专用界面，会形成大量一对一适配。工具更新后，多个客户端还需要分别维护组件和字段映射，协议层的连接复用没有完全转化成体验复用。

MCP Apps 尝试把一部分界面责任放回能力提供方。Server 可以把工具与经过设计的 View 一起发布，兼容的 Host 再负责安全承载。这样，工具作者不只定义输入输出，也能定义用户怎样查看结果、修改参数和继续任务。

但这并不意味着客户端体验可以被完全外包。Host 仍然拥有整体导航、权限提示、主题适配、确认策略和安全边界。MCP Apps 提供的是可嵌入体验，不是让第三方界面接管整个 AI 产品。

## Interaction Flow｜交互链路如何形成 ⚙️

从产品运行过程看，MCP Apps 可以拆成能力发现、工具执行、界面渲染和后续操作四个阶段。

### Capability Negotiation｜确认是否支持界面扩展

MCP Apps 是扩展能力，不属于所有客户端必须实现的核心功能。Client 与 Server 需要先声明是否支持对应扩展和内容类型，再决定是否注册或使用带界面的工具。

这一步直接影响产品降级策略。Server 不能假设所有用户都会看到界面，也不能因为缺少 UI 支持就让核心任务完全失效。

### Tool and Resource Linkage｜关联工具与界面资源

Tool 通过元信息指向一个 `ui://` Resource。用户发起任务后，模型仍然根据工具描述和参数决定是否调用；界面不是独立绕过工具契约运行，而是与工具结果形成关联。

这个边界能够减少“界面显示一种状态、工具实际返回另一种状态”的风险。产品仍需保证工具 Schema、返回数据与 View 预期保持兼容，并在版本变化时进行回归验证。

### Sandboxed Rendering｜在隔离环境中渲染

Host 获取 UI Resource 后，将其放在隔离 iframe 中运行，并通过受控通信通道与 View 交换数据。

官方扩展强调 iframe 隔离、可审计通信和声明式内容安全策略。原因很直接：界面代码来自外部 Server，如果它能任意读取 Host 页面、账号信息或本地环境，工具连接就会变成新的代码执行入口。

沙箱不能代替权限设计。它只能限制界面运行范围，无法自动判断一次业务操作是否合理、用户是否拥有对应权限，以及某个按钮是否需要二次确认。

### Bidirectional Interaction｜让用户继续推进任务

View 不只展示结果，也可以承接筛选、修改、选择和继续操作。用户在界面中调整条件后，View 可以通过 Host 请求工具，或把与任务有关的状态更新回模型上下文。

这种双向能力让对话和界面形成闭环，但也需要控制模型可见信息。用户在组件中的每次临时操作不一定都应该进入对话上下文；只有会影响后续判断的状态，才值得以清楚结构提供给模型。

## Use Case｜适用场景 📌

MCP Apps 更适合工具结果结构明确，并且用户需要理解、调整或继续操作的场景。

数据分析工具可以把指标、趋势和筛选条件组织成仪表盘；规划工具可以提供可调整的方案比较；审批或配置工具可以用表单收集结构化输入；媒体工具则可以提供播放器、时间轴或其他专用展示方式。

在这些场景中，界面不是装饰，而是帮助用户减少认知转换、核对关键数据并推进下一步。

简单问答、单个数值查询和一次性文本结果未必需要 MCP App。为了展示一句结果而加载完整界面，会增加实现、兼容和安全成本。产品应根据任务复杂度决定是否使用 UI，而不是把所有 Tool 都包装成小应用。

高风险动作也不能因为出现在精致界面中就默认可信。支付、发送、删除、权限变更和批量修改仍应由 Host 或业务服务执行权限检查，并在真实副作用发生前展示对象、范围和关键参数供用户确认。

## Boundaries｜与相邻概念的区别

MCP Apps、Generative UI 和 AG-UI 都涉及 AI 产品界面，但解决的问题不同。

Generative UI 是一种产品设计模式：模型或工作流根据任务结果选择受控组件，让输出从文本变成可操作状态。它可以完全在单个产品内部实现，不要求使用 MCP。

AG-UI 关注 Agent 后端与前端之间的运行事件、消息、工具调用和共享状态。它帮助前端理解一个持续执行的 Agent 正在发生什么，但不负责让 MCP Server 自带一个可嵌入界面。

MCP Apps 更具体：它规定外部 Server 怎样把 Tool 和 View 一起提供给兼容 Host，以及 Host 怎样隔离并连接这个 View。它处理的是跨客户端分发交互界面的问题。

MCP Resources 也参与其中，但普通 Resource 主要提供可读取的上下文；MCP Apps 使用特定 UI Resource 承载界面，并建立工具与界面的关联。能够读取 HTML 不等于客户端已经安全、完整地支持 MCP Apps。

## Product Insight｜产品观察 🔍

MCP Apps 最重要的产品启发，是 AI 工具生态的复用对象正在从 API 扩展到用户体验。

过去，一个工具是否“可接入”主要看参数和返回结构能否被客户端理解。以后还需要判断它是否能以用户可理解的方式展示状态、收集输入并承接下一步。

这种变化可能降低工具作者进入多个 AI Client 的适配成本，但“编写一次、所有客户端完全一致”并不现实。不同 Host 拥有不同窗口尺寸、主题、导航、权限模型和交互规范。可移植性更合理的目标，是保持核心任务和数据契约一致，同时允许 Host 对外框、确认和系统级体验进行控制。

界面来源也需要显式可见。用户应知道当前组件由哪个 Server 提供，它调用了什么工具，以及操作会影响哪个外部系统。第三方界面如果看起来与 Host 原生组件完全相同，却没有来源标识，可能让用户错误理解信任关系。

渐进增强是另一个关键原则。支持 UI 的 Host 获得更丰富体验，不支持的 Host 仍应通过文本或结构化结果完成核心任务。只有保留降级路径，MCP Server 才不会因为追求界面能力而失去原本的跨客户端可用性。

## Reusable Value｜可复用价值 🔁

设计 MCP App 时，可以先定义一个不依赖界面的核心工具契约，再决定哪些结果确实需要 View。

工具层应能够独立说明输入、输出、失败状态和副作用。界面层负责把结构化结果转化为图表、表单或操作状态，但不能成为隐藏业务规则和权限判断的唯一位置。

每个 View 还需要覆盖几类基础状态：加载中、无数据、部分数据、工具失败、权限不足和客户端不支持。只设计成功画面，会让跨 Host 运行时的问题全部退化成空白区域或无法解释的错误。

团队可以建立一份 Tool-View 契约，记录资源 URI、数据 Schema、支持的操作、需要的 Host 能力、降级结果和安全要求。工具或界面升级时，通过代表性任务验证数据兼容、交互闭环与文本回退。

评估时不只看界面是否成功显示，还要观察用户是否理解结果、是否能完成下一步、是否知道操作来源，以及不支持扩展时能否继续任务。

## Productization Direction｜产品化方向 🚀

AI Client 可以围绕 MCP Apps 建立统一的嵌入式应用容器，为第三方 View 提供主题、尺寸、加载、错误、来源和权限等标准能力。

工具市场也可以在安装前展示一个 MCP App 包含哪些 Tools、UI Resources、外部连接和内容安全策略，并区分纯展示组件与会触发真实操作的交互组件。

对团队环境而言，管理员可以维护允许使用的 Server 与 View 版本，记录界面来源、调用历史和权限变化。高风险 App 进入正式环境前，还需要进行代码审查、沙箱测试和业务流程验收。

更成熟的体验不会把 MCP App 当成聊天气泡里的网页，而会把它视为任务工作区的一部分：对话负责表达目标和解释判断，工具负责连接真实系统，View 负责让结果可见、可编辑和可继续操作。

MCP Apps 说明，AI 产品的开放生态不只需要统一工具调用，还需要思考交互如何跨系统交付。

当 Tool、数据契约、界面资源、安全隔离和降级路径一起被设计时，外部能力才可能从“能连接”进一步变成“用户能够理解并完成任务”。
