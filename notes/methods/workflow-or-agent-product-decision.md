# Workflow or Agent｜AI 产品何时需要固定流程，何时需要自主执行 🧭

- Source｜来源：LangGraph Official Documentation - Workflows and Agents
- Type｜类型：AI 产品方法观察 / Workflow / Agent / Product Decision Framework
- Link｜链接：https://docs.langchain.com/oss/python/langgraph/workflows-agents

当一个 AI 产品需要处理多步骤任务时，团队很容易直接想到 Agent：让模型理解目标、选择工具并自主推进，似乎比预先设计流程更智能。

但真实产品并不总是需要最大程度的自主性。许多任务的步骤、风险和完成标准本来就很明确，固定 Workflow 往往更容易测试、解释和控制。相反，如果问题路径无法提前穷举，强行把所有分支写成流程也会快速变得僵硬。

因此，真正重要的问题不是“Workflow 和 Agent 哪个更先进”，而是：当前任务中哪些部分应该由产品预先决定，哪些部分确实需要模型动态判断。

---

## What It Is｜它是什么 🧩

LangGraph 官方文档对两者给出了直接区分：Workflow 具有预先定义的代码路径，按照确定的顺序运行；Agent 则会动态决定自己的执行过程和工具使用方式。

从产品视角看，这一区别对应的是决策权放在哪里。

Workflow 把主要决策写进产品规则。系统知道下一步是什么、出现不同结果时走哪条分支，以及什么状态代表完成。模型可以参与分类、抽取、生成或判断，但整体路径仍由产品控制。

Agent 则把部分决策权交给模型。系统提供目标、工具和边界，模型根据当前状态选择下一步行动，并通过工具结果持续调整计划。

两者并不是互斥架构。大多数可落地的 AI 产品更接近混合形式：由 Workflow 保证关键路径和风险边界，在局部不确定环节使用 Agent 做动态判断。

---

## Why It Matters｜为什么值得关注 💡

Workflow 和 Agent 的选择会直接改变产品的成本、延迟、可解释性和失败方式。

如果一个任务本来只有三步，却被设计成开放式 Agent Loop，系统可能重复调用工具、走出不必要的路径，还会增加用户等待和排错难度。模型看起来拥有更多能力，但用户并没有因此更快获得可靠结果。

反过来，如果一个研究任务需要根据新证据不断调整方向，而产品预先规定固定搜索次数和固定总结顺序，系统又可能在信息不足时机械结束，无法处理真实问题中的变化。

这说明 Agent 不应被当作一个功能标签，而应被理解为一种更昂贵的决策机制。只有当动态判断带来的任务价值高于额外的不确定性时，它才值得进入产品。

---

## Decision Dimensions｜如何做选择 ⚙️

产品可以从五个维度判断任务更适合 Workflow、Agent，还是混合架构。

### Path Predictability｜路径可预测性

如果任务步骤可以提前列出，输入和分支数量有限，优先使用 Workflow。文档抽取、固定格式审核、批量分类和标准化报告都属于这一类。

如果任务需要根据中间结果决定后续方向，而且有效路径无法提前完整列举，Agent 更有价值。开放式研究、复杂故障定位和跨工具探索通常更接近这一类。

### Cost of Error｜错误代价

当错误会造成外部发布、资金变化、数据写入或权限影响时，产品应减少模型可以自由决定的范围。即使前面使用 Agent 探索，最终动作也应回到明确 Workflow 和人工确认节点。

低风险、可撤销、容易验证的任务，可以允许更高自治。例如生成多个备选方案、整理草稿或在隔离环境中尝试。

### Verifiability｜结果可验证性

如果每一步都有清晰规则或结构化结果，Workflow 更容易建立稳定检查。如果结果需要结合多种证据判断，Agent 可以承担探索，但仍需要定义完成证据，而不是以模型“认为已经完成”为结束。

### Environment Stability｜环境稳定性

接口固定、数据结构稳定的系统适合规则化流程。网页、第三方系统或不断变化的信息环境更难预先覆盖全部状态，Agent 的观察和适应能力更有意义，但同时需要更强的状态记录和失败恢复。

### User Control｜用户控制要求

用户希望快速获得确定结果时，复杂 Agent 过程可能成为负担。用户愿意委派目标、查看阶段进度并在关键点介入时，Agent 才能形成合理的协作关系。

## Use Case｜适用场景 📌

以用户反馈分析为例，导入数据、清洗字段、按既定标签分类和生成固定报表，都可以放在 Workflow 中。若系统还需要发现未知主题、提出新的问题假设并主动查找相关证据，则可以在主题探索阶段加入 Agent。

在企业知识问答中，权限检查、检索范围和引用要求应由 Workflow 控制。对于跨多个知识源的复杂研究，Agent 可以动态决定搜索顺序和补充查询，但不能自行绕过权限或省略来源验证。

在软件开发任务中，测试、格式检查和提交前确认适合固定流程；理解陌生代码、定位原因和提出修改路径则更适合 Agent。混合设计能让系统保留探索能力，同时把可验证的工程步骤固定下来。

## Product Insight｜产品观察 🔍

用户真正需要的不是一个更“自主”的系统，而是一个更少消耗注意力、能够稳定完成任务的系统。

如果产品把所有步骤都交给 Agent，用户可能需要持续监督；如果产品把所有路径都固定，用户又会在边界情况中不断与规则对抗。好的设计会把自治放在不确定性最高、最需要判断的环节，把确定性留给权限、数据和交付标准。

这也意味着界面不必展示后台使用了多少 Agent，而应展示任务当前处于什么状态、哪些步骤是确定流程、哪些判断由 AI 动态完成，以及用户何时可以介入。

Workflow 提供稳定骨架，Agent 提供局部适应能力。产品价值来自两者的分工，而不是技术名词本身。

---

## Reusable Value｜可复用价值 🔁

在设计 AI 功能前，可以先把任务拆成“已知步骤”和“未知决策”。已知步骤由规则、代码或固定模型调用完成；未知决策再判断是否需要 Agent。

随后为每个 Agent 环节补充边界：可调用哪些工具、拥有多少运行预算、什么结果算完成、何时必须停止或向用户求助。这样，Agent Loop、Human-in-the-loop 和评估机制都有具体落点。

最后用最简单可行方案验证。如果固定 Workflow 已经能稳定完成主要任务，就没有必要增加自主循环；只有真实样本证明固定路径无法覆盖关键变化时，再扩大 Agent 的决策范围。

---

## Productization Direction｜产品化方向 🚀

AI 应用搭建平台可以提供“自治程度”配置，而不是只让用户在 Workflow 和 Agent 两种模板之间二选一。

团队可以为每个节点声明它是固定执行、模型判断、Agent 探索还是人工决策，并为动态节点设置工具、预算、超时和完成证据。平台再根据运行记录显示哪些 Agent 判断真正提升了结果，哪些只是增加调用和延迟。

评估工具也可以比较同一任务的不同架构：固定流程是否已经足够，Agent 是否改善长尾任务，新增自主性带来的成本和错误是否可接受。这样，架构选择会从技术偏好变成可验证的产品决策。

---

## Product Observation｜进一步观察

Workflow 和 Agent 不是从传统到先进的升级关系，而是两种不同的任务组织方式。

成熟 AI 产品通常不会追求把所有控制权交给模型。它会让确定的部分保持确定，让不确定的部分获得适度判断空间，并在两者之间建立清楚的状态、权限和交接机制。

判断一个产品是否需要 Agent，最有效的问题不是“模型能不能自主完成”，而是“哪些决策无法提前定义，并且值得承担更高的不确定性”。
