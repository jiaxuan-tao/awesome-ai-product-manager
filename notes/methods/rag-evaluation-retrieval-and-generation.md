# RAG Evaluation｜知识库答错了，先查检索还是生成？ 🧪

- Source｜来源：Ragas Official Documentation
- Type｜类型：AI 产品方法观察 / RAG Evaluation / Retrieval Quality / Grounded Generation
- Link｜链接：https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/

RAG 产品出现错误答案时，最容易发生的误判是把问题统一归因于模型不够强。

但一条知识库回答从用户提问到最终生成，至少经过文档解析、切分、索引、检索、排序、上下文组装和答案生成。原始资料里可能没有答案，解析过程可能丢失表格，检索可能漏掉关键片段，也可能找回了正确内容却被无关信息淹没；即使上下文完整，模型仍可能忽略证据、补充未经支持的判断，或者回答了另一个相近问题。

因此，RAG Evaluation 的核心不是给整套系统打一个总分，而是把“答错了”还原成可以定位、解释和修复的具体问题。

> 评估的价值不只是判断结果好不好，而是帮助团队知道下一步应该改数据、改检索、改生成，还是改产品交互。

---

## What It Is｜它是什么 🧩

RAG Evaluation 是对检索增强生成系统进行分层评估的方法。它把一次回答拆成两段来看：系统有没有找到完成任务所需的证据，以及模型有没有基于这些证据给出合适的回答。

Ragas 官方文档列出了 Context Precision、Context Recall、Response Relevancy 和 Faithfulness 等指标。它们不是同一个质量概念的不同叫法，而是在观察不同失败位置。

Context Recall 关注关键证据是否被找全；Context Precision 关注返回结果中相关内容是否被排在前面，减少无关片段干扰；Faithfulness 关注回答里的判断能否由检索上下文支持；Response Relevancy 则关注回答是否真正回应用户的问题。只有把这些维度分开，团队才不会在检索失败时反复改 Prompt，也不会在生成偏离时盲目更换向量模型。

---

## Why It Matters｜为什么值得关注 💡

知识库产品的风险在于，错误答案往往也很流畅。用户看到完整句子、明确结论和引用标记时，容易把表达自信误认为内容可靠。如果团队只观察“用户有没有收到答案”，很多失败会被掩盖在一次看似正常的对话里。

单一总分同样会掩盖问题。例如，提高检索数量可能让 Context Recall 上升，因为更多相关证据被带入上下文；但它也可能引入大量噪声，降低 Context Precision，增加模型理解成本、响应延迟和调用费用。一个平均分没有办法告诉产品团队，这种变化究竟改善了什么，又牺牲了什么。

对产品经理来说，分层评估的意义是建立可行动的质量语言。客服知识库答错政策日期、内部问答漏掉例外条款、研究助手引用了不相关段落，它们表面上都是“答案不好”，对应的修复路径却完全不同。评估只有能连接到具体产品决策，才不是一张装饰性的分数报表。

## Evaluation Layers｜怎样定位失败环节 ⚙️

### 先建立可诊断的评估样本

一条有用的评估样本，不应只保存问题和最终答案。它至少要保留用户问题、检索到的上下文、系统生成的回答，以及在条件允许时补充参考答案或参考证据。文档版本、用户类型、查询时间和检索配置也值得记录，否则资料更新后，很难判断分数变化来自系统改进还是数据变化。

测试集应优先来自真实问题、用户纠错和历史失败案例。合成问题可以帮助扩大覆盖面，但不能替代真实表达，因为用户经常会使用缩写、模糊指代、错误术语和跨文档问题，这些才是检索系统真正需要处理的输入。

### Context Recall｜关键证据有没有找回来

Context Recall 关注的是不要遗漏完成回答所需的重要信息。低召回通常意味着资料源本身缺失、文档解析不完整、切分破坏了语义、查询改写不准确，或者检索范围和过滤条件过窄。

这类问题的修复重点应放在知识覆盖、解析质量、分块策略、查询理解与召回策略上，而不是要求模型“更认真回答”。模型无法可靠使用一个从未进入上下文的事实。

### Context Precision｜找回的内容是否足够干净

Context Precision 关注相关片段能否排在无关片段之前。低精度并不一定表示系统完全没有找到答案，也可能是正确证据埋在重复、过期或主题相近的内容里。

这种情况下，可以检查元数据过滤、去重、重排序、Top K 设置和文档版本管理。盲目扩大召回数量虽然可能减少遗漏，却也会把筛选责任转嫁给生成模型。产品需要在“找得全”和“给得准”之间做场景化取舍，而不是追求一个固定参数。

### Faithfulness｜回答是否忠于检索证据

Faithfulness 检查回答中的主张是否能够被检索上下文支持。它适合发现模型脱离资料自行补充、错误归纳或把推测说成事实的问题。低忠实度可以通过更清晰的生成约束、主张与引用绑定、无答案时拒答、生成后核验等方式改善。

但高 Faithfulness 不等于事实一定正确。如果知识库里的资料已经过期或本身错误，模型完全忠于资料，仍然会生成错误答案。它衡量的是“回答是否有上下文依据”，不是“这个依据是否代表现实真相”。

### Response Relevancy｜回答有没有真正解决问题

Response Relevancy 关注答案与用户意图的匹配程度，不负责判断事实准确性。一个回答可能句句有依据，却只回答了问题的一部分；也可能非常切题，却给出了未经证据支持的结论。

相关性偏低时，需要检查用户意图识别、追问机制、输出结构和任务边界。尤其在多条件问题中，产品应判断系统是否遗漏了用户要求的对象、时间、范围或输出格式，而不是只看答案是否提到了相同关键词。

## Use Case｜适用场景 📌

RAG Evaluation 适合用于企业知识库、客服问答、文档助手、研究检索、政策查询和垂直行业问答等产品。在上线前，它可以比较不同解析、切分、Embedding、检索和生成方案；上线后，它可以把用户反馈转化为回归样本，防止一次修复在后续版本中重新出现。

更实用的做法是按风险和问题类型分组观察，而不是只看全量平均分。高风险政策问题应更重视证据完整、资料时效和拒答边界；探索型问答可以容忍一定开放性，但需要让引用和推测清晰分离；客服场景还要关注答案是否能直接支持下一步行动。

## Product Insight｜产品观察 🔍

RAG 质量不是一个模型指标，而是一套跨数据、检索、生成和体验的产品责任。评估结果需要对应明确的责任边界：召回不足先检查资料与检索，噪声过多检查排序和过滤，回答无依据检查生成约束，回答不切题则回到意图和交互设计。

自动指标也不能被当作绝对裁判。Ragas 中部分指标会使用 LLM 进行判断，评分结果会受到评估模型、提示词、语言和样本表达影响。团队需要用人工标注样本校准评估器，定期抽查高分与低分案例，并记录指标版本。分数适合支持比较和回归，不适合单独证明产品已经可靠。

这篇内容与仓库里的 RAGFlow 项目分析关注点不同：RAGFlow 讨论文档理解与 RAG 平台如何被产品化，这里关注系统上线后如何定位质量问题。它也不同于 Agent Evaluation：后者观察多步骤任务的最终结果和执行轨迹，本篇只聚焦 RAG 链路中检索与生成的责任拆分。

## Reusable Value｜可复用价值 🔁

这套方法可以沉淀为一张持续更新的 RAG 质量地图。每个失败案例标记问题类型、证据状态、影响范围和修复动作，再把修复后的案例加入回归集。随着样本积累，团队会逐渐知道最常见的问题来自资料缺失、检索噪声还是生成偏离，也能判断下一阶段最值得投入的位置。

离线指标之外，还需要连接真实产品结果，例如用户纠错率、引用打开率、转人工比例、无答案率和任务完成率。离线评估帮助快速定位系统变化，线上信号则验证这些变化是否真的改善了用户任务。两者结合，才能避免为了提高指标而优化出一个用户并不需要的系统。

---

## Productization Direction｜产品化方向 🧭

如果把 RAG Evaluation 做成产品能力，它不应只有一个评分按钮，而应提供从失败发现到修复验证的闭环：保存查询与证据，按失败类型聚类，对比不同配置，回放具体案例，并把确认后的问题加入回归测试。

面向非技术用户，界面需要把抽象指标翻译成可行动解释，例如“关键资料没有被找到”“正确片段排序过低”“回答包含资料中没有的判断”。面向开发与运营团队，则需要保留模型、索引、数据版本和评估配置，让每次变化都可以追溯。

RAG 产品真正需要的不是一个看起来漂亮的质量分数，而是一套能够回答三个问题的机制：哪里出了错，为什么会错，修复后是否真的更好。只有做到这一点，知识库问答才可能从可演示的功能走向可持续维护的产品能力。
