# OpenTelemetry GenAI｜让模型与 Agent 运行轨迹拥有统一语言 🔭

- Source｜来源：OpenTelemetry GenAI Semantic Conventions / Official Specification
- Type｜类型：AI 产品方法观察 / GenAI Observability / Semantic Conventions / Agent Tracing
- Link｜链接：https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/README.md

当 AI 应用只有一次模型调用时，团队查看请求、响应时间和最终文本，通常就能大致理解系统发生了什么。

但当产品开始加入 RAG、记忆、工具调用和 Agent 工作流，一次用户任务可能经过多个模型、多个外部系统和多轮判断。最终结果不理想时，问题可能来自错误上下文、模型选择、工具参数、重试循环，也可能来自工作流中的某个决策。

这时，产品需要的不只是更多日志，而是一套能够描述 AI 运行过程的共同语言。

OpenTelemetry GenAI Semantic Conventions 正在尝试定义这套语言。它为模型推理、检索、记忆、Agent、工作流、工具执行和 MCP 等操作提供统一的 Trace、Metric 与 Event 语义，使不同框架和观测平台能够用更一致的方式理解 AI 应用的运行数据。

从产品视角看，它最重要的意义不是增加一批技术字段，而是让质量、延迟、成本和任务过程有机会被放进同一条证据链。

---

## What It Is｜它是什么 🧩

OpenTelemetry 是一套用于生成、收集和传输可观测数据的开放标准。Semantic Conventions 则进一步规定：不同系统在记录同类操作时，应使用什么名称、属性和结构表达其含义。

GenAI Semantic Conventions 把这种标准化方法扩展到生成式 AI 场景。

例如，一次模型调用可以记录请求的模型、实际响应模型、输入与输出 Token、结束原因、执行时长和错误类型；一次 Agent 运行可以继续关联计划、工作流和工具执行；RAG 应用还可以把检索操作与所使用的数据源连接到同一条 Trace 中。

标准化的价值在于，不同框架不必各自发明一套互不兼容的字段。观测平台也不需要为每一种模型 SDK 和 Agent 框架重新解释运行数据。

不过，这套 GenAI 规范目前仍处于 Development 状态。它代表一个正在形成的共同方向，而不是已经冻结、不会变化的最终标准。产品和工程团队可以参考它建立数据兼容意识，但需要保留版本迁移和字段调整能力。

## Why It Matters｜为什么值得关注 💡

传统软件监控主要回答服务是否可用、接口是否报错、资源是否异常。AI 应用还需要回答另一类问题：系统虽然成功返回了结果，为什么用户任务仍然失败？

一个研究 Agent 可能没有报错，但反复搜索同类网页；一个客服 Agent 可能正确调用退款工具，却传入错误金额；一个 RAG 应用可能正常生成回答，但检索到的材料与问题无关。

这些失败无法只靠 HTTP 状态码解释。团队需要还原任务经历的模型调用、检索、工具执行和状态变化，并知道每一步使用了什么配置、消耗多少时间、产生多少成本。

如果每个框架都用自己的数据结构，团队更换模型、Agent 框架或观测平台时，历史指标和分析逻辑很难延续。统一语义能够降低这种迁移成本，让团队关注产品问题，而不是不断翻译不同工具的内部格式。

更重要的是，统一记录方式为跨版本比较创造了前提。只有同一类操作在不同模型与框架下具有可比较含义，团队才可能判断一次调整究竟改善了质量、缩短了延迟，还是只是把成本转移到另一个环节。

## Observation Model｜运行过程如何被描述 ⚙️

从产品分析角度，可以把 GenAI 可观测数据理解为三层。

第一层是一次用户任务的完整 Trace。它代表用户从提出目标到获得结果的整个过程，为任务复盘提供统一入口。

第二层是 Trace 内部的 Span。模型推理、检索、记忆操作、Agent 调用、工作流和工具执行，都可以作为具有开始、结束和结果的操作被记录。父子关系能够说明一次任务如何被拆解，以及时间和失败集中在哪个环节。

第三层是描述每个操作的属性和指标，例如模型名称、Token 用量、结束原因、错误类型和执行时长。它们让团队能够对相同操作进行筛选、聚合和比较。

这三层共同解决的不是“记录得越多越好”，而是让数据具有稳定含义。团队看到 `execute_tool` 时，应知道它代表一次工具执行；看到输入和输出 Token 时，应能在不同模型调用之间进行一致分析。

其中，完整 Prompt、系统指令、工具定义、参数和结果属于另一种敏感级别。官方实践默认只记录模型、Token 和时长等元数据，完整内容需要显式启用。因为这些内容可能包含用户隐私、企业数据或访问凭据，可观测性不能以牺牲数据边界为代价。

## Use Case｜适用场景 📌

对于多模型产品，统一语义可以帮助团队比较不同供应商或模型版本的延迟、Token 使用和错误分布，而不必为每个平台维护完全独立的报表。

对于 RAG 产品，一条 Trace 可以连接用户问题、检索操作、数据源和模型生成过程。回答失败时，团队能够判断问题发生在检索、上下文组织还是最终生成，而不是笼统归因于模型。

对于 Agent 产品，计划、工作流、模型调用和工具执行之间的父子关系可以还原任务路径。团队可以识别重复调用、异常重试、长期停滞或某类工具的集中失败。

对于正在从原型走向持续运营的产品，标准化数据也有利于建立稳定的版本对比。更换 Prompt、模型或编排方式后，团队可以沿用相同观察维度，而不是每次重新定义指标。

如果应用只是低频、单次、低风险的文本生成，完整的分布式 Trace 可能过重。可观测设计应从关键任务和最小必要数据开始，复杂度需要与任务链路和失败成本匹配。

## Boundaries｜与已有内容的区别

OpenTelemetry GenAI 与 Langfuse 处于不同层次。

Langfuse 是一个具体的 AI 可观测性与评估平台，它提供 Trace 查看、评估、数据集和 Prompt 管理等产品能力。OpenTelemetry GenAI 更接近数据契约：它关注运行信息应如何被描述和传输，使兼容的后端能够接收并解释这些数据。

它也不等同于 Agent Evaluation。Agent Evaluation 需要产品团队定义什么任务算成功、哪些行为属于风险，以及使用什么 Grader 判断结果。可观测规范可以提供执行证据，却不能替团队决定产品标准。

它与普通应用日志同样不能互相替代。业务日志可以记录订单号、用户操作和领域状态；标准化 Trace 更适合描述跨组件的执行关系。成熟产品通常需要把两者关联起来，而不是把全部信息塞进一种记录方式。

因此，这篇内容补充的是“观测数据如何保持可迁移和可比较”，而不是重复介绍某个可观测平台或评估方法。

## Product Insight｜产品观察 🔍

OpenTelemetry GenAI 带来的核心启发是：AI 产品的运行轨迹正在成为一种需要设计的数据资产。

产品团队过去常在上线后才讨论需要记录什么，结果往往只留下接口状态和最终文本。等到用户报告问题时，系统已经缺少还原任务过程所需的证据。

更合理的方式是在设计功能时同步定义观测契约：一次用户任务从哪里开始，哪些步骤属于同一条 Trace，哪些操作必须保留时间与结果，什么字段可以用于版本比较，哪些内容因为隐私只能在明确授权后采集。

这也意味着可观测性不只是工程排障工具。产品角色需要决定哪些状态能够解释用户体验，哪些指标代表任务价值，以及成本和延迟应该如何与成功率共同判断。

另一个重要变化是平台选择权。统一语义不能消除所有供应商差异，但可以减少数据被单一框架格式锁定的程度。当模型、Agent 框架和观测后端持续变化时，可迁移的数据契约本身就是产品基础设施的一部分。

## Reusable Value｜可复用价值 🔁

在实际项目中，可以先为关键用户任务定义一个稳定的 Trace 边界，再逐步补充模型、检索和工具 Span。不要一开始记录所有中间文本，而应优先保留操作类型、模型、时长、Token、错误和任务关联标识。

数据采集还需要分级。低敏感度元数据可以默认记录；可能包含用户内容、商业资料和工具参数的数据，应进行脱敏、采样、访问控制或显式启用。保留周期也不应由日志系统默认决定，而要与产品用途和隐私要求一致。

团队还可以建立一张观测字段到产品问题的映射：每个字段用于回答什么问题，谁会使用，缺失后会影响什么决策。无法对应真实问题的数据，通常不值得长期收集。

由于规范仍在演进，落地时应记录使用的语义版本，并在内部封装字段映射。这样既能采用开放标准，也能避免外部字段变化直接扩散到所有分析和业务代码。

## Productization Direction｜产品化方向 🚀

统一语义可以支持跨模型和跨 Agent 框架的运行质量工作台。团队在同一界面中比较模型、版本、工作流和工具表现，而不是被单一供应商的数据格式限制。

它也可以发展为面向产品角色的任务复盘工具。系统把底层 Trace 转化为更容易理解的用户路径，标记等待、重试、工具失败和人工接管节点，让产品判断不必停留在原始日志层。

进一步看，标准化运行数据还能连接评估与发布流程。真实失败可以被筛选为回归样本，新版本上线前运行测试，上线后再用相同语义观察实际任务，从而形成从运行证据到产品改进的闭环。

OpenTelemetry GenAI 仍然是一套快速演进中的规范，但它揭示了一个明确方向：当 AI 产品越来越依赖多模型、工具和 Agent 编排，可观测性不能只依赖某个平台的专有视图。

模型提供能力，Agent 组织过程，而统一运行语义让这些过程能够被理解、比较和持续改进。
