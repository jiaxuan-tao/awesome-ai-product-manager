# OpenClaw Automations｜让个人 Agent 按约定启动任务 ⏰

- Source｜来源：OpenClaw Official Documentation - Automations / Heartbeat
- Type｜类型：AI 产品工作流观察 / Personal Agent / Scheduled Tasks / Notification UX
- Link｜链接：https://docs.openclaw.ai/automation/cron-jobs

用户说“每周帮我整理一次项目进展”，期待的并不是 AI 此刻回答一句“记住了”，而是未来真的有人按约定开始工作，并把有用结果交回来。

这与即时聊天有不同的产品要求。任务可能在用户不在线时启动，数据和权限可能已经变化，结果也可能生成了却没有送达。一个看起来简单的定时请求，实际上包含计划、执行和交付之间的长期约定。

OpenClaw Automations 提供了观察这一问题的具体入口。本文依据公开官方文档讨论它的任务机制和产品含义，不代表已经部署 OpenClaw、创建自动任务，或验证了实际运行效果。

---

## What It Is｜它是什么 🧩

OpenClaw 的[Automations 文档](https://docs.openclaw.ai/automation/cron-jobs)把它描述为内置调度器：保存任务，在满足时间条件时唤起执行，并按配置处理输出。任务可以面向一次性提醒，也可以周期性运行。

调度不是模型在对话里自行计时。[运行机制文档](https://docs.openclaw.ai/automation/cron-jobs/how-it-works)明确指出，它运行在 Gateway 进程中，Gateway 必须保持运行，计划才会触发；任务定义和运行记录的持久保存，并不能代替执行进程本身。

因此，“计划已创建”和“届时一定完成”不是同一个承诺。设备、服务、模型与工具仍然构成实际条件。即使重启后能找回计划，也需要按具体恢复规则处理错过的运行，不能默认所有历史时点都会原样补做。

---

## Why It Matters｜为什么值得关注 💡

即时聊天主要依靠用户主动进入。周期任务则把一部分责任交给系统：用户不必每次重新提出目标，但系统需要记清楚正在承担哪一份约定。

这让个人 Agent 从临时助手走向持续协作，也让错误更容易积累。一次摘要不准确，用户可能及时纠正；一个不再需要的任务若长期运行，就会持续产生费用、重复消息和过期判断。

真正值得设计的不是“让 AI 更主动”，而是让主动性有具体范围。检查什么、多久检查、没有变化时是否安静、何时需要用户处理，以及任务什么时候结束，都影响这项能力能否被长期接受。

已有 n8n 文章关注 AI 怎样进入业务节点；Computer Use 关注操作界面；Mem0 和 Ambient Context 分别关注记忆与上下文来源。本篇只简要引用这些背景，独立讨论个人任务跨时间启动后，用户与系统之间怎样保持约定清楚。

## How It Works｜把一句约定变成可执行安排 ⚙️

### Schedule｜先确认时间表达的实际含义

[时间安排文档](https://docs.openclaw.ai/automation/cron-jobs/schedules)区分一次性时间、固定间隔和日历式周期，并说明时区及部分周期的错峰行为。这意味着“每天九点”不能只保存成一段自然语言，还要对应明确的执行规则。

对产品来说，固定间隔与每天固定时刻有不同含义。用户出差、更换设备时区或遇到夏令时变化时，预期可能进一步分离。设置完成后，展示下一次实际运行时间，比只展示一串技术表达式更容易核对。

任务还需要区分“九点开始整理”和“九点前收到结果”。前者是启动时间，后者涉及耗时与交付目标。若产品只配置了前者，就不能把它说成已经满足后者。

### Execution Context｜约定未来做事，也要准备未来的输入

[任务载荷文档](https://docs.openclaw.ai/automation/cron-jobs/payloads)区分系统事件、Agent 消息、命令和脚本等执行方式。它们并不都会自动产生一次模型推理，因此有计划不等于已经具备完成目标的全部动作。

[投递文档](https://docs.openclaw.ai/automation/cron-jobs/delivery)也区分执行上下文与结果目的地。结果发到某个聊天，不代表执行时自动读取了那个聊天的全部历史；独立执行与延续已有会话，对输入的要求不同。

以周报为例，任务应知道要读哪个项目、统计哪段时间、输出保存在哪里，以及材料不足时怎么办。把“按我们刚才说的做”长期保存下来，容易随着会话和资料变化失去含义。必要约束应进入任务定义，动态事实则在运行时重新获取。

### Heartbeat｜周期检查不等于每次都发消息

[Heartbeat 文档](https://docs.openclaw.ai/gateway/heartbeat)将其定义为系统管理的周期性 Agent 运行，并要求独立周期工作使用明确的自动化任务。默认行为不应从旧对话中猜测、重复未明确安排的工作；没有需要关注的内容时，可以保持安静。

从产品角度看，检查频率和通知频率需要分开。系统可以多次查看同一状态，但只有出现变化、需要决策或达到约定节点时才通知。否则，助手只是把用户自己检查的负担，换成了不断阅读“暂无变化”的负担。

## Use Case｜适用场景 📌

周期性资料整理是较清楚的入口。比如按周读取指定项目记录，提取新增进展与未决问题，生成可复查摘要。它的价值来自减少重复准备，而不是把历史材料重新改写一遍。

变化监测也适合这一思路，例如定期检查某个项目的公开更新，只报告与用户关注点有关的新变化。这是本文提出的应用示例，具体数据连接、访问限制和判断标准仍需要另行实现与验证。

对于低频、简单的时间提醒，传统日历往往已经足够，不必为了使用 Agent 增加模型调用。只有任务包含读取、比较、归纳或判断，且重复执行确实有价值时，这类自动化才更有意义。

不适合直接无人值守的动作，也不会因为设置了日程就变得适合。对外发送、发布或修改重要数据，应沿用明确的授权与确认规则。时间条件决定何时启动，不会自动扩大原有权限。

## Product Insight｜计划、运行与送达是三种状态 🔍

用户没有收到消息时，至少存在几种解释：任务没有启动，启动后失败，结果还在处理，结果已经完成但投递失败，或者按约定没有值得通知的变化。

这些情况对应不同动作，不能统一显示为“未完成”。[官方故障排查文档](https://docs.openclaw.ai/automation/cron-jobs/troubleshooting)也分别讨论未触发和已触发但没有投递，并指出某次运行显示正常，仍可能存在工具执行诊断需要检查。

因此，运行状态不应替代业务验收。“Agent 已返回”只能证明一次执行结束，不能证明周报覆盖了所有材料；消息渠道确认投递，也不能证明用户已经阅读或接受结果。产品需要把可证明的事实与目标完成判断分开。

这还能避免错误恢复扩大问题。若摘要已生成，只是消息投递不确定，重新运行整项任务可能重复消耗或重复写入。应先查原记录与接收端，再决定补送还是重做。这里沿用已有 Tool Retry 的恢复原则，不重复展开幂等实现。

在界面上，任务定义与每次运行也应分开管理。暂停未来计划，不必然停止正在执行的一次任务；停止当前运行，也不一定取消下一次安排。把这两种操作合成一个含糊的“停止”，容易让用户产生相反预期。

## Reusable Value｜先跑通一次，再建立长期约定 🔁

设计个人自动任务时，可以先完成一次真实任务，让用户看到结果是否有价值，再讨论是否周期化。官方运行机制文档也将重复工作的自动化视为一种从已完成任务出发的转化，而不是从一句模糊目标直接建立长期安排。

在这一步，最有用的确认是一段普通话：什么时候、读取什么、完成什么、结果去哪、哪些情况才通知，以及到什么时候复查或结束。这比让用户批准一个看不懂的表达式，更能暴露双方理解是否一致。

验证不能只测“手动点运行成功”。还应检查无人在线时是否有足够输入、权限失效时如何反馈、没有新增数据时是否安静，以及出现中断后能否找到原记录。手动成功只能说明当时条件成立，不代表未来环境没有变化。

长期使用还需要复查收益。任务是否持续提供新信息，用户是否经常忽略通知，运行成本是否超过节省的时间，都比任务数量更重要。若只是定期输出相同内容，正确的优化可能是降低频率或关闭，而不是增加更复杂的 Prompt。

## Productization Direction｜产品化方向 🚀

基于这类机制，可以设计一个面向个人工作的任务中心。它既展示长期约定，也展示最近一次运行、下一次计划和结果位置，让用户能够快速判断“还在替我做什么”。这属于产品设计延伸，不是对现有界面的功能承诺。

[官方管理文档](https://docs.openclaw.ai/automation/cron-jobs/managing-jobs)提供了任务管理与运行历史入口。借鉴时，产品可以进一步围绕具体运行给出稳定链接，避免用户点开一条通知后，只看到最新结果而找不到当时那次记录。

通知策略也可以成为任务本身的一部分。固定摘要按期送达，监测任务只在变化时提醒，失败则按影响决定是否立即通知。用户还应能理解安静是正常结果、没有执行，还是系统无法确认；不能用少发消息掩盖故障。

---

## Product Observation｜进一步观察

个人 Agent 的持续价值，不来自它看起来始终在线，而来自它能够维护一份清楚、可修改、可结束的工作约定。

Skill 解决某类任务可以怎样执行，调度机制解决何时启动，运行记录帮助核实发生了什么，交付机制则让结果真正回到用户手中。任何一层都不能单独证明任务成功。

OpenClaw Automations 提供的具体启发，是把“之后再做”从一句聊天承诺变成可检查的产品对象，同时保留对执行条件、通知边界和结束方式的诚实表达。
