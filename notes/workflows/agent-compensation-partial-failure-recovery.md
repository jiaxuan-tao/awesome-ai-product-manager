# Agent Compensation｜任务失败后，如何处理已经完成的操作 🔄

- Source｜来源：Microsoft Azure Architecture Center / AWS Prescriptive Guidance
- Type｜类型：AI 产品工作流观察 / Agent Compensation / 部分失败 / 补偿操作 / 执行恢复
- Link｜链接：https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction

用户让 Agent 整理反馈、创建任务，再通知相关人员。

Agent 已经创建了任务，但通知发送失败。此时，界面如果只显示“任务失败”，用户可能以为什么都没有发生；如果直接重新运行，又可能创建第二批任务。

更复杂的情况是，用户要求取消，但前面的操作已经生效。停止后续执行，并不会让已经修改的文件、创建的记录或发送的消息自动消失。

这意味着，Agent 产品不仅需要设计如何完成任务，还需要设计任务没有完整完成时，怎样处理已经发生的变化。

本文借用分布式系统中的补偿思路，分析 Agent 工作流的失败恢复。这里的 Agent Compensation 是观察角度，不是一个独立工具或统一协议。

---

## What It Is｜它是什么 🧩

补偿操作，是在原操作已经生效后，通过另一个明确动作处理它留下的影响。

例如，创建了一条不再需要的任务，可以按业务规则将它关闭；修改了文件，可以在满足条件时恢复内容；预订已经成立，则可能需要调用取消流程，而不是简单删除本地记录。

微软的补偿事务模式强调，这类处理依赖具体业务规则，不一定把系统完全恢复到最初状态。其他人可能已经继续操作，有些成本也已经发生，机械地还原旧数据反而可能产生新问题。

因此，补偿不应被理解为一个万能的撤销按钮。它更接近一条事先设计的恢复路径：明确哪些变化可以处理、需要什么条件，以及处理完成后允许留下什么结果。

重试和补偿也不是一回事。重试尝试完成原来的动作；补偿则处理已完成动作的影响。选择哪条路径，需要先知道外部系统实际发生了什么。

---

## Why It Matters｜为什么值得关注 💡

普通内容生成失败，往往可以丢弃结果重新生成。但 Agent 一旦获得写入能力，失败就可能发生在外部状态已经改变之后。

任务可能已经创建，文件可能已经更新，通知也可能只发给了部分人。这些结果不会因为聊天窗口显示失败而消失，也不会因为模型重新规划就自动保持一致。

用户真正关心的，不只是最后一步有没有成功，还包括现在留下了什么、哪些结果仍然有效，以及是否需要自己处理。

如果产品只提供成功和失败两个状态，就会把“部分完成”隐藏起来。用户为了弄清现状，只能逐个打开外部系统核对，自动化节省的时间又被恢复成本抵消。

补偿设计的产品价值，在于把这些后果提前纳入流程，而不是等到出错后，再让模型临时猜测应该删什么、改什么或重新做什么。

---

## Recovery Design｜先确认事实，再选择恢复路径 ⚙️

恢复的第一步，是区分未执行、已完成和结果待核实。尤其在超时场景中，没有收到成功响应，并不能证明操作没有生效。

应用应保存操作对象、请求身份和外部返回的记录标识。执行前记录意图，执行后记录证据；遇到结果不确定时，保留核实路径，而不是把缺失响应直接改写成失败。

确认现状后，再判断目标是否仍能继续完成。如果任务已经创建，只是通知失败，通常更值得考虑保留任务并补发通知，而不是立即删除全部结果。若用户已经改变目标，则需要重新判断保留或补偿的范围。

补偿动作本身也要有明确条件。例如，恢复文件之前，应检查当前内容是否仍是 Agent 修改后的版本。如果别人已经继续编辑，直接覆盖成旧版本可能抹掉后续工作，此时应转为差异检查或人工处理。

这些规则需要由应用和工具契约支持。仅在 Prompt 中要求“出错后恢复原样”，无法建立可靠保证，因为模型未必掌握完整状态，也未必拥有能够撤销操作的接口。

---

## Use Case｜适用场景 📌

以反馈整理助手为例，可以把资料分析、任务创建和通知发送分别记录。通知失败后，产品告诉用户任务已经创建，附上实际入口，并提供继续通知或保留现状的选择。

如果用户决定取消，不应默认把所有任务删除。部分任务可能已经被负责人接手，关闭、标记取消或保留并说明原因，可能比删除更符合业务需要。

文件整理助手也会遇到类似问题。假设一批文件中，前几个已经移动，后面的处理失败。恢复时需要知道原位置、新位置和当前状态，而不是凭文件名重新扫描后猜测哪些属于本次任务。

在内容发布场景中，还需要区分草稿、已发布内容和已经被外部读取的内容。撤下文章可以改变当前可见状态，但不能保证之前收到通知的人没有看过，也不能消除已经发生的传播。

这些场景共同说明，恢复目标应该由具体任务决定。有时是继续完成，有时是减少影响，有时则是明确保留部分结果，并把剩余处理责任交还给用户。

## Product Insight｜部分完成需要自己的交互状态 🔍

一个成熟的 Agent 产品，不应该把所有异常都压缩成一句“执行失败，请重试”。

更有用的反馈应说明哪些步骤已经生效、哪些没有完成、哪些结果还在核实，以及接下来准备采取什么动作。用户不必阅读全部日志，但应能够直接检查受影响对象。

例如，“已创建三条任务，通知尚未发送”比“任务失败”更准确。如果系统已经开始补偿，还应区分“正在处理”和“已确认完成”，不能在发出撤销请求后就宣称恢复成功。

取消按钮也需要表达真实含义。“停止后续步骤”“取消尚未执行的请求”和“处理已完成操作”是不同承诺。若工具只能做到第一种，界面就不应暗示所有影响都已撤销。

它与仓库已有 Tool Retry & Idempotency 的区别是，后者关注恢复时避免重复副作用，本篇关注已有副作用如何收尾。LangGraph 关注流程状态与恢复，恢复一个检查点却不等于外部世界也回到过去。

Human-in-the-loop 则提供介入位置，但是否需要人确认、确认哪些后果，仍然要结合具体补偿动作设计。不能因为用户曾同意原任务，就推断他也同意删除所有中间结果。

## Product Boundary｜补偿也可能失败 🛡️

补偿不是失败之后天然可靠的第二条通道。它同样可能遇到权限变化、网络故障、对象被修改或接口不可用。

因此，原操作与补偿操作都需要保留身份和进度。对于可能重复提交的补偿请求，也应按接口约定处理重复执行，避免一次恢复又造成新的重复变化。

补偿顺序也不一定机械地倒着执行。应根据步骤依赖和业务风险确定：有些结果需要先保留，有些资源应先释放，还有些操作必须等待其他步骤的状态得到确认。

对不可逆或难以完整补偿的动作，更重要的是执行前的控制。可以采用预览、延迟生效、明确确认，或在依赖条件验证完成后再执行，而不是寄希望于事后补救。

还有一种边界是，系统无法确认原操作是否成功。此时贸然补偿，可能处理错误对象；贸然重试，又可能产生重复。产品应保留待核实状态，提供具体对象与证据，而不是为了给出一个确定结论继续猜测。

这些限制意味着，补偿应只覆盖应用已经定义并验证过的路径。不能把“Agent 很灵活”当成它能够安全处理任意后果的依据。

---

## Reusable Value｜把失败后的责任写进工作流 🔁

设计一个有外部写入的 Agent 功能时，可以在成功路径之外，再检查每个步骤生效后会留下什么，以及后续失败时应该怎样处理。

这里值得记录的，不只是对应的撤销接口，还包括恢复所需证据、允许处理的条件、是否需要重新确认，以及无法自动处理时由谁接手。

验证也应覆盖中间失败，而不只测试全部成功。例如，前两步完成后第三步失败，补偿执行到一半断线，用户取消时仍有请求在运行，以及对象已经被别人修改。这些场景能暴露正常演示中看不到的问题。

验收标准应该落到外部实际状态。界面显示“已恢复”，就需要有证据证明目标对象符合预定恢复条件；如果仍有残留影响，应明确列出，而不是用流程结束代替问题解决。

可以观察待核实操作的持续时间、补偿后仍需人工处理的数量、错误撤销情况和用户核对成本。单独统计补偿接口调用成功率，仍可能掩盖处理错对象或恢复不完整的问题。

对个人 Vibe Coding 项目，可以先选一个写入动作，把执行记录、部分失败反馈和恢复路径走通。没有必要立即引入复杂编排系统，但需要让用户知道每次操作发生了什么，以及出错后还有哪些可行选择。

---

## Product Observation｜进一步观察

Agent 产品获得更多行动能力之后，产品责任也会延伸到行动之后。

停止执行只是停止继续推进，重试只是再次尝试，补偿则需要处理已经发生的影响。它们可以共同服务恢复，但不能在界面和任务逻辑中被混为一谈。

真正可靠的恢复机制，不是保证所有事情都能回到过去，而是在无法完整完成任务时，让现状清楚、后果可核对、处理范围受控，并为无法自动解决的部分保留明确交接。

一个值得托付的 Agent，不仅要知道下一步怎么做，也要知道做了一半以后，应该怎样负责任地收尾。
