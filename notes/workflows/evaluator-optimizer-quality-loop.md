# Evaluator-Optimizer Workflow｜用反馈循环提升 AI 输出质量 🔁

- Source｜来源：LangGraph Official Documentation - Workflows and Agents
- Type｜类型：AI 产品工作流观察 / Evaluator-Optimizer / Feedback Loop / Output Quality
- Link｜链接：https://docs.langchain.com/oss/python/langgraph/workflows-agents#evaluator-optimizer

很多 AI 产品把一次模型生成直接当作最终结果。输出不理想时，用户只能重新生成、修改 Prompt，或者自己编辑内容。

但有些任务拥有相对明确的成功标准，又很难通过一次生成稳定达到。例如翻译需要保持原意和语气，报告需要覆盖指定信息，代码修改需要满足测试，内容审核需要符合一组规则。

Evaluator-Optimizer Workflow 把“生成—检查—修改”组织成受控循环。一个生成节点负责产出或修订结果，另一个评估节点依据标准判断是否接受，并在不通过时提供具体反馈。

这不是让模型无限自我反思，而是把质量改进变成有标准、有反馈、有预算的产品流程。

---

## What It Is｜它是什么 🧩

LangGraph 官方文档将 Evaluator-Optimizer 描述为一种 Workflow：一个 LLM 调用生成结果，另一个调用对结果进行评估；如果评估器或 Human-in-the-loop 认为需要改进，就把反馈送回生成器重新产出，直到结果达到可接受标准。

这个模式适合成功标准可以表达，但结果需要迭代才能满足的任务。

它与开放式 Agent Loop 不同。Agent 会动态决定工具和执行路径；Evaluator-Optimizer 的角色和循环关系通常是预先定义的。生成器不负责判断自己是否完成，评估器也不负责重新生成，两者通过明确反馈连接。

从产品视角看，这是一种把“再生成一次”升级为“根据失败原因定向修订”的工作流设计。

---

## Why It Matters｜为什么值得关注 💡

普通重新生成只改变随机结果，不一定解决原来的问题。如果用户认为报告缺少证据，系统却只是用同一 Prompt 再生成一遍，新的结果可能换了表达，但仍然缺少证据。

Evaluator-Optimizer 的价值在于把质量差距显性化。评估器需要指出哪个标准没有满足，生成器再围绕反馈修改。这样，每一轮都应减少一个明确问题，而不是盲目尝试。

这个过程也让产品可以区分结构错误、事实不足、风格不符和任务遗漏。不同失败原因可以进入不同修订策略，甚至在需要外部资料时转回检索，而不是继续要求模型改写现有文本。

不过，多一轮模型调用不天然等于更高质量。如果评估标准模糊，评估器与生成器共享同样偏差，循环只会增加延迟和成本。因此，这个模式的核心不是循环次数，而是反馈是否可执行。

## How It Works｜工作流如何运行 ⚙️

### Success Criteria｜定义成功标准

工作流开始前，需要先说明什么结果可以被接受。标准应与用户任务相关，并尽量能够逐项判断，例如必须覆盖哪些要点、引用是否存在、输出结构是否完整、是否符合长度或风险边界。

“质量更高”“更专业”这类描述太模糊，难以产生可操作反馈。评估器需要把抽象目标转成具体差距，同时避免为了容易评分而忽略真正的用户价值。

### Generate｜生成结果

第一轮生成根据任务输入和成功标准产出候选结果。后续轮次还会接收评估反馈，因此生成器需要区分原始要求和新反馈，避免修复一个问题时破坏已经满足的部分。

产品可以保留版本差异，让用户知道每轮具体修改了什么，而不是只显示最后一版。

### Evaluate and Feedback｜评估与反馈

评估节点判断候选结果是否达到标准。若不通过，反馈应说明具体问题、依据和建议修改方向。

结构化反馈比一段泛泛评价更容易进入后续流程。例如返回未满足的标准、严重程度、证据片段和建议动作。高风险或主观任务还可以让人工参与判断，避免模型独自决定是否合格。

### Stop or Iterate｜结束或继续

通过评估后，工作流返回最终结果；未通过时进入下一轮。产品还需要设置最大轮次、时间或成本预算，并处理连续反馈没有变化的停滞情况。

达到预算上限不等于结果合格。系统应明确标记部分完成或仍有问题，并让用户决定接受、继续还是人工修改。

## Use Case｜适用场景 📌

在翻译任务中，生成器负责翻译，评估器检查语义保持、术语和语气。反馈可以指出具体段落的含义偏差，再由生成器定向修订。

在结构化报告中，评估器可以检查必要章节、来源、结论依据和格式要求。若问题来自资料不足，工作流应返回补充检索，而不是让生成器凭空扩写。

在代码生成中，测试和静态检查可以成为确定性评估器，模型评估器则负责可读性或需求覆盖。只有自动检查和必要人工审核都满足时，结果才进入下一步。

在品牌内容中，评估器可以检查禁用表达、事实依据和品牌规则。但主观风格不适合只用一个模型给出绝对分数，产品应允许人工反馈进入循环。

对于简单改写、低价值草稿或一次生成已经足够的任务，额外循环可能得不偿失。Evaluator-Optimizer 更适合质量标准明确且错误成本值得承担额外调用的场景。

## Product Insight｜产品观察 🔍

Evaluator-Optimizer 最重要的产品启发，是把 AI 输出质量从一次结果变成可推进的状态。

用户看到的可以不只是“生成中”和“已完成”，还包括候选版本、未满足标准、正在修订和等待确认。产品由此能够解释为什么需要更多时间，以及新一轮到底改进了什么。

这篇内容与 Agent Evaluation 的区别在于，后者关注如何评价最终结果和执行轨迹，评估结果可以服务测试、发布或运营；Evaluator-Optimizer 则把评估直接放进单次任务运行，用它决定是否重新生成。

它与 Agent Loop 的区别也很清楚。Agent Loop 处理开放任务中的行动、工具和停止；这里的路径相对固定，重点是通过反馈反复逼近清楚标准。

DSPy 一类优化框架会基于数据集和指标调整 Prompt 或程序配置，关注跨样本的系统优化；Evaluator-Optimizer 更关注当前这一次用户任务的产物修订。

## Reusable Value｜可复用价值 🛠️

设计这类工作流时，可以先把评价标准拆成确定性检查和判断性检查。格式、字段、长度和测试结果优先由代码验证；语义一致性、表达质量和任务覆盖再交给模型或人工。

每条反馈都应能够改变下一轮行为。如果反馈只是“还不够好”，循环没有继续价值。产品可以要求评估器指出未满足项、证据和建议动作，并记录本轮是否真的改善。

还要设计退化保护。新版本修复缺失章节时，可能破坏原有事实或格式。评估不应只检查上一轮问题，也要重新验证关键基础标准。

最后设置清楚预算和退出状态：通过、部分通过、等待资料、需要人工、达到上限或无法改进。它们比一个笼统的成功或失败更适合真实 AI 输出。

---

## Productization Direction｜产品化方向 🚀

AI 应用平台可以提供可配置的 Quality Loop Builder，让团队定义生成器、评估器、标准、反馈结构、最大轮次和人工确认点。

平台还可以展示版本比较和改进轨迹。团队能够观察哪些反馈最常出现、哪一轮开始收益下降、哪些标准适合自动判断，进而优化 Prompt、数据和工作流。

在面向普通用户的产品中，系统可以把复杂评估转成简单选择：接受当前结果、根据某项反馈继续修改、手动编辑或补充资料。用户不需要理解后台有几个模型调用，但应保持对成本、时间和最终决定的控制。

长期来看，评估器本身也需要评估。团队应使用代表性样本检查它是否过度严格、偏向某种表达，或错误接受看似完整但缺少事实依据的结果。

---

## Product Observation｜进一步观察

AI 输出的不确定性不能只靠“再生成一次”解决。有效迭代需要明确标准、具体反馈和停止边界。

Evaluator-Optimizer Workflow 展示了一种介于单次生成和开放 Agent 之间的产品形态：流程是确定的，内容可以迭代，质量判断能够进入运行过程。

它真正优化的不是某一段文字，而是用户从初稿走向可用结果的路径。
