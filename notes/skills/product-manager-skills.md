## What It Is｜它是什么

这是一个面向产品经理的 AI Skills 与工作流项目，主要把产品管理中的常见方法、框架和任务流程整理成可被 AI Agent 调用的结构化 Skills。

它和普通 Prompt 模板不同。Prompt 更像一次性的任务输入，而 Skill 更像一个可复用的能力模块。  
从产品视角看，这个项目的重点不只是“让 AI 帮 PM 写东西”，而是把产品经理的专业方法拆成可以被调用、组合和复用的工作单元。

这里的 Skill 不是一篇介绍某种方法的普通文章，也不只是换了文件格式的 Prompt。它需要让支持 Skills 的 Agent 能够识别何时使用这项能力、需要哪些输入、按什么过程执行，以及最终应该交付什么结果。只有这些约束能够被实际读取和执行，Skill 才从知识说明变成可调用能力。

---

## Why It Matters｜为什么值得关注 🔍

很多 AI 工具的问题是：用户知道自己想要结果，但不知道怎么把任务拆清楚。

比如“帮我分析一个产品机会”这句话很模糊。真正可执行的过程可能包括：

- 明确用户是谁
- 判断问题是否真实存在
- 分析现有替代方案
- 评估机会大小
- 拆解产品假设
- 输出下一步验证方案

Skills 的价值就在于，它把这些隐性的专业过程变成了更明确的执行结构。

这对 AI 产品设计很重要。因为 AI 产品未来不只是提供一个聊天框，而是要把复杂任务拆成可选择、可组合、可迭代的能力模块。

这种变化也降低了重复沟通成本。用户不必每次重新解释完整方法，Agent 可以先依据 Skill 建立任务框架，再针对当前项目补充上下文。但它并不会消除信息质量问题：输入材料不足时，结构化流程只能让缺口更清楚，不能替用户制造真实证据。

## How It Works｜它如何工作 ⚙️

一个可用的 Skill 通常需要同时处理“被发现”和“被执行”两个问题。

首先，名称、描述和触发条件需要足够明确，让 Agent 知道什么任务适合调用它，什么任务不适合。其次，Skill 内部要说明必要输入、执行步骤、输出结构和检查规则；如果任务需要模板、示例或脚本，也应把这些资源与主说明放在稳定关系中。

以需求洞察为例，一个 Skill 不应只要求“分析需求”，而应先检查是否存在用户反馈、业务目标和使用场景，再区分事实、推断与待验证假设，最后给出下一步验证方案。这样的过程才具有重复使用价值。

从产品角度看，Skill 的结构可以理解为四层：

- **触发入口**：用户在什么场景下会想到并调用它
- **输入契约**：完成任务前必须提供哪些信息
- **执行方法**：Agent 应遵循哪些步骤和判断原则
- **交付标准**：结果需要达到什么形式与质量要求

这四层共同决定 Skill 是否真的可用，而不是文件是否已经放进某个目录。

## Product Insight｜产品观察 💡

这个项目最有启发的地方，是它体现了 AI 工具从“Prompt 驱动”走向“能力模块驱动”的趋势。

Prompt 解决的是“怎么问 AI”。  
Skill 解决的是“如何让 AI 按某种专业方法持续完成任务”。

这两者的差别很重要。

如果一个 AI 工具只有 Prompt，用户每次都要重新组织上下文、任务目标和输出要求。  
但如果一个 AI 工具有 Skills，用户就可以直接调用某种能力，比如需求拆解、用户故事生成、机会评估、定价分析、PRD 梳理等。

这更接近产品化的 AI 工作流：  
用户不需要从空白输入框开始，而是从一个具体能力入口开始。

但“能够安装”不等于“达到生产级”。Skill 仍需要在不同输入质量、不同项目上下文和异常场景下反复验证。尤其是涉及产品判断时，输出是否可追溯、假设是否被明确标记、用户能否在关键节点纠正方向，比一次生成得是否完整更重要。

Skill 也不应该把所有工作塞进一个巨大流程。边界过宽会让触发条件模糊、上下文膨胀，执行结果也更难评估。更合理的方式是按稳定任务拆分，并通过明确的输入输出关系组合起来。

## Reusable Value｜可复用价值 🛠️

这个项目可以作为整理 AI 产品经理中文工具箱的重要参考。

可以复用的方向包括：

- 把产品方法论整理成 Skill
- 把常见 PM 任务拆成可调用模块
- 把 Prompt 从单条文本升级成工作流
- 把 Vibe Coding 前期需求分析流程模板化
- 把 Agent 的任务执行过程拆成更稳定的步骤

后续如果继续整理，可以形成一套中文 AI PM Skills，例如：

- 用户需求澄清 Skill
- PRD 生成 Skill
- 竞品分析 Skill
- 用户故事 Skill
- 产品机会判断 Skill
- Vibe Coding 项目拆解 Skill

复用这些 Skill 时，重点应放在方法是否适合当前任务，而不是简单追求数量。一个需求澄清 Skill 可以为 PRD Skill 提供结构化输入，验收清单 Skill 又可以读取 PRD 的范围和状态；这种衔接比孤立地生成几份漂亮文档更能体现工作流价值。

## Possible Productization｜可能的产品化方向 🚀

如果把这类 Skills 进一步产品化，可以做成一个“AI 产品经理技能库”。

用户进入后，不是直接面对 AI 聊天框，而是选择自己当前要完成的产品任务：

- 我要判断一个产品机会
- 我要拆解一个需求
- 我要写一版 PRD
- 我要分析一个竞品
- 我要把想法变成 Vibe Coding 提示词

每个任务对应一个 Skill，Skill 内部再规定输入信息、执行步骤、输出结构和检查标准。

这样，AI 工具就不只是回答问题，而是在帮助用户按照专业流程完成产品工作。

如果继续产品化，还需要增加版本管理、运行记录和效果反馈。用户应该知道某次输出使用了哪个 Skill 版本、哪些步骤由 Agent 完成、哪些结论经过人工确认。只有这些过程能够被检查和复盘，技能库才可能从个人模板集合发展为可靠的协作基础设施。
