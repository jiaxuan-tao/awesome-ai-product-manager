# Superpowers｜让多个编程 Skill 凭证据接力 🧩

- Source｜来源：obra/superpowers 官方仓库 / v7.0.2 发布说明与 Skill 定义
- Type｜类型：AI 产品能力模块观察 / Coding Agent / Skill 编排 / 开发验证
- Link｜链接：https://github.com/obra/superpowers/releases/tag/v7.0.2

给编程 Agent 装上几个 Skill，不等于它们会自动组成一套可靠的工作方式。需求讨论可能已经结束，但关键决定没有传到实现环节；开发 Agent 可能报告任务完成，但审查只看了最后一次提交；测试也可能确实通过，却没有覆盖用户最在意的行为。每一步单独看都像做过，连起来却仍然有缺口。

Superpowers 值得观察的地方，是它试图规定这些环节怎样交接。本篇不列举全部 Skill，而是围绕一个问题：上一阶段要留下什么，下一阶段才有理由开始？本文基于 v7.0.2 的公开资料分析，案例为假设，不是对安装效果或开发效率的实测。

## What It Is｜它是什么 ⚙️

Superpowers 是面向编程 Agent 的一套可组合 Skill。它用启动指引提醒 Agent 在行动前检查适用的能力，再让设计讨论、计划、实现、审查和验收各自承担不同责任。用户不需要在每一轮都记住该点名哪个 Skill；但能否触发，以及触发后是否遵循，仍取决于实际运行环境和 Agent 行为。[启动 Skill](https://github.com/obra/superpowers/blob/v7.0.2/skills/using-superpowers/SKILL.md)

理解它，可以把「能力库」和「工作流」分开。能力库回答某个 Skill 会做什么；工作流还要回答，它什么时候介入、接收哪一版输入、结果交给谁，以及不满足条件时怎么办。两者差别不在于装了多少能力，而在于各能力之间有没有明确的交接依据。

## Why It Matters｜最容易丢的是阶段之间的决定 💡

用户同意的是「导入时保留现有记录」，下一阶段拿到的任务却可能只剩下「实现导入」。丢掉的几个字足以改变行为：实现者可能用覆盖来简化逻辑，测试者也可能只验证新记录成功写入。后续每一步都可以执行得很认真，但已经不是用户最初同意的方案。

把完整聊天记录交给每个阶段，并不能保证它们抓住相同重点。对话中会同时存在被否决的建议、临时假设和最终决定。更可靠的交接是保留对下一步有约束力的信息：已确认的行为、必须保留的限制，以及遇到哪些变化需要回来确认。要传递的是决定，而不是它出现过的全部对话。

这也改变了对「流程跑完」的理解。生成了设计文档，只证明有东西可供审核；实现者报告完成，只说明可以开始核对改动。两种状态都不应被直接升级成「用户已确认」或「结果已验收」。好的工作流会让这些区别影响下一步动作，而不是只体现在最终报告的用词里。

## How It Works｜把交接条件写进工作方式 🔗

在设计环节，Superpowers 的发布说明强调减少无效追问：只有答案会改变做出来的东西、现有上下文又无法回答时，才值得问。对产品来说，这不只是缩短聊天，而是把人的注意力用在真正的选择上。关于导入冲突，是保留、覆盖还是交给用户决定，值得确认；项目现有的文件命名惯例，通常应该先自行查看。[v7.0.2 发布说明](https://github.com/obra/superpowers/releases/tag/v7.0.2)

进入实现后，官方描述了两种路径：对能拆成相对独立任务的计划，可以由子 Agent 逐项实现并复核，再做整体审查；也可以在当前会话连续实现，把独立复核集中到最后，有条件才使用新的审查上下文。前者更早暴露局部问题，但反复分发上下文和审查要付出成本；后者减少交接次数，却可能让同一个错误假设影响更多任务。[子 Agent 执行](https://github.com/obra/superpowers/blob/v7.0.2/skills/subagent-driven-development/SKILL.md) · [会话内执行](https://github.com/obra/superpowers/blob/v7.0.2/skills/executing-plans/SKILL.md)

一个具体细节是，逐任务复核需要查看从该任务起点到当前结果的完整差异，而不是默认最后一次提交包含全部工作。假如第一笔提交改了导入策略，第二笔提交才补充界面提示，只审第二笔就会错过真正影响数据的改动。复核范围是否选对，比给流程加上「已审查」标签更重要。

## Practical Use｜用一次导入改动看交接 📌

假设一个个人记录工具要支持 CSV 导入。用户确认：匹配到已有编号时保留原记录，跳过冲突行，并告诉用户哪些行没有导入。这个决定需要进入实现任务，而不是只留在需求讨论里。否则，下一阶段即便把 CSV 读得很稳定，也可能在重复数据出现时做出错误选择。

实现前可以先用一组包含已有编号的样例建立验证：原记录不能被修改，冲突行应出现在结果里。第一次失败还要看失败原因。如果测试只是因为文件路径写错而失败，它并没有证明系统缺少冲突处理。修正实现后，除了确认新增用例通过，还应核对普通导入路径没有被破坏。

审查时则有两个独立问题：交付行为是否符合已经确认的规则，以及实现是否引入了新的质量问题。例如，原记录确实未被覆盖，但提示把冲突行算进成功数量，用户仍无法判断哪些数据真正导入。测试命令成功、规格要求满足、结果可放心交付，不能用同一个勾代替。

## Product Insight｜「完成」必须说明完成了哪一层 🔍

Superpowers 的验证 Skill 要求在宣告完成之前，找出能支撑该声明的检查，实际运行并阅读结果。它的产品启发不是把每次交付都做重，而是让声明的范围和证据的范围相符。只验证了冲突处理，就说冲突用例通过；没有打开真实界面，就不能说导入体验已经验收。[完成前验证](https://github.com/obra/superpowers/blob/v7.0.2/skills/verification-before-completion/SKILL.md)

而在多个 Skill 的流程里，证据还应带着对象。一次测试属于哪个工作区、对应哪段改动、覆盖了什么行为，决定后面的 Agent 能不能直接使用它。改动继续发生时，旧结果可以说明上一步的状态，却不一定支持当前结论。因此，有用的进度记录应能让下一环节知道：哪里可以继续，哪里需要重新验证。

这篇与 Spec Kit 的区别，是把注意力从「应该写哪些规格材料」移到「这些材料如何改变下一步行为」。与 Agent Planning 的区别，是不展开计划怎样生成或重新规划，而是看设计决定、实现差异和验证结果怎样通过各自的交接条件。Skill Evaluation 则仍负责另一层问题：单项能力是否真的在适当时机触发和产生效果。

## Evidence & Limits｜有流程不等于流程生效 🛡️

Skill 里的要求是对 Agent 行为的约束，不能直接当成运行时保证。启动指引可能没有加载，审查可能缺少完整差异，测试也可能选错场景。Superpowers 提供了回看会话记录的诊断 Skill，用来核对触发、计划偏离和重复工作等问题。诊断说明要求结论能回到记录里的具体位置；找不到证据时，不应靠记忆判断它走过哪些步骤。[会话诊断](https://github.com/obra/superpowers/blob/v7.0.2/skills/diagnosing-superpowers/SKILL.md)

执行方式也有取舍。没有子 Agent 工具时，官方会话内执行指引允许单独做一次自审，并要求如实标明它不是独立复核。对小而明确的调整，这可能已经足够；对会改变既有数据的改动，用户则可能需要更强的复核依据。缺少独立审查时，最重要的是不要把它写成已经完成。

流程本身也不会扩大授权。即使设计已通过、检查也通过，推送到共享分支或发布仍要遵守用户和仓库的规则。相反，只改一处明确文案时，也不应为了显得严谨而多造几份文件。判断流程是否合适，要看它降低了哪种真实风险，以及减少的返工是否值得额外成本。

## Reusable Value｜先建立一个有用的交接点 🔁

个人项目可以先从最常出问题的一步做起。若经常做偏，先让实现任务引用一条已确认的行为和一条不可破坏的约束；若经常提前宣布完成，先让交付报告对应到实际检查及未覆盖事项。等这一步有用，再考虑是否需要完整的计划、逐项复核或独立的执行记录。

评价时，选两个类似的小改动，比较采用交接条件前后的需求遗漏、重复解释和验收返工。不要用调用次数或生成文档数量衡量改进。复核开销上升并不一定是坏事，但如果没有发现过去容易漏掉的问题，也没有让结果更好判断，就值得缩短流程。

Superpowers 提供了一个观察样本：多个 Skill 真正形成工作流，不是因为它们按顺序出现，而是因为前一步留下了下一步能核对、能使用的依据。把这种交接设计好，比让 Agent 每次都把流程念得完整更重要。
