# Skill Evaluation｜如何验证 Agent Skill 是否真正有效 🧪

- Source｜来源：Anthropic Agent Skills Best Practices
- Type｜类型：AI 产品方法观察 / Agent Skills / Skill Evaluation / Capability Quality
- Link｜链接：https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices

Agent Skill 把任务说明、参考资料、模板和脚本封装成可复用能力，让 Agent 在遇到匹配任务时按需加载专业工作方式。

但一个 Skill 被成功创建、能够被 Agent 读取，并不等于它已经成为可靠的产品能力。它可能在用户真正需要时没有触发，也可能在无关任务中被错误调用；即使成功触发，Agent 仍可能遗漏关键步骤，或者完成了流程却没有改善最终结果。

因此，Skill 上线前需要回答的不只是“文件格式是否正确”，而是三个更接近产品价值的问题：

> 它是否在正确场景被发现，是否按照预期方法工作，以及是否让用户任务完成得更好。

Skill Evaluation 的意义，就是把这些问题转化为可以持续验证的能力质量标准。

---

## What It Is｜它是什么 🧩

Skill Evaluation 是围绕一个 Skill 的触发、执行和任务结果进行系统验证的方法。

它和普通 Prompt 测试有相似之处，但评估对象更完整。Prompt 测试通常观察给定输入能否产生理想输出；Skill 还多了一层能力路由：Agent 首先要根据用户意图判断是否应该加载这个 Skill，随后才会读取说明、使用资源或运行脚本。

这意味着一个 Skill 至少存在三类失败：

- **Discovery Failure**：该触发时没有触发，或不该触发时被调用。
- **Instruction Failure**：已经加载 Skill，但没有遵循关键步骤和边界。
- **Outcome Failure**：流程看似正确，最终结果却没有达到任务目标。

这三类失败不能只靠检查 `SKILL.md` 的文字发现。团队需要用接近真实用户表达的任务进行测试，并把 Agent 的选择过程、执行行为和结果质量放在一起观察。

---

## Why It Matters｜为什么值得关注 💡

Skills 的产品价值来自复用。团队希望一次整理好的能力，可以在不同用户、不同任务和不同时间里保持相对稳定的表现。

但复用也会放大问题。一个表达模糊的 Skill 描述可能持续错过真实需求；一个范围过宽的 Skill 可能抢占其他能力；一条看似合理的指令可能在模型更新后被不同方式理解。用户看到的不是某次偶然失误，而是一个产品能力长期不可靠。

如果团队只测试“能否成功运行一个演示案例”，很容易得到虚假的稳定感。演示输入通常会直接使用 Skill 名称和标准术语，而真实用户可能使用口语、省略背景，或者同时提出多个目标。Skill 在理想输入下可以工作，不代表它能在真实能力目录中被正确路由。

评估还决定了能力能否安全迭代。Skill 的描述、说明、参考资料、脚本、模型或工具环境发生变化后，团队需要知道新版本究竟改善了什么，是否破坏了既有任务，以及能否回退到上一个稳定版本。

从产品角度看，Skill Evaluation 不是发布前的一次检查，而是能力生命周期的一部分。

---

## Evaluation Layers｜评估层次 ⚙️

### Triggering｜触发准确性

触发评估关注 Agent 是否在正确场景发现 Skill。

测试不能只包含明显应该触发的请求，还要加入表达方式不同但意图相同的正向案例。例如，一个“用户反馈归类” Skill，不应只测试包含“请调用反馈归类 Skill”的输入，还要测试“把这些评论按问题类型整理一下”这类自然表达。

同时需要准备负向案例。用户可能只是询问如何设计反馈分类方法，并不希望系统真的读取文件或执行归类；另一个 Skill 也可能处理相邻任务。负向测试可以发现 Skill 描述是否过度宽泛，以及多个 Skills 之间是否存在能力冲突。

触发评估的关键不是追求所有请求都自动调用，而是在漏触发和误触发之间建立与任务风险相匹配的边界。低风险的格式整理可以更主动，高权限或有副作用的能力则应更保守。

### Instruction Following｜指令遵循

Skill 被加载后，需要观察 Agent 是否真正采用了其中定义的工作方法。

这里不应机械检查每一句说明是否被复述，而要识别决定任务质量的关键行为。例如，需求审查 Skill 可能要求先确认目标用户，再检查验收标准；数据处理 Skill 可能要求保留原文件并在写入前验证字段。

评估可以把这些关键行为定义为检查点：必要输入是否被收集，重要步骤是否执行，禁止事项是否被遵守，模板和脚本是否在适当阶段使用，异常情况是否进入正确分支。

如果一个 Skill 包含很多难以验证、彼此冲突或没有优先级的说明，问题可能不在模型，而在能力本身设计得过于复杂。评估结果也应反过来推动 Skill 拆分和说明重构。

### Task Success｜任务结果

遵循步骤并不等于任务成功。

一个 Agent 可能完整执行 Skill 中的流程，却输出了一份不能直接使用的结果。因此，最终评估还要回到用户目标：结果是否准确、完整、可操作，是否减少了用户修改成本，以及相比没有启用 Skill 时是否产生实际改善。

这一步适合使用基线对比。对同一组任务分别运行未启用 Skill、当前版本和候选新版本，比较任务成功率、关键错误、人工修改量和完成成本。这样可以避免把“输出更长”或“步骤更多”误判为能力更强。

## Test Set Design｜测试集设计 📋

高质量测试集应该来自真实任务分布，而不是围绕现有说明反向编写一组必然通过的题目。

团队可以从用户请求、失败记录、人工接管和客服反馈中收集代表性案例，再去除敏感信息并补充必要上下文。测试集需要覆盖典型任务、边界任务、容易混淆的相邻任务，以及输入不完整或存在噪声的情况。

每个案例至少应记录预期是否触发、必须满足的关键行为和任务成功标准。对于存在多种合理路径的任务，不应把某一条固定执行轨迹当作唯一答案，而应检查真正影响结果的约束。

测试集也需要持续维护。当产品新增 Skill、用户表达方式变化，或某类错误频繁出现时，旧测试可能不再代表真实环境。一次线上失败如果具有复现价值，应该转化为新的回归案例。

## Product Insight｜产品观察 🔍

Skill Evaluation 最重要的产品启发，是 AI 产品的能力目录需要像软件功能一样拥有明确质量标准。

传统功能通常有可见入口和相对确定的执行逻辑。Skill 的入口可能隐藏在自然语言路由中，执行过程又受到模型、上下文和其他能力影响。因此，用户感受到的“这个功能时有时无”，可能来自触发、说明、工具或结果中的不同环节。

产品不能只显示某个 Skill 已安装或已启用，还应理解它在真实任务中的健康状态。哪些表达经常无法触发，哪些 Skill 容易互相冲突，哪个版本开始出现结果退化，这些信息决定能力库是否可维护。

这篇内容与 Agent Evaluation 的边界也需要保持清楚。Agent Evaluation 关注完整任务中的决策、工具调用、执行轨迹和最终结果；Skill Evaluation 更聚焦能力单元本身，回答它是否应该被选中、是否提供了有效工作方法，以及加入它之后任务表现是否改善。

两者可以连接，但不能互相替代。一个 Agent 整体表现不好，可能是规划、模型或工具问题；一个 Skill 单独通过测试，也不代表它放入复杂能力目录后不会与其他 Skills 冲突。

## Reusable Value｜可复用价值 🔁

在实际产品中，可以为每个 Skill 建立一份轻量评估契约，包括适用意图、不适用意图、关键行为、结果标准和已知限制。它既帮助作者澄清能力边界，也为后续自动评估和人工复核提供共同依据。

发布流程可以从少量高价值案例开始：先检查明显正向和负向触发，再验证关键步骤，最后比较启用前后的任务结果。对于会读取敏感数据、执行脚本或产生外部写入的 Skill，还需要增加权限和安全测试，但不能用安全通过代替效果评估。

团队还可以把线上反馈映射到三个层次。用户说“它没帮我处理”可能是漏触发；“做法不对”可能是指令遵循问题；“流程都走了但结果没用”则属于任务成功问题。这样的分类比笼统记录一次差评更容易形成具体改进。

## Productization Direction｜产品化方向 🚀

### Skill Evaluation Workspace｜能力评估工作台

能力平台可以集中管理测试案例、候选版本、模型配置和评估结果。作者修改 Skill 后，系统自动运行正向、负向和回归任务，并展示触发变化与结果差异。

### Capability Conflict Detection｜能力冲突检测

随着 Skills 增加，平台可以寻找描述和适用场景高度重叠的能力，并使用相邻任务测试路由结果。目标不是禁止重叠，而是帮助作者明确优先级和边界。

### Release Gate｜能力发布门槛

团队可以为不同风险等级设置发布条件。低风险 Skill 通过核心案例即可进入个人使用，高权限或组织级 Skill 则需要更完整的评估、审核和灰度观察。

Skill 只有被封装起来，还不能算成熟能力。

真正可复用的 Skill，需要在正确时机被发现，按照清楚边界完成任务，并且在持续变化的模型和工具环境中证明自己仍然有效。
