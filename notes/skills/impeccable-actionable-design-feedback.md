# Impeccable｜把“界面不好看”变成可执行的设计反馈 🎨

- Source｜来源：Impeccable 官方 GitHub 仓库 / 官方设计工作流文档
- Type｜类型：AI 产品方法观察 / Agent Skill / UI Review / Vibe Coding
- Link｜链接：https://github.com/pbakaus/impeccable

用 AI 做产品时，生成第一版界面已经不难。更难的是看着一个能运行的页面，知道哪里不对，却说不清应该怎样改。“高级一点”“简洁一点”“不要那么像 AI”，都表达了感受，却没有明确问题。Agent 只能自行猜测，可能换掉配色、增加动画，甚至重做布局，真正影响使用的问题却仍然存在。

Impeccable 提供了一个值得观察的方向：把模糊的设计感受拆成有对象、有依据、可以执行和复查的反馈。本文根据公开资料分析其方法，未实际安装或在个人项目中验证效果。

## What It Is｜它是什么 🧩

Impeccable 是面向编程 Agent 的设计能力工具集，包含 Skill、设计指导和配套检查能力。它不是一个独立设计师，也不是自动保证质量的认证系统，而是帮助 Agent 更有针对性地理解和改进界面。[官方仓库](https://github.com/pbakaus/impeccable)

它既支持新页面设计，也强调对已有界面的定向改进。对 Vibe Coding 而言，后者尤其值得关注：当第一版已经可以使用，下一步往往不是再生成一个全新的产品，而是逐步修正信息层次、操作反馈和阅读负担，同时保留已经成立的功能。

它的产品意义不只是让生成结果拥有某种视觉风格，而是给用户与 Agent 增加一层共同语言。用户可以说明希望改善的具体对象，Agent 也应解释问题发生在哪里、为什么值得修改，而不是只宣布页面已经“更专业”。

## Why It Matters｜为什么值得关注 💡

模糊反馈会把大量决定留给模型。用户说“首页太乱”，可能是主要操作被埋没、内容重复，也可能是间距过小。这些问题需要不同处理。若一律通过删除内容解决，页面可能更空，却让必要信息变得更难找到。

反复整体重做还会增加验证成本。一次调整同时改变布局、文案、组件和交互，用户很难判断究竟什么改善了体验，也不容易发现哪些原有行为被破坏。第一次生成的速度优势，可能消耗在之后的来回修订中。

因此，AI 设计工具需要解决的不只是生成能力，还包括问题定位与修改范围。能够把“我觉得不对”转化为“这个位置妨碍了这项任务”，才更容易形成有效协作。设计反馈应帮助缩小不确定性，而不是开启下一轮无边界生成。

## How It Works｜从评价到定向修改 ⚙️

官方将 `critique` 与 `audit` 分成两类评审。前者侧重设计清晰度、层次与使用体验；后者关注可访问性、性能、主题和响应式等实现问题。两者都先返回发现，而不是自动应用全部修改。[设计评审](https://impeccable.style/docs/critique/) · [实现审查](https://impeccable.style/docs/audit/)

这种区分有实际意义。按钮颜色不够鲜明，与键盘操作时看不出焦点，是不同性质的问题。前者可能涉及视觉判断，后者可能直接妨碍操作。把它们混成一句“按钮需要优化”，用户就无法判断应先处理什么，以及怎样验证。

官方工作流还要求说明哪些内容必须保留，再围绕明确对象改进；普通润色与替换视觉方向的重设计也应分开。[已有界面的改进流程](https://impeccable.style/docs/improve-design/) 从产品角度看，这是把“允许改善”与“允许推翻”分开。用户希望列表更易扫描，并不意味着同意删除筛选条件或改变保存方式。

设计判断也需要项目背景。官方通过 `PRODUCT.md` 保存用户、目标与约束，通过 `DESIGN.md` 记录已有视觉系统。[上下文文档](https://impeccable.style/docs/context/) 文件本身不是目的，重要的是让后续修改有共同依据；过时或未经确认的记录，同样可能让 Agent 持续做出错误决定。

## Practical Use｜适合怎样的任务 📌

假设正在做一个 AI 文档问答工具，第一版已经支持上传和提问，但测试者找不到答案引用。此时，要求“重新设计得更高级”并没有抓住问题。更有用的目标是：让用户在阅读答案时识别出处，并能回到对应材料，同时保持现有问答与上传流程不变。

接下来需要判断，引用究竟是视觉不明显、位置不合理，还是信息本身缺失。前两类可能通过局部界面调整解决；如果系统没有保存文档位置，只增加一个醒目的来源按钮，就不能补齐真实能力。设计改进不能用一个看起来可点击的入口掩盖后端缺口。

另一个假设场景是优化提示词管理列表。用户需要快速找到最近使用的模板，Agent 却加入大面积介绍和装饰卡片。评审应回到查找任务：关键信息是否容易比较，筛选是否可见，主要操作是否稳定。这里需要的是更清楚的信息组织，不一定是更强烈的视觉表达。

这些例子不是本次实测，而是用于说明使用边界。对于已经有明确设计规范的项目，重点应是发现偏差并保持一致；对于方向尚未确定的探索，才适合比较更大范围的方案。不能把所有“不满意”都解释为需要重设计。

## Product Insight｜反馈需要连接用户任务 🔍

一条可执行的反馈，应该连接界面位置、用户行为与实际后果。例如，“历史记录文字太小”仍然比较笼统；“用户需要连续比较多条记录，目前时间和标题难以扫描，因此容易打开错误条目”，才说明了修改理由。字体调整只是可能方案，未必是唯一答案。

优先级也应该围绕任务损失，而不是视觉显眼程度。一个很突出的装饰元素可能只是令人分心，一个不明显的错误状态却可能让用户误以为内容已保存。若先处理容易展示改进效果的部分，真正影响可信度的问题就可能一直被延后。

同时，反馈应说明值得保留的部分。AI 评审容易不断寻找缺点，让用户以为整个页面都需要推翻。但一个已经熟悉的导航、一条稳定的操作路径，本身就是产品资产。好的改进应减少问题，而不是为了表现修改力度，让用户重新学习全部界面。

这也是本篇与已有内容的区别：Huashu Design 关注产物能否继续编辑与交接，Ponytail 关注实现中的最小完整改动；这里关注的是修改之前的判断，怎样把体验问题表达清楚，让有限改动真正服务用户目标。

## Evidence & Limits｜设计建议不等于验证结果 🛡️

Impeccable 的评审会结合源码与自动检查，在浏览器工具可用时观察渲染页面。官方也明确将模拟视角作为进一步调查的线索，而不是真实用户研究。[评审依据与边界](https://impeccable.style/docs/critique/) 因此，需要分清哪些结论来自实际操作，哪些来自代码阅读，哪些只是模型提出的假设。

“减少 AI 味”也不是独立的质量证明。渐变、卡片和圆角并非天然错误，去掉它们也不自动提升效率。若规则能够提醒我们检查惯用套路，它就有价值；若只是把一种流行模板换成另一种模板，产品判断仍然没有发生。

评审分数同样不能替代具体发现。官方提醒，总分较高仍可能包含阻断任务的问题。[审查评分说明](https://impeccable.style/docs/audit/) 对实际交付而言，一个无法完成保存的入口，不能被其他视觉项目的高分抵消；是否可用，需要回到关键路径逐项确认。

还需要防止同一个 Agent 生成、修改并评价自己的结果，却不断重复最初的假设。真实输入、不同屏幕、键盘操作和必要的人工试用，提供了不同来源的证据。自动评审可以减少遗漏，但不能因此省略这些检查。

## Reusable Value｜建立轻量的界面改进闭环 🔁

个人实践可以从一个页面、一项任务开始。先说明用户是谁、要完成什么，以及哪些功能不能改变；再让 Agent 给出最重要的问题与依据。无需一开始检查整个产品，也不必把每个建议都变成开发任务。

确认修改后，应保留可比较的前后状态，用同一组内容、相同屏幕和相同任务复查。否则，换了更短的标题或更理想的数据，可能让页面看起来改善，却没有解决真实条件下的溢出与阅读问题。比较条件一致，比展示一张更漂亮的截图更重要。

结果记录也可以很简洁：原问题是什么，改了哪里，用什么方式检查，还剩什么不确定。若本轮只验证桌面，就不要宣布移动端也已完成；若只看截图，就不要声称表单操作已经通过。记录应帮助下一次修改，而不是制造一份更长的完成报告。

## Product Observation｜进一步观察

沿着这个方向，AI 设计工具可以进一步把发现定位到组件，将建议、实际改动与复查证据关联起来。用户需要看到的不只是“这里不好”，还包括为什么优先处理、允许改到什么程度，以及改完后如何判断。这是可以延展的产品方向，不代表现有工具已经自动完成全部环节。

Impeccable 值得记录的，不只是它能帮助 AI 改界面，而是它把设计反馈变成了可以讨论、选择和执行的工作对象。对于 Vibe Coding，生成能力越强，越需要准确描述问题，并限制不必要的变化。

真正有价值的设计辅助，不是每次都让页面看起来像换了一个产品，而是在保留有效部分的基础上，让用户更容易完成原本要做的事情。
