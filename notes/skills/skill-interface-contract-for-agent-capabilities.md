# Skill Interface Contract｜为可复用能力定义输入、输出与边界 🧩

- Source｜来源：Anthropic Agent Skills Best Practices
- Type｜类型：AI 产品方法观察 / Agent Skills / Capability Contract / Input & Output Design
- Link｜链接：https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices

当一个 Skill 只被单个 Agent 临时使用时，模糊的描述有时还能工作。随着它被更多 Agent、工作流或用户入口复用，问题会迅速出现：有人不知道该提供哪些资料，有人把输出直接用于不适合的场景，也有人在任务失败后无法判断责任落在输入、Skill 还是后续流程。

Skill Interface Contract 可以理解为一份面向使用者的能力约定。它不要求把每一步内部实现公开出来，而是明确说明这个 Skill 接收什么、产出什么、在哪些条件下适用，以及它明确不承担什么。这样，能力模块才不只是一个“看起来能用的说明”，而是可组合系统中的稳定节点。

---

## What It Is｜它是什么 🧩

在传统软件里，接口会定义参数、返回值和异常。对于 Agent Skill，接口同样存在，只是它常常同时面对人、模型和其他能力模块。

一份有效的 Skill Interface Contract 至少应回答几个问题：任务的目标是什么；完成任务必须具备哪些输入；输出将以什么格式和质量标准交付；哪些上下文只在特定条件下需要；当信息不足、权限不够或目标超出范围时，系统会怎样把任务交还给使用者。

这不是把 Skill 写成冗长的使用手册。重点是让调用方能够在开始前判断“这是不是我要用的能力”，让工作流能够在结束后判断“这个结果能否继续向下传递”。

---

## Why It Matters｜为什么值得关注 💡

已有的 Skill 整理通常会讨论能力如何封装、如何被发现，以及如何评估是否触发正确。但当 Skill 数量增加后，真正影响协作效率的往往不是“能否找到”，而是“找到之后是否知道如何安全地使用”。

例如，一个“生成竞品分析”的 Skill 如果没有说明输入资料的最低要求、输出是否包含未经核验的推断、以及它不替代事实核验，使用者就很容易把一个探索性草稿当成定稿。问题并不完全来自模型输出，而是能力边界没有被产品化地表达。

因此，接口约定是一种降低协作不确定性的设计。它把隐藏在提示词、脚本和经验里的前提显性化，让同一能力可以被不同任务稳定复用。

---

## Interface Elements｜接口应包含什么 ⚙️

一个可复用的 Skill 可以围绕以下六类信息定义接口。它们不必都写成固定表单，但应能被人和 Agent 清晰识别。

- **任务承诺**：它处理哪一类目标，最终交付的结果是什么。
- **输入要求**：哪些资料是必需的，哪些是可选的；输入不完整时能否继续。
- **输出约定**：结果的结构、粒度、语言和可直接使用的范围。
- **能力边界**：哪些相邻任务不属于它，避免一个 Skill 被误当成万能入口。
- **副作用与权限**：它是否读取外部资料、写入文件、调用工具或产生费用。
- **失败与交接**：遇到冲突、缺少事实依据或无法完成时，向谁说明、需要补充什么。

其中最容易被忽略的是边界和失败方式。一个能力是否可靠，不只取决于成功时输出多好，也取决于它不能可靠完成时是否会及时停下并交还判断权。

## Use Case｜适用场景 📌

接口约定尤其适合放在会被反复调用、会进入自动化流程，或会影响后续决策的 Skill 上。比如研究整理、内容改写、数据抽取、需求拆解和代码变更检查，都很容易因为输入格式或输出假设不一致而产生返工。

以“用户反馈分类”为例，Skill 不应只写“分析反馈”。更有用的约定是：它接收原始反馈和目标分类；输出带有证据片段的主题归纳；不能自行把推测当成用户事实；当样本量不足时提示继续收集。这样的设计让下一步的汇总、优先级判断或人工审核都有明确依据。

在多 Agent 工作流里，接口还是角色切换的依据。上游 Agent 知道何时准备好材料，下游 Agent 知道怎样理解结果，协调层也能识别是否需要重试、补充信息或转交人工。

## Product Insight｜产品观察 🔍

从产品视角看，Skill Interface Contract 的核心不是文档规范，而是把“能力使用体验”设计成可预期的过程。

用户不需要理解一个 Skill 的全部技术细节，但需要在调用前看见关键承诺：这个能力会处理什么数据、给我怎样的结果、是否会触发外部动作、我还需要对哪些结论负责。把这些内容放到可发现和可检查的位置，能降低 AI 产品中常见的误用与过度信任。

这也改变了能力市场或 Skill Library 的信息架构。列表页不能只展示名称和一句卖点，还应帮助使用者比较输入成本、输出形式、权限范围和适用限制。能力越接近真实工作流，这种透明度越重要。

---

## Reusable Value｜可复用价值 🔁

这套思路可以用于设计个人 Agent、团队内部能力库或面向用户的 AI 应用。产品团队可以把接口约定作为 Skill 上线前的最小检查项：是否有明确任务、输入、输出、边界和失败提示；不同版本修改后，原有调用方是否仍能理解结果。

它也能让评估更有针对性。已有的 Skill Evaluation 可以验证是否被正确触发、是否完成任务；接口约定则提供了测试的前提。没有可检验的输入和输出定义，所谓“任务成功”往往无法被稳定判断。

---

## Productization Direction｜产品化方向 🚀

面向规模化使用的 Agent 平台，可以把接口约定做成能力发布流程的一部分。创建者在提交 Skill 时声明输入、输出、权限和不可处理的情形；平台据此生成调用界面、权限提示和基础测试用例。

进一步来看，系统还可以根据这些约定完成能力匹配。用户表达目标后，平台不是只按名称推荐 Skill，而是比较当前上下文是否满足输入条件、输出是否能接到下一步任务、以及是否需要额外授权。这样，Skill 的“可发现”会进一步变成“可安全组合”。

---

## Product Observation｜进一步观察

AI 能力越容易被复用，越不能依赖使用者自行猜测其行为。Prompt 提供行为指引，Skill 封装可复用能力，而接口约定负责让能力在真实协作中保持边界清楚、结果可接续、问题可追溯。

对 AI 产品而言，成熟并不等于把更多能力塞进列表，而是让每一项能力都能被正确理解、正确调用，并在不适用时有清晰的退出方式。
