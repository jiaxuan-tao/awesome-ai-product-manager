# Agent Skill Security｜把 Skill 当作可执行软件进行审查 🛡️

- Source｜来源：Anthropic Claude Platform Docs
- Type｜类型：AI 产品方法观察 / Agent Skills / Security Review / Capability Governance
- Link｜链接：https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise

Agent Skill 把任务说明、参考资料、模板和脚本封装成可复用能力，让 Agent 不必每次都从空白对话开始工作。

这种封装提高了能力复用效率，也改变了产品的安全边界。用户启用的可能不只是一段文字说明，而是一个会读取文件、调用工具、执行脚本或访问外部服务的能力包。

因此，Skill 不能只按“Prompt 模板”理解。随着它拥有更多行动能力，安装和更新 Skill 应该接近安装软件：先确认来源和用途，再检查它会访问什么、执行什么，以及出现问题后能否停用和回退。

> Skill 的价值来自能力复用，风险也来自能力被打包后更容易传播和执行。

---

## What It Is｜它是什么 🧩

Agent Skill Security 关注的是 Skill 从创建、审核、分发到运行和更新的完整信任过程。

现有的 Agent Skills 文章讨论了如何把专业工作方式封装成可发现、可组合的能力单元。这篇进一步关注另一个问题：当能力包可以携带脚本、引用 MCP 工具、读取文件或发起网络请求时，产品如何判断它是否适合被安装和运行。

根据 Anthropic 的企业 Skills 指南，具体 Skill 的风险评估需要关注代码执行、指令操纵、MCP Server 引用、网络访问、硬编码凭证、文件系统范围和工具调用等因素。这些风险不一定意味着某个 Skill 有问题，但它们决定了审核强度和运行边界。

例如，一个用于整理本地报告的 Skill 读取指定文件夹可能符合用途；如果它同时要求访问无关目录并把结果发送到外部地址，风险就已经超出“文档整理”本身。

安全判断不能只看 Skill 名称或简介，而要检查说明、脚本、资源和外部依赖是否共同符合它宣称的任务。

---

## Why It Matters｜为什么值得关注 💡

Skill 的产品优势是降低重复配置成本。一个经过整理的能力包可以在团队中共享，让不同用户获得相对一致的工作方法。

但共享也会放大错误和恶意行为。一段普通 Prompt 通常只影响当前对话，而一个被广泛安装的 Skill 可能进入多个用户的文件环境、工具连接和任务流程。它一旦存在过宽权限、隐藏指令或不可信依赖，影响范围会随分发规模扩大。

另一个问题是用户容易把“来自能力库”误解成“已经安全”。实际上，被收录、可下载或由同事分享，只能说明 Skill 可以被发现，不能自动证明其代码、指令和依赖已经经过审核。

产品需要区分几个状态：

- 来源是否可以确认
- 内容是否经过安全审查
- 当前版本是否通过评估
- 运行需要哪些数据和工具
- 更新后是否仍然符合原有边界

只有把这些信息显式化，用户才能理解自己启用的究竟是什么。

## Risk Surface｜Skill 的风险面 ⚠️

Skill 的风险来自多个部分共同作用，而不是只来自某一段脚本。

### Instructions｜指令内容

`SKILL.md` 和引用的说明文件会影响 Agent 如何理解任务。如果其中包含隐藏操作、绕过确认、忽略既有规则或根据特定输入改变行为的指令，风险可能在正常预览中并不明显。

这和 Prompt Injection 有相邻之处，但关注对象不同。Prompt Injection 讨论外部内容如何劫持当前决策；Skill Security 关注的是一个被主动安装的能力包是否从一开始就携带了不恰当的指令和行为边界。

### Scripts and Resources｜脚本与资源

Skill 可以通过脚本完成确定性处理，这也是它比纯文字 Prompt 更有价值的原因之一。但脚本可能读取环境变量、访问文件、执行命令或连接网络。

产品不能只展示“包含三个文件”，而应告诉用户这些文件分别承担什么作用，是否可执行，以及运行时可能接触哪些资源。脚本测试也应优先放在隔离环境中，避免审核本身就触发真实副作用。

### External Dependencies｜外部依赖

Skill 可能引用包、远程地址、MCP Server 或其他工具。即使 Skill 本身内容稳定，外部依赖的版本、权限和返回行为仍可能变化。

因此，审核对象不应止于当前目录。产品还需要记录依赖来源、版本和用途，并在依赖发生重大变化时重新提示审查。

### Combined Permissions｜组合权限

单项能力的风险可能有限，组合后却可能形成新的路径。例如，读取本地文件和发送网络请求分别都有合理场景，但同时存在时就需要判断敏感内容是否可能被传出。

权限评估应围绕完整任务链进行，而不是逐项确认后简单相加。

## Product Insight｜产品观察 🔍

Agent Skill Security 最重要的产品启发，是能力市场不能只优化“发现和安装”，还必须设计“理解和控制”。

传统插件商店常用名称、评分和安装量帮助用户决策，但 Skill 的行为更依赖自然语言指令、模型理解和运行环境。同一个 Skill 在不同模型、工具集合或文件权限下，实际表现可能不同。一个静态详情页很难完整表达这种动态风险。

因此，Skill 安装页需要提供接近权限清单的能力预览：它会读取哪些范围、是否执行脚本、是否连接外部服务、可能调用哪些工具，以及哪些步骤会产生写入或发送等副作用。

更新体验同样重要。如果新版本扩大了文件访问范围或增加了网络依赖，产品不应像普通文案更新一样静默替换。用户或管理员需要看到差异，并决定是否继续使用。

这也说明“已审核”不应该是永久标签。Skill 的内容、依赖、模型和业务流程都可能变化，安全状态必须与具体版本和评估时间绑定。

## Use Case｜适用场景 📌

在个人 AI 工作台中，用户可能从社区安装写作、数据分析或代码处理 Skill。产品应帮助用户区分只提供说明的低风险 Skill，与会运行脚本、读取本地文件或连接账号的高权限 Skill。

在团队环境中，多个成员可能共同使用统一能力。此时需要明确维护者、批准版本、适用角色和依赖工具，避免成员各自安装来源不明或行为不同的副本。

在企业 Agent 平台中，Skill 还可能进入正式业务流程。团队不仅要检查安全，还要验证它是否在正确任务触发、是否会抢占其他 Skill、能否稳定遵循流程，以及模型升级后是否出现退化。

对于一次性、低风险的个人任务，完整治理流程可能过重。产品应根据代码执行、数据敏感度、外部连接和影响范围分级，而不是让所有 Skill 都经历相同审批。

## Reusable Value｜可复用价值 🔁

设计 Skill 产品时，可以把治理拆成五个可复用环节：

1. **来源确认**：记录作者、仓库、签名或组织归属，避免来源在传播过程中丢失。
2. **安装预览**：展示说明文件、可执行脚本、外部依赖、数据范围和工具权限。
3. **隔离评估**：验证正确触发、非目标任务不触发、输出质量和与其他 Skills 共存时的表现。
4. **版本发布**：把审核和评估绑定到具体版本，生产环境固定已批准版本。
5. **停用与回退**：出现异常时能够立即停用，并恢复到上一个已知稳定版本。

这些机制不只适用于 Agent Skills，也适用于 Prompt 包、Agent 模板、MCP 组合和可执行工作流。只要产品允许用户安装并复用第三方能力，就需要回答同样的问题：谁提供了它，它能做什么，发生变化时谁负责。

## Productization Direction｜产品化方向 🚀

### Skill Trust Center｜能力信任中心

能力库可以为每个 Skill 集中展示来源、维护者、版本、依赖、权限、最近审核和评估结果。可信状态应有明确依据，而不是只显示模糊的认证图标。

### Permission Diff｜权限变化对比

更新前自动比较新旧版本，让用户看到新增脚本、外部地址、工具引用和访问范围。没有扩大权限的更新可以更顺畅，边界变化则需要重新确认。

### Sandbox Review｜隔离审查

平台可以在隔离环境运行 Skill 的代表性任务，记录文件访问、网络请求、命令执行和工具调用，帮助审核者把静态内容与实际行为结合起来判断。

### Organization Registry｜组织能力注册表

团队可以维护批准的 Skill 目录，记录负责人、适用角色、当前版本、依赖和评估状态。注册表的价值不是集中控制数量，而是让能力资产拥有清楚的责任和生命周期。

Agent Skills 让 AI 产品能够积累专业能力，而安全治理决定这些能力能否被长期信任。

真正成熟的 Skill 产品，不只是让能力容易安装，还要让用户在安装前理解边界、运行中保留控制，并在更新或异常时能够追溯和恢复。
