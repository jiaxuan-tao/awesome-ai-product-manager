# Huashu Design｜从生成好看的页面到交付可编辑的演示文稿 🎨

- Source｜来源：花叔（alchaincyf）官方 GitHub 仓库 / 幻灯片制作规范 / PPTX 导出文档与脚本
- Type｜类型：AI 产品能力模块观察 / Design Skill / Editable PPTX / 文档交付
- Link｜链接：https://github.com/alchaincyf/huashu-design

让 AI 生成一页好看的演示稿，与把一套材料交给别人继续使用，并不是同一个任务。

第一次展示时，用户可能只关心画面是否清楚、有吸引力。真正进入工作之后，还会修改结论、替换截图、更新数字，或把材料交给不使用同一套工具的人。此时，生成过程省下的时间，可能重新消耗在格式转换和反复修订里。

Huashu Design 提供了一个值得观察的 Skill 样本。这篇不全面罗列它的设计能力，而是聚焦一个具体问题：AI 设计产物怎样从“可以展示”走向“可以编辑、维护与交接”。本文基于公开文档和源码阅读，未实际安装该 Skill，也未生成或验证演示文件。

---

## What It Is｜它是什么 🧩

Huashu Design 是一套面向 Agent 的 HTML 原生设计 Skill，覆盖原型、幻灯片、动画和信息图等场景，包含说明、参考资料、素材与脚本。它不是独立的在线 PPT 编辑器，实际执行仍依赖 Agent 及相应环境。[作者仓库](https://github.com/alchaincyf/huashu-design)

对幻灯片任务，官方规范把 HTML 演示版作为基础产物，再根据需求导出 PDF 或 PPTX，并要求在制作之前确认交付格式。[幻灯片规范](https://github.com/alchaincyf/huashu-design/blob/master/references/slide-decks.md)

这个顺序具有产品意义。格式并不只是最后保存文件时的选项，它会影响制作过程中哪些结构适合采用，以及接收方以后怎样修改。用户说“做一份 PPT”，可能只是想在会议中展示，也可能需要交出可以持续维护的工作文件，两者不能默认等同。

---

## Why It Matters｜为什么值得关注 💡

AI 设计产品容易把优化目标放在首次生成上：更快出现结果、更丰富的画风、更醒目的封面。这些能力有价值，但没有覆盖材料后续的生命周期。

例如一份产品复盘，今天写的是试验结果，下一周可能需要补充真实数据；一份项目介绍，换了目标读者之后，可能需要调整论点和页面顺序。如果每次都必须重新生图、重新导出，再人工检查所有页面，第一次生成的效率就不能直接代表长期效率。

因此，这类工具的产品价值还应包含修改成本和交接成本。接收方能否在熟悉的软件中完成一次小改动，作者是否知道修改应落在哪个源文件，都会决定产物是否真正进入日常工作。

这与单纯比较画面质量不同。一个视觉略简洁但容易维护的文件，在反复更新的场景中，可能比效果更强、却难以局部修改的产物更合适。

## How It Works｜交付要求怎样影响制作路径 ⚙️

### Format Before Layout｜先确认用途，再决定格式

可以先把需求分成三类，而不是直接要求某个扩展名：

- 浏览器演示：重点是现场呈现与翻页体验。
- PDF 分发：重点是阅读、打印和相对稳定的版面。
- 可编辑 PPTX：重点是接收方能继续修改文字与页面对象。

这些用途可能同时存在，但验收标准不同。一份能打开的 PPTX，不一定便于改字；一份视觉一致的 PDF，也不等于提供了适合继续维护的源文件。

从产品角度看，开始前最有用的问题是：“谁会在什么工具里修改哪些内容？”答案比“喜欢哪种风格”更早决定交付方案。

### Two Export Paths｜不要把不同路径的限制混为一谈

仓库的一条路径通过 `html2pptx.js` 将页面元素转换为文本框、形状和图片等对象，配套文档要求 HTML 满足特定结构与样式约束，例如文字标签的组织方式，以及背景图、渐变的处理限制。[可编辑导出约束](https://github.com/alchaincyf/huashu-design/blob/master/references/editable-pptx.md)、[转换脚本](https://github.com/alchaincyf/huashu-design/blob/master/scripts/html2pptx.js)

另一份文档提供面向已有视觉稿的渲染坐标路径，并说明如何以现有 PPTX 模板为基础生成页面。[已有视觉稿的导出路径](https://github.com/alchaincyf/huashu-design/blob/master/references/pptx-from-rendered-html.md)

因此，不能把第一条路径的约束概括成所有导出方式的共同限制，也不能因为存在第二条路径，就推断任意网页都能无损变成演示文件。需要结合实际页面、脚本版本与目标软件验证，而不是只看一个“支持导出”的标签。

### Editable Objects｜能选中文字，只是可编辑的一层

原生文本框让文字有机会在演示软件中继续修改，但编辑体验还取决于对象如何组织。一个段落被拆成许多小框，与保留连续段落，在后续改写时的成本完全不同。

官方文档提供合并文本框的机制，也列出对齐和行距等限制。[文本框组织说明](https://github.com/alchaincyf/huashu-design/blob/master/references/editable-pptx.md) 这说明可编辑并不是简单的有或无，而是用户能够以多小的代价完成预期修改。

因此，验收可以包含一次真实编辑：把标题加长、把结论改成两行，观察是否仍容易调整。只确认双击后能输入文字，还不足以判断文件适合长期维护。

## Use Case｜适用场景 📌

对个人 AI 产品实践，这个方向适合产品介绍、阶段复盘、方案比较和知识分享等需要持续更新的材料。重点不是把所有记录都做成演示稿，而是让确实需要传播的判断拥有清楚、可维护的表达形式。

例如整理一个 Vibe Coding 项目，可以先确定真实用户问题、关键流程、已经实现的能力和待验证部分，再决定哪些页面需要截图、流程或数据。真实界面应保留真实素材，不能为了视觉统一而生成并不存在的产品状态。

若材料只是一次性现场演示，不一定需要把所有视觉内容都转换成原生对象。若接收方需要更新文字、调整模板和反复复用，则应优先考虑编辑结构。交付能力应由后续使用决定，而不是一律追求最多格式。

## Product Insight｜把后续使用纳入生成目标 🔍

### 可编辑、可维护与可协作需要分别判断

可编辑关注能否改动对象；可维护关注下一次更新能否稳定完成；可协作还涉及其他人是否理解结构、使用相同资产，以及怎样避免版本混乱。

例如作者在 HTML 中更新数据，接收方同时在 PPTX 中修改结论，两份材料就可能开始分歧。能够导出两种格式，不等于它们之间存在双向同步。

因此，交付时需要约定下一次修改以哪一份为准，以及重新导出会不会覆盖已有调整。对于小型项目，一句清楚的维护说明可能比增加复杂同步功能更有用。

### 文件存在，不代表页面完整

阅读 `export_deck_pptx.mjs` 可以看到：全部页面转换失败时脚本停止；部分页面失败时，仍可能写出文件，并在日志中显示成功与总页数。[批量导出实现](https://github.com/alchaincyf/huashu-design/blob/master/scripts/export_deck_pptx.mjs)

这意味着自动流程不能仅凭“输出文件已生成”宣布交付。还应检查预期页数、实际页数和失败记录，防止中间缺页的材料被误当成完整结果。这是对当前源码行为的阅读结论，不是本次运行发现的故障。

### 导出预览，不等于接收方看到的效果

作者在渲染坐标路径的文档中提醒，不同渲染工具可能呈现不同结果，并建议在实际演示软件中确认，同时进行文字完整性检查。[验证与渲染差异](https://github.com/alchaincyf/huashu-design/blob/master/references/pptx-from-rendered-html.md)

产品上需要把检查放到最终使用环境里。源页面没有重叠，不代表导出的页面没有重叠；导出时文字齐全，也不代表字号、行距和换行适合阅读。最值得验证的是接收方会做的那次打开、修改和展示，而不是只检查生成环节自身。

## Reusable Value｜可迁移的交付判断 🔁

这个案例可以延伸出一个轻量原则：先定义接收方的下一步动作，再决定生成结构和验证方式。

如果下一步是阅读，就关注内容层次与阅读顺序；如果下一步是更新数字，就关注数字和图表是否容易找到、是否需要同步改动；如果下一步是改模板，就需要检查公共元素与内容层的关系，而不是只把所有页面做得像同一个模板。

这种方法同样适用于 AI 生成的报告、原型和表格。产物是否完成，不能只由生成者的输出动作定义，还要看使用者能否顺利接着做下一件事。

它与 [Huashu Art Motion](./huashu-art-motion-executable-creative-workflow.md) 的交付检查相邻，但本篇重点是格式转换后的编辑与维护，不再展开动画审片。与 [PromptInfuser](../workflows/promptinfuser-ai-ui-workflow.md) 相比，这里也不是验证模型和界面的联动，而是观察生成产物离开原环境之后，能否继续被使用。

## Practical Direction｜面向后续使用的产品化方向 🚀

一种可延展的设计，是在制作前展示交付能力说明：哪些内容可以原生编辑，哪些会作为图片保留，哪些视觉效果需要调整，以及模板能否沿用。让用户在生成之前理解取舍，比导出之后再解释限制更有效。

另一方向是修改回归检查。用户改过标题或替换截图后，重新检查受影响页面的溢出、遮挡和字体状态，而不是每次都从头生成整套材料。它的价值来自缩小修订范围，不是增加更多生成次数。

交接时还可以附一份简短记录，说明维护源文件、使用字体、素材位置、导出路径和未验证项。记录需要与实际文件对应，不应把自动化能够执行的步骤直接标成已经完成。以上是基于案例延展的产品建议，不是本次已实现的功能。

## Product Observation｜进一步观察

Huashu Design 值得记录的，不只是 AI 能否帮助设计，而是设计方法开始包含交付之后的使用要求。

一次好看的生成可以吸引注意，一次低成本的修改和顺畅交接，才更可能让工具进入长期工作。对 AI 产品而言，生成质量应与后续使用成本一起衡量：用户拿到的究竟是一张结果图，还是一份能够继续工作的材料。
