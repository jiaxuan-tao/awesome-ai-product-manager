# Hallmark｜让真实素材和用户任务决定第一版界面 🎨

- Source｜来源：Nutlope/hallmark 官方 GitHub 仓库 / Skill 定义与设计参考文档
- Type｜类型：AI 产品能力模块观察 / Design Skill / 页面生成 / Vibe Coding
- Link｜链接：https://github.com/Nutlope/hallmark

让 AI 做一个页面，往往很快就能得到完整结果：标题、介绍、功能卡片、几组数字，再加一个醒目的行动按钮。问题在于，换一个产品名称，这套结构可能仍然成立。页面看起来完整，却没有说明这个产品为什么需要这样呈现。

Hallmark 提供了一个值得观察的方向：在生成界面之前，先检查有什么真实材料、用户准备完成什么任务，再决定页面形态。本文基于官方公开资料分析，未实际安装或验证生成效果；文中的案例与产品建议不代表已经完成的实践。

## What It Is｜它是什么 🧩

Hallmark 是面向编程 Agent 的设计 Skill，结合设计说明、参考资料与脚本，约束页面生成过程。它不只是提供一组配色，而是试图组织从理解项目、确定方向到生成和检查的工作方式。[官方仓库](https://github.com/Nutlope/hallmark)

其 Skill 要求先阅读项目，再确认素材、受众、用途与风格。对于已有设计，普通修改不应自动变成 Hallmark 重设计；使用者需要明确点名相应操作。[Skill 定义](https://github.com/Nutlope/hallmark/blob/main/skills/hallmark/SKILL.md) 这个边界很重要：提供一种设计方法，不等于获得推翻现有界面的授权。

本篇不把 Hallmark 当作“让 AI 更有审美”的笼统工具，而是观察它如何影响第一版的决定。用户看到页面之前，结构、素材与主要动作已经被选择；如果这些选择缺乏依据，后续再调整字体和间距，也很难补回产品本身的表达。

## Why It Matters｜为什么值得关注 💡

首次生成很容易形成后续迭代的默认起点。一个页面只要已经存在，讨论就会自然转向“这里换颜色”“那里加内容”，较少重新判断这一整块是否应该出现。最初未经确认的假设，因此可能被逐渐固化。

例如，一个个人工具还没有真实使用数据，AI 却生成了用户数量、客户标志和评价区域。即使后来把数字替换为占位文字，页面仍然围绕并不存在的证明组织内容。问题不是文案没填完，而是结构先于事实成立了。

因此，第一版质量不应只用视觉完整度衡量。更值得问的是：它是否利用了已经存在的材料，是否清楚表达用户能做什么，以及是否暴露了尚未确定的部分。一个范围诚实、路径清楚的初稿，比一份需要不断拆除虚构内容的完整页面更容易继续推进。

## How It Works｜先决定内容，再选择形式 ⚙️

Hallmark 的流程先整理真实内容、可展示图片与缺失证据，再确定页面的主要任务。主题承担视觉表达，不应替代内容和顺序的判断。[生成流程](https://github.com/Nutlope/hallmark/blob/main/skills/hallmark/SKILL.md) 从产品角度看，这是把“有什么可说”与“准备怎么呈现”分开，避免先挑中一种漂亮形式，再为它临时编造材料。

官方页面结构参考按访问者任务组织，例如订阅、预约、购买或试用，并让主要动作、内容类型和结束方式围绕任务展开。[任务与页面结构](https://github.com/Nutlope/hallmark/blob/main/skills/hallmark/references/anatomy.md) 值得借鉴的不是某个固定顺序，而是不同任务不应该因为同样由 AI 生成，就拥有相同的页面骨架。

素材也有明确角色。官方图片规范优先使用用户材料与可获取的真实产品截图，并区分真实内容、尚无产品时的构建展示和替代素材。[素材规范](https://github.com/Nutlope/hallmark/blob/main/skills/hallmark/references/imagery.md) 这让视觉不只是填满空间，还承担展示产品状态与使用对象的责任。

对个人实践而言，这些机制可以简化成一个判断：先确认页面需要证明什么，再选择能够支持它的材料。若关键事实尚不存在，应该缩小表达范围，而不是让视觉上的完整掩盖信息上的缺口。

## Practical Use｜适合怎样的任务 📌

假设要为一个已经能运行的桌面翻译工具制作介绍页。现有材料包括真实窗口、截图识别流程和历史记录，但没有用户规模与效果评测。合理的第一版可以围绕实际操作展示：用户从哪里开始，怎样获得翻译结果，以及目前支持哪些使用路径。

这时，一张清楚呈现真实状态的截图，可能比三组抽象能力图标更有解释力。尚未实现的功能不应该出现在产品演示中，示意内容也不能被写成已经验证的效果。页面的可信度来自材料与事实对应，而不是来自它拥有多少常见模块。

如果目标是翻译工具本身的工作界面，判断又不同。官方为应用界面提供单独分支，不套用营销页面的首屏、分段节奏和字数预算等要求。[应用界面分支](https://github.com/Nutlope/hallmark/blob/main/skills/hallmark/references/flow.md) 输入、翻译、修正和保存才是主要任务，不需要在工作区上方再放一个介绍产品的巨大标题。

这也说明，适合公开介绍的页面，不一定适合反复操作。识别页面用途，比寻找一种适用于全部场景的“高级感”更早影响设计质量。

## Product Insight｜模板化不只是视觉重复 🔍

模板化最深的部分，往往不是配色相似，而是默认每个产品都需要同样的证明方式、内容顺序与行动入口。一个供用户直接使用的工具，如果先让人阅读大量介绍，再进入真正功能，即使视觉独特，也可能仍在沿用不合适的产品逻辑。

反过来，熟悉的布局不一定需要被消灭。用户已经理解的表单、列表与导航，可以降低学习负担。为了看起来与众不同而改变常见操作，可能把视觉上的新鲜感转化为使用中的额外成本。

因此，去模板化更值得追求的是决定有依据，而不是每次都不同。主要动作为什么放在这里，截图为什么展示这个状态，哪些内容没有加入，都应该能够回到用户任务和现有事实。差异是这些判断的结果，不应成为独立目标。

这与已发的 Impeccable 形成不同侧重：那篇关注已有界面的问题如何变成可执行反馈；本篇关注第一版出现之前，哪些事实和任务应该决定它的结构。两者能力存在交集，不应被简单划成只能生成或只能修改的两类工具。

## Evidence & Limits｜规则不能代替产品判断 🛡️

Hallmark 将检查分为不同层级：不可豁免的 Floor、允许有依据例外的 Reflex，以及不阻断交付的 Finish 等。其文档也明确，部分硬性要求属于项目自身的风格规则，而不只是普遍正确性要求。[规则层级](https://github.com/Nutlope/hallmark/blob/main/skills/hallmark/references/gates.md)

这意味着，遵守这套规则与满足所有产品需求不是同一件事。工具选择限制某种表达方式，可以减少模型反复采用的套路；但不能据此证明该方式在任何场景都错误。已有品牌规范、用户习惯和实际任务仍然需要单独判断。

同样，脚本检查通过，只能证明已执行检查没有发现相应问题，不能证明用户理解产品、表单完成真实提交，或外部服务已经接通。规则还区分静态、渲染与需要判断的检查，不能用一种结果替代全部验证。

如果环境缺少运行条件，就应说明没有完成什么。要求 Agent 执行浏览器检查，不等于浏览器检查真的发生；留下一个通过标记，也不等于存在对应证据。本文介绍工作方法，不将其描述为无需人工判断的质量保证。

## Reusable Value｜把生成前的决定留下来 🔁

对个人产品实践，可以先准备一份简短的生成依据：真实材料有哪些，本次页面服务哪项任务，哪些事实尚未获得，以及必须保留什么。它不必成为另一份复杂文档，但应让 Agent 少猜测几个会影响结果的关键问题。

初稿出现后，审阅也可以先看这些决定是否成立。产品本身有没有被展示，主要动作是否符合当前能力，缺失材料有没有被偷偷补成事实。若这里不成立，继续微调视觉通常只是推迟结构问题。

对于不同方向的比较，可以保持内容与任务相同，只改变部分表达方式。否则，一个方案使用真实截图，另一个方案拥有虚构数据，比较出来的偏好就混入了内容差异，不能直接说明哪种视觉更合适。

这里可以延展出一种轻量设计记录：把关键选择与依据关联，让后续修改知道哪些来自事实、哪些属于风格、哪些只是临时推断。它的价值是减少下一轮误解，而不是让每次生成都多交一份报告。

## Product Observation｜进一步观察

Hallmark 值得记录的，不只是它试图减少 AI 页面的惯用套路，而是它把素材与任务放到了生成之前。很多页面缺少独特性，并非模型不会选颜色，而是开始时没有足够具体的对象，也没有清楚的使用目标。

对 AI 产品而言，生成得越快，越需要留意第一版中哪些决定已经获得依据。真实材料不足时，克制表达往往比补齐常见模块更有价值；用户任务明确时，熟悉而有效的结构也不需要为了新鲜感被替换。

好的第一版，不是看起来已经什么都有，而是让已经成立的事实得到清楚呈现，让用户知道能够做什么，也让尚未确定的部分没有被假装完成。
