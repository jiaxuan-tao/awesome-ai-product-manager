# Agent Handoffs｜让多 Agent 协作不丢失任务上下文 🔄

- Source｜来源：OpenAI Agents SDK Docs
- Type｜类型：AI 产品方法观察 / Agent Handoffs / Multi-agent Workflow / Task Delegation
- Link｜链接：https://openai.github.io/openai-agents-python/handoffs/

多 Agent 并不等于把一个任务拆给更多模型。真正困难的部分往往出现在交接时刻：当前 Agent 为什么不能继续；下一个 Agent 需要知道什么；用户是否意识到任务已经换了负责者；发生错误后又该由谁恢复。

Agent Handoff 描述的是任务在 Agent 之间的控制权转移。它让一个负责入口或协调的 Agent，把明确的子任务交给更适合的专业 Agent，同时尽量保留完成任务所需的上下文和对用户的责任边界。这个概念值得从产品层面理解，因为用户感受到的不是“模型换了”，而是同一个任务能否持续被推进。

---

## What It Is｜它是什么 🧩

Handoff 通常发生在一个 Agent 判断另一个 Agent 更适合处理当前目标时。它不是简单复制一段对话给下游，而是一次有条件的任务委派：明确委派对象、交接原因、可传递的上下文、期待结果，以及何时回到原来的协调流程。

这与跨系统协作协议关注的问题不同。A2A 更关注不同系统中的 Agent 如何发现彼此并交换任务；Handoff 更关注一个具体工作流内部，任务怎样从通用入口转到专业能力，再以可理解的结果回到用户面前。

因此，Handoff 的价值不在于制造更多角色，而在于让角色分工真正减少复杂度。若每次交接都丢失目标、重复追问用户或无法说明状态，多 Agent 只会让体验更碎片化。

---

## Why It Matters｜为什么值得关注 💡

一个通用 Agent 很难同时在研究、数据分析、代码修改、客户沟通等领域保持同样可靠的判断。专业化可以提高任务质量，但专业化也会带来新的协调成本。

用户通常不会关心背后有几个 Agent。他们只会观察：我刚才说明的目标是否还被理解；系统为什么转交；现在正在做什么；最后得到的结果是否仍然对原始问题负责。若这些问题没有被设计好，所谓“多 Agent 协作”会变成多轮重复输入。

Handoff 让产品团队不得不正视任务所有权。哪个 Agent 有权继续、哪个 Agent 只能提供建议、什么情况下应该请用户确认，这些边界决定了自动化程度是否真正带来效率。

---

## How a Handoff Works｜交接如何发生 ⚙️

一次可靠的交接通常需要保留最小但足够的任务包，而不是无差别传递全部历史。这个任务包可以包括原始目标、已确认的约束、已经完成的步骤、相关资料引用、未解决的问题，以及下游 Agent 被授权执行的范围。

交接触发也需要明确。它可以来自任务类型匹配、需要特定工具、风险等级变化或当前 Agent 置信度不足。触发之后，系统应记录谁接手、为什么接手、预计产出是什么。这样，当下游结果不足以支持结论时，协调层能够继续追问、改派或请求用户补充信息。

最重要的是回收机制。专业 Agent 不能只返回一段孤立答案，而应返回可被上游理解的结果、证据和未完成事项。否则用户仍要自己把多个角色的输出重新拼成行动方案。

## Use Case｜适用场景 📌

研究型任务是典型例子。入口 Agent 先澄清用户的问题和判断标准，再把资料检索、数据比较或观点归纳交给不同专业 Agent。最终由协调 Agent 汇总证据、标注不确定性，并对最初问题给出回应。这里的关键不是并行数量，而是每一段工作都能回到同一目标。

在软件开发场景中，协调 Agent 可以把故障定位交给代码分析 Agent，把测试执行交给验证 Agent。用户需要看到的是当前修改由谁提出、验证结论是什么、是否仍有未解决风险，而不是被迫理解内部角色图。

对于涉及外部动作的任务，Handoff 还可以作为风险分界线。例如，研究 Agent 可以收集信息，但执行 Agent 在提交、发送或写入前必须获得明确授权。角色交接由此成为权限控制和人工介入的自然节点。

## Product Insight｜产品观察 🔍

多 Agent 产品最容易被忽视的体验问题是连续性。用户的目标、偏好、已做决定和不希望发生的动作，不能因为后端切换了角色就消失。

因此，产品界面应把交接表达为任务进度，而不是神秘的模型切换。必要时可以说明“正在转由数据分析能力核对来源”，并展示当前阶段、可用的取消或接管动作，以及最终结果由谁汇总。透明度并不要求暴露全部内部推理，但应让用户知道任务是否仍在受控地前进。

另一个关键是避免把 Handoff 变成责任逃逸。上游 Agent 即使不亲自完成子任务，也应对任务整体保持协调责任。系统不能因为下游输出不完整，就把一堆片段直接交给用户处理。

---

## Reusable Value｜可复用价值 🔁

设计多 Agent 工作流时，可以用 Handoff 检查清单替代模糊的“角色分工”：每次转交是否有可解释的原因；下游是否拿到完成任务所需的最小上下文；结果是否能回接到原始目标；失败时是否知道由谁继续处理；用户是否能看见和控制关键转折。

它与 Agent Loop 的停止、求助和完成证据形成互补。Agent Loop 关注单个 Agent 何时继续或停止；Handoff 则关注停止自己处理后，如何把任务安全交给下一个合适的执行者。它也与 A2A 的互操作议题相邻，但不重复：前者解决工作流内的任务连续性，后者解决跨系统协作。

---

## Productization Direction｜产品化方向 🚀

面向团队的 Agent 工作台可以把交接设计成可配置的流程节点。创建者定义哪些任务可转交、每种角色可接收的上下文字段、哪些外部动作需要人工批准，以及结果如何回流到统一任务视图。

随着任务规模增加，Handoff 记录也可以成为治理数据。团队能观察哪些交接最常失败、哪些角色反复收到信息不足的任务、哪些任务总需要人工接管，从而优化能力边界和流程设计，而不是单纯增加更多 Agent。

---

## Product Observation｜进一步观察

多 Agent 协作的价值不是让系统看起来更复杂，而是让复杂任务的责任、上下文和下一步更清晰。好的 Handoff 应该让用户感觉任务在持续推进，而不是被不同角色来回转交。

当交接被视为一种可设计的产品体验，Agent 才能从多个独立能力，真正组成可靠的任务系统。
