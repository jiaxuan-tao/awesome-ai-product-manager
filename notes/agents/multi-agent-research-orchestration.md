# Multi-agent Research Systems｜从单 Agent 到并行协作架构 🔬

- Source｜来源：Anthropic Engineering Blog
- Type｜类型：AI Agent 方法观察 / Multi-agent System / Orchestrator-Worker / Research Agent
- Link｜链接：https://www.anthropic.com/engineering/multi-agent-research-system

复杂研究任务很难提前写成一条固定流程。

用户可能只提出一个目标，系统却需要探索多个方向、比较不同来源、继续追问新线索，并在信息足够后整理成有依据的结论。单个 Agent 可以依次完成这些步骤，但它的上下文、时间和注意力都有限。

Multi-agent Research System 提供了另一种组织方式：由一个 Lead Agent 理解目标和制定策略，再把适合并行探索的部分交给多个 Subagents，最后汇总发现并生成结果。

从产品视角看，多 Agent 的重点不是让界面里出现更多“AI 角色”，而是判断一个任务能否通过专业分工和并行投入获得更好的结果。

> 多 Agent 不是默认更强的架构，而是一种需要用任务价值、并行程度和协调成本共同证明的资源配置方式。

---

## What It Is｜它是什么 🧩

Anthropic 公开的 Research 系统采用 Orchestrator-Worker 结构。

Lead Agent 先分析用户问题，确定研究方向，再创建具有明确目标的 Subagents。每个 Subagent 在独立上下文中搜索、判断来源和整理发现，然后把压缩后的结果返回给 Lead Agent。Lead Agent 根据现有信息决定是否继续探索，最终再由专门环节处理引用并交付完整报告。

这种结构和简单的并行搜索不同。

Subagent 不是接收几个关键词后返回网页列表，而是围绕具体子任务持续使用工具、调整方向并筛选信息。Lead Agent 也不只是把结果拼接起来，它需要判断任务是否覆盖完整、不同结论是否冲突，以及哪些发现值得进入最终输出。

多 Agent 因此包含两层智能工作：一层负责各自领域内的探索，另一层负责整个任务的资源分配与结果整合。

---

## Why It Matters｜为什么值得关注 💡

研究任务往往同时需要广度和深度。

如果一个 Agent 顺序探索所有方向，前面的信息会不断占用上下文，后面的搜索也容易受既有路径影响。Subagents 使用独立上下文，可以分别追踪不同线索，并把大量中间材料压缩成 Lead Agent 可以继续处理的结论。

并行也能改善等待体验。多个彼此独立的方向可以同时推进，而不必让用户等待一条漫长的串行任务。

但这种能力有明确代价。Anthropic 在公开文章中指出，其多 Agent 研究架构更擅长需要广泛并行探索的查询，同时也会显著增加 Token 和工具调用消耗。官方内部评估显示了质量提升，也明确提醒多 Agent 并不适合共享上下文要求很高、步骤强依赖或任务价值不足以覆盖额外成本的场景。

这让多 Agent 成为一个产品判断问题：

- 任务能否拆成相对独立的方向
- 并行探索是否真的提高覆盖率
- 最终结果是否值得更高成本和更长运行过程
- 用户能否理解系统为何投入这些资源

只有这些条件成立，多 Agent 才不是架构上的过度设计。

## Architecture｜协作结构 ⚙️

### Lead Agent｜规划与资源分配

Lead Agent 需要把模糊目标转化成可执行研究策略。

它不仅要决定“研究什么”，还要决定投入多少。简单事实查询可能不需要 Subagent；明确对比任务可以拆成少量方向；开放且高价值的研究才可能需要更广泛的并行探索。

如果 Lead Agent 无法判断任务规模，就可能为简单问题创建大量 Agent，或在复杂问题上投入不足。产品需要为它提供努力预算、停止条件和任务边界，而不是让它无限扩张。

### Subagents｜独立探索与信息压缩

每个 Subagent 应获得清楚的目标、范围、来源要求和交付格式。

模糊的委派容易让多个 Agent 重复搜索同一方向，或者分别理解成不同时间范围和问题边界。真正有效的分工不是给 Agent 起不同角色名，而是让每个子任务拥有尽量低的重叠和明确的完成条件。

Subagent 返回的也不应是全部搜索过程。它需要提炼关键发现、证据和不确定性，让 Lead Agent 可以在有限上下文中完成判断。

### Synthesis｜结果整合

多个 Subagents 完成任务后，系统仍然需要处理冲突、缺口和重复。

Lead Agent 要判断哪些来源更可靠、哪些结论只是初步线索，以及是否需要再次派出 Agent 补充验证。最终报告不能因为参与者更多就默认更可信。

Anthropic 的案例还设置了引用处理环节，将结论与具体来源位置对应。这说明多 Agent 产品的最后一步不只是语言润色，而是把分散探索转化成可检查的交付物。

## Use Case｜适用场景 📌

多 Agent 研究更适合可并行、信息规模较大且结果价值较高的任务。

例如，用户需要比较多个市场、政策、产品或技术路线时，不同 Subagents 可以分别研究独立对象，再由 Lead Agent 统一比较。尽职调查、竞品研究、文献综述和跨来源事实核验也具有类似结构。

它不一定适合步骤强依赖的任务。如果后一步必须完整等待前一步结果，创建多个 Agent 并不会带来真正并行，只会增加状态同步和错误传播。

共享上下文要求很高的任务也要谨慎。多个 Agent 如果必须持续理解同一份不断变化的代码、设计或业务状态，分离上下文可能导致信息不一致。

判断是否采用多 Agent 时，首先应该问“任务中有哪些可以独立推进的工作”，而不是“系统最多能创建多少 Agent”。

## Product Insight｜产品观察 🔍

Multi-agent Research System 最值得关注的地方，是它把 Agent 架构变成了一种动态资源分配产品。

传统工作流由产品预先规定步骤，多 Agent 系统则可能根据问题复杂度临时决定参与者数量、搜索范围和工具调用次数。这意味着产品需要管理的不只是流程，还包括任务投入。

### 多 Agent 的核心不是角色，而是分工

很多多 Agent Demo 通过“研究员、分析师、编辑”等角色营造协作感，但角色名称不能保证任务被合理拆解。

真正有效的结构需要说明每个 Agent 负责什么、不能做什么、结果如何被验证，以及其他 Agent 是否已经覆盖相同范围。角色只是呈现方式，边界和交付标准才决定协作质量。

### 任务进度需要从内部状态变成用户反馈

用户不需要阅读每次模型思考，但应该知道系统正在探索哪些方向、哪些部分已经完成、是否遇到信息缺口，以及为什么需要继续投入。

如果界面只显示“正在研究”，多 Agent 带来的并行能力仍然是不可理解的黑箱。更合适的体验可以展示研究计划、方向状态、关键来源和最终整合阶段，同时避免用大量技术日志增加负担。

### 质量提升必须与成本匹配

多 Agent 会增加 Token、搜索、外部工具和运行时间。产品不应默认把所有任务升级为最高投入，而应根据问题价值、用户时效要求和质量目标选择不同档位。

这与 A2A 文章的重点不同。A2A 关注独立 Agent 服务如何跨系统发现和委派任务；本篇关注同一产品内部如何组织 Lead Agent 与并行 Subagents。它也不重复 OpenAI Agents SDK 的基础框架，而专门讨论多 Agent 何时值得采用。

## Reusable Value｜可复用价值 🔁

设计多 Agent 产品时，可以先从任务可分解性开始。

团队需要识别哪些方向彼此独立、哪些步骤存在强依赖、哪些资料必须共享，以及最终由谁承担汇总责任。只有任务地图清楚，Agent 数量才有意义。

然后为每个子任务定义最小交付契约，包括目标、范围、来源要求、输出格式和停止条件。这样可以减少重复探索，也方便 Lead Agent 判断结果是否可用。

系统还应保留投入预算。预算可以覆盖 Subagent 数量、工具调用、Token、运行时间和重试次数，并根据任务复杂度分级。超过预算时，产品需要选择缩小范围、请求用户确认或基于已有信息完成结果。

评估时，不能只看最终答案。还要观察拆解是否覆盖问题、不同 Agent 是否重复工作、重要方向是否遗漏、汇总是否忠实于来源，以及增加的成本是否带来可感知质量提升。

---

## Productization Direction｜产品化方向 🚀

### Adaptive Research Mode｜自适应研究模式

产品可以先评估问题复杂度，再选择单 Agent、少量并行或深度研究模式，并向用户说明预计时间、投入和适用范围。

### Research Plan View｜研究计划视图

界面可以展示当前探索方向、执行状态和主要来源，让用户能够删除无关方向、补充关注重点或提前结束任务。

### Agent Budget Control｜Agent 投入控制

团队或用户可以设置任务级成本、时间和工具预算。系统在预算内动态分配 Agent，而不是让并行规模完全不可见。

### Synthesis Review｜汇总审查

最终结果可以把关键结论、来源和存在分歧的发现放在一起，帮助用户判断 Lead Agent 如何从多个 Subagents 的结果形成结论。

多 Agent 研究系统说明，复杂任务的能力提升不只来自更强模型，也来自更合理的分工、并行和信息压缩。

真正成熟的多 Agent 产品，不是让更多 Agent 同时运行，而是能够判断什么时候需要协作、如何限制投入，并把分散探索转化成用户可以理解和验证的结果。
