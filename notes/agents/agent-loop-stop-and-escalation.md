# Agent Loop｜让 Agent 知道何时继续、停止与求助 🔄

- Source｜来源：OpenAI Agents SDK Documentation
- Type｜类型：AI Agent 方法观察 / Agent Loop / Stop Conditions / Error Recovery
- Link｜链接：https://openai.github.io/openai-agents-python/running_agents/

Agent 与普通问答产品的差异，不只是它能够调用工具，而是它会根据工具结果继续决定下一步。

用户给出一个目标后，Agent 可能先读取信息，再调用搜索或代码工具，观察结果，调整计划，然后继续执行。这个过程形成一个循环：模型判断、工具行动、环境反馈，再回到新的判断。

循环让 Agent 能处理无法一次完成的任务，也带来一个基础问题：系统如何知道应该继续，什么时候已经完成，什么情况下必须停止并向用户说明没有完成。

如果结束太早，Agent 可能只完成了表面步骤；如果没有清楚停止条件，它可能反复调用工具、消耗预算，甚至在错误方向上持续扩大影响。

> Agent 产品不仅要设计“如何行动”，还要设计“什么证据足以证明任务完成，以及什么时候继续行动已经没有价值”。

---

## What It Is｜它是什么 🧩

Agent Loop 是围绕目标持续进行判断、行动和观察的运行结构。

OpenAI Agents SDK 的运行文档描述了一个基础循环：系统调用当前 Agent，模型生成输出；如果得到最终输出，运行结束；如果发生 Handoff，则切换当前 Agent并继续；如果产生工具调用，则执行工具、把结果加入上下文，再次调用模型。超过最大轮次时，系统会结束或进入相应错误处理。

这套结构看起来简单，但每一个分支都包含产品判断。

“最终输出”是否真的代表任务完成？工具返回成功是否意味着用户目标已经实现？一次失败应该重试、换工具、缩小任务，还是立即求助？最大轮次应该按模型调用、工具步骤、时间还是成本定义？

框架可以提供循环机制，产品仍需要定义完成标准、运行预算和异常策略。否则，Agent 只是获得了持续行动能力，却没有获得可靠的结束方式。

---

## Why It Matters｜为什么值得关注 💡

在普通聊天中，一次模型回答自然构成一轮结束。用户可以判断答案是否满足需求，再决定是否追问。

任务型 Agent 会在用户看不到的后台执行多个步骤。用户不一定知道系统已经读取了什么、工具是否真正成功，以及当前回答是一份最终结果还是执行到一半的总结。这使“完成”从对话形式变成产品状态。

很多 Agent 失败并不是完全无法行动，而是缺少正确停止判断。

一种情况是过早完成。Agent 找到一个相关网页就宣布研究结束，修改了代码却没有运行验证，点击提交按钮却没有确认页面状态。它完成了一个动作，但没有获得能够支撑用户目标的证据。

另一种情况是无效循环。Agent 重复搜索相似关键词、反复调用失败工具，或在缺少必要权限时持续尝试。每一步单独看都有理由，整体却没有产生新进展。

还有一种情况是隐性失败。Agent 达到步数或成本限制后，给出一段听起来完整的回答，却没有清楚说明哪些部分未完成。用户容易把运行终止误解为任务成功。

因此，停止条件不仅影响成本和速度，也影响用户是否能正确理解结果、决定是否继续，以及是否愿意把更重要的任务交给 Agent。

## Loop Design｜循环如何设计 ⚙️

### Goal and Completion Contract｜目标与完成契约

循环开始前，产品需要把用户目标转化为可以验证的完成条件。

“帮我检查这个仓库”过于宽泛，Agent 很难判断何时结束。更清楚的契约可以说明检查范围、需要交付的问题类型、是否必须运行测试，以及最终结果应包含什么证据。

完成条件不必把所有步骤提前写死。Agent 可以根据环境调整路径，但结果必须满足稳定标准。例如，修复问题可以允许不同实现方式，完成证据仍应包括目标行为已改变、相关测试通过，以及没有发现明确回归。

如果用户目标本身存在歧义，正确的循环动作可能不是继续探索，而是先请求补充信息。把澄清视为一种有效状态，可以避免 Agent 在错误假设上运行很久。

### Observe and Verify｜观察与验证

每次工具调用后，Agent 都需要区分“动作已经发出”和“结果已经成立”。

搜索工具返回内容不代表来源可靠，文件写入成功不代表内容正确，网页按钮被点击也不代表业务操作已经完成。工具结果需要转换成与当前目标相关的证据，再决定下一步。

产品可以为关键动作定义验证方式：读取修改后的文件、运行测试、检查页面成功状态、查询更新后的记录，或者要求用户确认不可自动判断的结果。

验证会增加步骤和成本，但省略验证会把系统调用成功误认为任务成功。产品应根据动作风险选择证据强度，而不是让所有任务使用同一套固定循环。

### Progress Detection｜判断是否仍有进展

Agent 需要知道当前步骤是否带来了新的信息或状态变化。

连续调用不同工具并不一定代表进展。如果检索结果高度重复、错误原因没有变化、页面状态保持不变，系统应该识别停滞，而不是继续消耗轮次。

进展可以通过目标状态变化、新证据数量、未解决子任务减少，或失败原因是否发生改变来判断。对于复杂任务，维护一个简洁计划和已完成事项，有助于 Agent 区分探索、执行和重复。

当系统检测到停滞时，可以重新规划、切换工具、缩小范围或请求用户帮助。重试只是其中一种策略，不能成为默认答案。

### Budget and Limits｜预算与运行限制

最大轮次是最直接的保护，但轮次并不能完整代表成本。

一次轮次可能只产生简短判断，也可能包含多个并行工具调用。产品还需要关注时间、Token、外部 API 费用和操作风险，并根据任务价值设置不同预算。

预算接近上限时，Agent 不应等到突然终止。它可以优先整理已经获得的结果、保存可继续状态，并说明剩余工作。这样，即使任务没有完全完成，用户仍能获得有用的部分成果。

### Escalation and Exit｜求助与退出

停止不只分为成功和失败。

Agent 可能因为缺少信息等待用户补充，因为高风险动作需要确认，因为权限不足无法继续，或者因为连续失败需要人工接管。产品应该为这些状态提供不同表达，而不是全部返回“发生错误”。

一次合格的求助需要说明当前目标、已经完成什么、具体卡在哪里，以及用户提供什么信息后可以继续。这样，人工介入不是重新开始任务，而是接过一个具有清楚上下文的运行状态。

## Use Case｜适用场景 📌

Agent Loop 适用于需要多步骤行动、环境反馈会改变后续决策的任务。

在 Coding Agent 中，循环可能包含理解需求、检查代码、修改文件、运行测试和修复失败。真正的停止条件不是代码已经生成，而是目标行为得到验证，未通过的检查被清楚说明。

在研究 Agent 中，系统需要持续搜索、比较和补充证据。完成标准可以包含核心问题已有来源支撑、主要冲突得到说明，以及继续搜索的边际价值已经降低。

在浏览器或业务操作 Agent 中，每一步都会改变外部状态。循环需要在提交、发送、删除和支付等动作前暂停确认，并在动作后验证结果，而不能只根据预设步骤机械前进。

对于单轮总结、改写或简单提取任务，引入完整循环可能增加不必要的延迟和不确定性。产品不应把所有 AI 功能都升级为 Agent，只有任务确实需要环境反馈和连续决策时，循环才有价值。

## Product Insight｜产品观察 🔍

Agent Loop 最重要的产品启发，是任务完成必须成为可以解释的产品状态，而不能只由模型生成一句“已完成”决定。

传统自动化通常提前定义固定步骤和成功条件。Agent 允许路径动态变化，因此更需要稳定的目标契约和证据规则。路径可以灵活，完成标准不能完全模糊。

这篇内容与已有 Agent 文章的边界也很清楚。OpenAI Agents SDK 文章介绍 Agent 如何组织目标、工具和多智能体工作流；LangGraph 关注状态、节点和可恢复编排；Agent Evaluation 关注运行结束后如何评价结果与轨迹。本篇关注的是运行当下：系统如何决定再走一步是否有价值，以及何时应该把控制权交还给用户。

另一个产品判断是，不应把最大轮次当作主要停止策略。轮次限制只能阻止无限运行，不能告诉用户任务是否完成。成熟产品需要同时展示完成、部分完成、等待输入、需要批准和无法继续等状态。

当这些状态清楚后，用户才能区分“Agent 正在努力”与“Agent 正在重复”，也能判断是否值得继续投入时间和成本。

## Reusable Value｜可复用价值 🔁

设计任务型 Agent 时，可以先为每类任务写一份完成契约：最终要改变什么状态，需要哪些证据，哪些内容允许部分交付，哪些动作必须由用户确认。

随后定义退出矩阵。任务可能成功完成、达到部分目标、等待用户输入、触发风险确认、遇到可重试错误、发生不可恢复错误，或达到预算上限。每种退出都应对应清楚的用户说明和后续操作。

运行中还可以记录三个轻量信号：当前目标、最近获得的新证据，以及仍未解决的问题。连续多个步骤没有改变这些信号时，系统应触发重新规划或求助，而不是继续调用相似工具。

复盘时，可以把失败按过早结束、无效循环、错误完成声明和不清楚求助进行分类。这比只统计任务成功率更容易定位产品需要修改的是 Prompt、工具反馈、状态模型还是预算策略。

## Productization Direction｜产品化方向 🚀

### Completion Contract Builder｜完成条件配置

Agent 平台可以让团队为不同任务定义结果结构、必要证据和确认边界。运行结束时，系统根据契约检查交付，而不是只接受任意自然语言作为最终答案。

### Loop Health Monitor｜循环健康监测

平台可以观察重复工具调用、相似页面状态、连续失败和长时间没有新增证据等信号，提示 Agent 重新规划，或在超过阈值前请求人工介入。

### Partial Result Handoff｜部分结果交接

预算耗尽或任务被中断时，产品可以保存已完成步骤、有效证据、未解决问题和可恢复状态，让用户或另一个 Agent 从明确位置继续。

Agent 的价值不是运行更多步骤，而是用必要步骤把目标推进到可验证结果。

当产品能够区分继续、完成、停滞和求助，Agent 才不只是一个会反复调用工具的循环，而会成为具有清楚责任边界的任务执行系统。
