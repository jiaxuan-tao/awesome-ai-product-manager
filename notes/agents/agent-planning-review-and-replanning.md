# Agent Planning｜让复杂任务先形成可检查的执行计划 🗺️

- Source｜来源：Anthropic Research - Trustworthy agents in practice
- Type｜类型：AI Agent 方法观察 / Task Planning / Plan Review / Replanning / Agent UX
- Link｜链接：https://www.anthropic.com/research/trustworthy-agents

当用户把复杂目标交给 Agent 时，真正令人不安的通常不是它需要执行很多步骤，而是用户不知道它准备如何理解目标、会影响哪些对象，以及什么时候需要自己做决定。

如果 Agent 接到任务后立即开始调用工具，用户只能逐步审批每个动作，或者等到结果出现后再判断方向是否已经偏离。前者会不断打断用户，后者又可能让错误理解持续累积。

Agent Planning 提供了另一种协作方式：在执行前先形成一份可检查的行动计划，让用户理解任务范围、主要阶段、预期产物和风险节点；执行过程中再根据新证据更新计划，并把重要变化重新交给用户判断。

从产品视角看，计划不是 Agent 展示能力的过程记录，而是一份连接用户意图与实际行动的动态任务契约。

---

## What It Is｜它是什么 🧩

Agent Planning 是把用户目标转化为一组可理解、可检查和可调整的执行阶段。

Anthropic 在关于可信 Agent 的官方文章中，将 Agent 描述为持续进行计划、行动、观察和调整的系统。文章还介绍了一种整体策略审核方式：用户可以在动作发生前查看、编辑和批准计划，并在执行过程中继续介入。

一份用户可见的计划通常需要说明当前目标、执行范围、关键步骤、依赖条件、可能产生的外部动作和预期交付物。它不必提前穷举所有工具调用，也不应伪装成未来一定会严格发生的脚本。

这与固定 Workflow 不同。Workflow 的主要路径由产品预先定义，计划则根据当前用户目标和环境生成。它允许 Agent 在执行后根据真实结果调整路径，但调整必须保持与原始目标和授权边界一致。

计划也不等于模型内部推理。用户需要看到的是可验证的行动意图、关键判断依据和影响范围，而不是模型逐字展开的私有思考过程。产品透明度来自可检查的承诺和状态，不来自展示冗长思维文本。

---

## Why It Matters｜为什么值得关注 💡

复杂 Agent 任务往往包含多个合理路径。用户提出“整理这个仓库”“研究一个市场”或“处理一批报销”时，输入描述可能没有覆盖全部偏好，Agent 也会在执行中遇到新的文件、规则和异常状态。

没有计划层时，产品容易在两种极端之间摇摆。一种是每次工具调用都请求批准，让用户疲于判断低价值细节；另一种是把整个任务一次性授权给 Agent，却没有让用户理解它采用的策略和可能影响。

计划把用户监督从单个动作提升到任务策略。用户可以先确认范围是否正确、顺序是否合理、哪些结果需要保留，以及哪些动作必须再次确认。这样，低风险步骤可以连续执行，高风险或偏好性判断仍然保留人的控制权。

但计划本身不能保证可靠。它可能遗漏关键依赖、对环境做出错误假设，或者在执行后迅速失效。真正有价值的 Agent Planning 必须同时设计计划生成、执行对照、偏离提示和重新规划，而不是只在开始时展示一张看起来完整的清单。

## Plan Design｜计划如何设计 ⚙️

### Goal and Scope｜目标与范围

计划首先要把用户目标转成可以检查的任务范围。用户需要知道 Agent 准备处理哪些对象、不会触碰什么，以及最终交付什么。

“优化项目”仍然过于模糊。更清楚的计划可以说明会检查哪些目录、是否允许修改文件、是否运行测试，以及最终提供修改、报告还是两者。若目标存在关键歧义，Agent 应先澄清，而不是用一份详细计划掩盖不确定性。

### Steps and Dependencies｜步骤与依赖

计划应展示有意义的阶段，而不是把每次读取文件或模型调用都列成一步。对用户有价值的是理解“先检查现状，再提出修改，最后验证结果”这样的任务结构，以及哪些阶段依赖资料、权限或前一步结果。

依赖没有满足时，计划状态应明确显示等待输入、等待授权或无法继续。这样，用户不会把计划中出现的步骤误解为已经具备执行条件。

### Approval Boundary｜授权边界

批准计划不应被解释成授权所有后续动作。

用户可以在策略层同意 Agent 整理文件，但删除内容、发送消息、提交付款或访问新的敏感数据仍可能需要单独确认。计划需要标记哪些步骤可以自动执行，哪些步骤只是在当前范围内准备，哪些动作发生前必须再次批准。

如果执行中出现原计划没有说明的新高风险动作，Agent 必须暂停，而不能把最初批准当作无限授权。

### Replanning｜重新规划

执行结果会改变计划。工具可能失败，资料可能不足，用户也可能在中途调整目标。重新规划的关键不是静默改写清单，而是说明发生了什么、哪些步骤改变、为什么改变，以及变化是否影响时间、成本或授权范围。

小范围调整可以自动更新，例如某个来源无法访问后改用另一个已授权来源。改变交付物、扩大数据范围或新增外部写入，则应该重新请求用户确认。

产品还需要保留计划版本或差异，避免用户回来后只看到一份被覆盖的新计划，却不知道 Agent 何时改变了方向。

### Completion Evidence｜完成证据

每个阶段最好对应可以观察的结果。检查阶段产出问题清单，修改阶段产出文件差异，验证阶段产出测试或核对结果。

计划中的勾选不能只由 Agent 自行宣告。关键步骤需要工具结果、环境状态或人工确认作为证据。这样，计划既帮助组织执行，也能与最终完成判断连接起来。

## Use Case｜适用场景 📌

Agent Planning 适合步骤较多、执行路径会根据环境变化，同时用户需要理解整体策略的任务。

在 Coding Agent 中，计划可以展示准备检查的模块、预期修改、验证方式和提交边界。用户先确认修改方向，再让 Agent 执行；如果测试暴露新的问题，计划应显示新增工作，而不是悄悄扩大改动范围。

在研究 Agent 中，计划可以说明核心问题、资料方向、比较维度和最终交付结构。搜索结果改变研究假设时，Agent 可以更新计划，但不能把新的主题扩张包装成原任务已经完成。

在业务操作中，计划可以把资料读取、规则核对、草稿生成和最终写入分开。用户在整体层面审核策略，同时对付款、发送或修改记录等高风险动作保留最终批准权。

对于一次简单改写、单次查询或步骤已经完全固定的任务，先展示计划会增加不必要的等待和界面负担。计划层应服务真正需要策略判断的复杂任务，而不是成为所有 Agent 请求的仪式。

## Product Insight｜产品观察 🔍

Agent Planning 最重要的产品启发，是用户控制不必等于逐步控制。

当产品只提供每一步批准时，用户需要理解大量执行细节，注意力被低风险动作不断消耗。让用户审核整体计划，可以把判断集中在目标、范围、策略和高风险节点，更接近人们管理复杂任务的方式。

这篇内容与 Human-in-the-loop 的边界在于，后者讨论确认、编辑、拒绝、澄清和接管等介入机制；本篇聚焦介入前用户审核的对象是什么，以及计划在执行变化后如何保持可理解。

它与 Agent Loop 的边界也很清楚。Agent Loop 关注运行时何时继续、停止或求助；Agent Planning 关注循环开始前如何建立路径，以及循环中的新证据如何更新路径。计划可以帮助循环判断进展，但不能替代完成条件和停止策略。

另一个关键判断是，计划的价值不取决于写得多详细。过度细化会制造虚假的确定感，也会让计划在第一轮执行后失效。好的计划应该稳定表达目标和边界，同时允许实现路径根据现实调整。

## Reusable Value｜可复用价值 🔁

设计计划体验时，可以先定义四项最小内容：目标、范围、阶段和确认点。只有当用户理解这四项后能够判断“是否愿意让 Agent 继续”，计划才具有实际价值。

随后为变化设置等级。工具替换、顺序调整等不改变目标和权限的变化可以记录后继续；范围扩大、成本明显增加、高风险动作或交付物改变则需要重新确认。

执行界面可以持续比较计划与实际状态：哪些步骤已经完成、证据是什么、哪些步骤被修改、当前为什么暂停，以及剩余工作是否仍符合原始目标。

评估时，可以观察用户修改计划的频率、计划外动作比例、重新确认是否发生在正确节点、计划偏离后是否及时说明，以及用户是否能准确判断任务最终完成了什么。

## Productization Direction｜产品化方向 🚀

Agent 工作台可以提供结构化计划视图，把阶段、状态、依赖、风险和产物放在同一任务中。用户可以编辑目标或顺序，但不必直接修改模型 Prompt。

计划变化可以使用类似差异审查的方式展示。新增步骤、删除步骤、范围扩大和授权变化分别标记，让用户快速判断这次重新规划是否需要介入。

平台还可以建立计划策略：低风险任务允许自动执行，涉及敏感数据或外部写入的计划默认进入审核；执行中出现未声明风险时，自动暂停并请求新的授权。

长期来看，计划记录还可以帮助团队复盘。哪些任务经常在同一阶段重新规划，哪些初始假设最容易失效，哪些确认点给用户造成重复负担，这些信息可以推动任务模板、工具和交互持续改进。

---

## Product Observation｜进一步观察

Agent 计划不是对未来步骤的保证，而是当前信息条件下的一份可检查承诺。

成熟的计划体验既要让用户在执行前理解整体策略，也要在现实变化后诚实说明偏离，并在目标、风险或权限发生变化时重新交还决定权。

当计划能够被审核、更新、对照和验证，Agent 的自主执行才不会变成不可见的黑箱，而会成为一种用户可以理解和持续校准的任务协作方式。
