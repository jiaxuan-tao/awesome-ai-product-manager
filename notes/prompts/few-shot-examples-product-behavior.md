# Few-shot Examples｜用示例定义 AI 产品的行为边界 🧭

- Source｜来源：Anthropic Claude Platform Docs
- Type｜类型：AI 产品方法观察 / Few-shot Prompting / Example Design / Product Behavior
- Link｜链接：https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices

AI 产品经常用自然语言告诉模型应该做什么。

团队会描述角色、任务、输出格式和限制，希望模型把这些抽象要求稳定地转化为具体行为。但很多规则即使写得清楚，仍然存在解释空间。例如，“保持简洁”究竟是两句话还是五段文字，“给出可执行建议”是否需要说明优先级，“不要替用户做决定”在不同场景中又应该如何体现。

Few-shot Examples 提供了另一种表达方式：不只告诉模型规则，还展示几个符合预期的输入与输出，让模型从具体样本中理解产品希望呈现的行为。

从产品视角看，示例不只是提高单次回答效果的 Prompt 技巧。它更像一组轻量的行为样本，帮助团队把抽象标准转化为模型可以参考、团队可以讨论、后续可以验证的产品配置。

> 指令说明“应该遵守什么”，示例展示“遵守之后具体是什么样子”。

---

## What It Is｜它是什么 🧩

Few-shot Prompting 是在请求中提供少量输入与理想输出示例，让模型参考这些样本完成新的相似任务。

Anthropic 的提示词最佳实践指出，少量经过设计的示例可以提高回答的准确性和一致性，并建议通过明确结构把示例与其他指令区分开。真正值得关注的并不是示例标签本身，而是示例向模型传递了哪些仅靠抽象规则难以表达的信息。

一个示例可以同时展示任务判断、内容范围、语气、格式和异常处理。例如，用户反馈归类功能的示例不仅告诉模型输出字段，还可以展示一条反馈涉及多个问题时如何处理、证据不足时是否保留“不确定”，以及模型如何避免添加用户没有表达的原因。

这意味着示例是一种压缩后的产品行为说明。团队不必为每种情况增加一段越来越复杂的规则，而可以选取有代表性的案例，让模型看到规则在真实输入中的落地方式。

但示例并不是越多越好。无关或高度重复的样本会占用上下文，过于理想化的样本无法覆盖真实输入，彼此矛盾的样本还会让产品行为更加不稳定。Few-shot 设计的核心不是堆积案例，而是选择能够清楚说明边界的最小样本集合。

---

## Why It Matters｜为什么值得关注 💡

很多 AI 产品问题并不是模型完全不理解指令，而是团队和模型对同一句要求的理解不同。

传统软件可以把规则写成确定性条件，输入满足某项约束就进入固定分支。生成式 AI 的输出空间更开放，同一条“结构清晰”的要求可以对应多种合理结果。如果产品只依赖自然语言形容理想输出，团队内部也可能无法形成一致判断。

示例让这种判断变得更具体。产品、设计、运营和开发可以围绕同一组输入输出讨论：这个回答为什么符合预期，哪些部分必须保留，哪些只是当前案例的偶然内容，以及相邻场景应该如何变化。

示例也能降低用户表达成本。一个分类、改写或信息提取功能如果已经通过示例明确了默认行为，用户就不需要每次重新解释格式和标准。产品把高频判断沉淀在内部，用户只需要提供当前任务材料。

不过，示例带来的稳定性并非没有代价。模型可能过度模仿样本措辞，把案例中的实体、长度或结构误认为强制要求。产品需要把应该复用的规律与不应复制的具体内容区分开，并用不同类型输入验证模型是否真正理解了任务。

## Example Design｜示例如何设计 ⚙️

### Representative Cases｜代表性案例

示例首先要代表真实任务，而不是只展示最容易成功的标准输入。

团队可以从真实用户请求、人工处理记录和常见失败中选择案例。核心不是覆盖所有可能情况，而是覆盖最常出现、最影响结果，以及最容易产生歧义的几类输入。

如果所有示例都结构完整、信息充分，模型可能在真实用户提供零散材料时表现明显下降。代表性示例应该保留适量的自然噪声，让产品默认行为接近实际使用环境。

### Boundary Cases｜边界案例

理想示例告诉模型应该怎样做，边界示例说明什么时候不应该照常处理。

例如，一个自动提取行动项的功能可以展示：明确承诺应被提取，普通建议不应被当作任务；缺少负责人时保留空值，而不是猜测；存在时间冲突时标记问题，而不是自行选择日期。

这类示例对建立产品信任很重要。它让模型看到“不确定”“需要补充信息”和“不能执行”也可能是正确结果，而不是把每次输入都强行处理成完整答案。

### Contrastive Examples｜对比案例

有些行为差异很难通过单个正确示例表达，可以使用相邻输入的对比。

例如，两条看起来相似的用户反馈，一条是在描述问题，另一条只是询问功能是否存在。把它们放在一起，可以帮助模型理解分类依据，而不是只记住某些关键词。

对比案例的价值在于揭示决策边界。但对比数量需要克制，差异点也要足够明确，否则模型可能只看到两段不同答案，却无法理解真正需要学习的判断。

### Output Discipline｜输出一致性

示例本身必须遵守产品要求。

如果指令要求返回固定结构，示例却省略字段；如果产品强调基于来源，示例却加入无法追溯的判断，模型会同时接收到冲突信号。团队不能把示例视为临时演示文本，而应像检查线上行为一样审查它。

示例之间还需要保持命名、字段、语气和信息粒度一致。模型通常会学习展示出来的模式，包括团队原本没有打算固化的细节。

## Use Case｜适用场景 📌

Few-shot Examples 更适合标准可以通过具体案例表达、但难以完全写成确定规则的任务。

在用户反馈分类中，示例可以展示多标签、模糊诉求和无关内容如何处理。在内容生成中，示例可以明确品牌语气、段落密度和避免使用的表达。在结构化提取中，示例能够说明缺失信息、冲突字段和来源引用如何表示。

对于需要专业判断的 Agent Skill，示例还可以作为能力说明的一部分，帮助 Agent 理解什么结果才算符合组织方法。但如果任务主要依赖实时事实、精确计算或外部系统状态，示例不能替代数据连接、工具调用和结果验证。

示例也不适合用来掩盖不清楚的产品定义。如果团队无法解释为什么某个输出是正确的，增加更多案例只会把隐含偏好塞进 Prompt，而不会真正解决标准问题。

## Product Insight｜产品观察 🔍

Few-shot Examples 最重要的产品启发，是 AI 产品的行为规范不一定只存在于文字规则中，也可以存在于经过选择的案例里。

传统产品团队常用原型、示例数据和验收案例统一理解。Few-shot 样本承担了类似作用：它既参与模型运行，也把团队对理想行为的判断具体化。这让 Prompt 设计从个人调试转向可协作的产品工作。

它与 Instruction Architecture 的关系是互补的。指令架构解决稳定规则、当前任务、用户输入和外部数据如何分层；示例位于任务定义内部，用具体输入输出补充抽象要求。示例不能覆盖产品级安全边界，也不应该被用来改变更高层规则。

它与 Prompt Versioning 的关注点也不同。版本管理解决示例和指令发生变化后如何记录、测试、发布与回退；Few-shot 设计解决的是当前版本为什么选择这些案例，以及它们共同定义了什么行为。

当示例开始影响线上结果，它们就不再只是写在 Prompt 里的演示内容。团队需要知道每个示例服务什么场景、来自哪里、是否包含敏感信息，以及移除某个案例会影响哪些任务。

## Reusable Value｜可复用价值 🔁

设计示例集时，可以先写出任务最重要的三类判断：正常情况应该怎样处理，最常见的歧义在哪里，什么情况下必须保留不确定或拒绝继续。随后为每类判断选择尽量少但具有区分度的案例。

评估时，不应只把示例原样输入模型。更重要的是准备没有出现在 Prompt 中、但遵循相同规律的新任务，观察模型是否能够迁移行为。如果模型只会复制示例格式，却无法处理相邻表达，示例集仍然过度拟合。

团队还可以记录示例覆盖图：每个案例对应哪项产品标准，哪些高频失败尚未被覆盖，哪些案例已经与当前产品规则冲突。当线上出现具有代表性的新问题时，可以先判断应该修改规则、补充工具，还是增加一个边界示例，而不是默认继续拉长 Prompt。

## Productization Direction｜产品化方向 🚀

### Example Registry｜示例注册表

Prompt 管理平台可以把示例作为独立对象记录，保存适用任务、来源、敏感信息状态、关联规则和当前版本。团队能够知道一个示例为什么存在，而不是只看到一大段拼接文本。

### Coverage Review｜行为覆盖检查

产品可以把示例与评估集关联，提示示例是否只覆盖理想输入，是否缺少边界情况，或多个案例是否给出了互相冲突的行为信号。

### Dynamic Example Selection｜动态示例选择

当任务类型较多时，系统可以根据用户意图选择少量相关示例，而不是长期把全部案例放入上下文。动态选择需要设置稳定边界和回归评估，避免同一任务因为检索到不同示例而产生不可解释的行为变化。

Few-shot Examples 的价值不在于让 Prompt 看起来更完整，而在于把抽象产品标准转化为可以被观察和验证的具体行为。

真正成熟的示例集应当数量克制、边界清楚，并随着真实任务持续更新。它帮助模型理解产品希望怎样工作，也帮助团队更准确地讨论自己究竟希望 AI 做成什么样。
