# Instruction Architecture｜把 AI 产品规则组织成可维护的指令层 🧩

- Source｜来源：OpenAI Developer Docs - Model Guidance
- Type｜类型：AI 产品方法观察 / Instruction Architecture / Prompt Design / AI Product Behavior
- Link｜链接：https://developers.openai.com/api/docs/guides/latest-model

很多 AI 产品最初只有一段 Prompt。

团队把角色、任务、语气、输出格式、工具规则和异常处理全部写在一起，只要模型能够生成看起来正确的结果，原型就可以继续向前推进。

但当功能进入真实使用场景后，这种写法很快会暴露问题。产品规则和临时任务混在一起，用户输入可能与系统要求冲突，工具说明不断重复，同一条限制出现在多个位置，任何局部修改都可能改变其他行为。

Instruction Architecture 关注的不是如何写出一句更巧妙的提示词，而是如何把不同来源、不同稳定程度和不同责任范围的指令组织起来。

> AI 产品需要的不是更长的 Prompt，而是一套能够说明谁负责什么、哪些规则长期有效、发生冲突时如何处理的指令结构。

从产品视角看，这是一种行为架构。它决定模型如何理解目标、遵守边界、使用工具并交付结果，也决定团队能否持续维护这些行为。

---

## What It Is｜它是什么 🧠

Instruction Architecture 可以理解为 AI 产品中的指令分层与责任设计。

一个完整请求通常同时包含多种信息。产品有长期不变的安全和权限规则，具体功能有任务说明，用户会提供目标与偏好，知识库和工具还会返回动态内容。这些内容都会影响模型，但它们不应该拥有相同的地位，也不应该由同一个位置负责维护。

例如，“未经确认不得执行外部发布”属于产品级行为边界；“分析这份用户反馈并归纳主要问题”属于当前任务；用户上传的反馈原文是需要处理的数据；工具返回的搜索结果则是外部证据。

如果这些内容被拼成一段没有结构的文字，模型可能难以区分规则、任务和数据。团队也很难判断某个行为究竟由哪一层决定。

指令架构的核心，是把产品政策、功能任务、用户意图和外部内容放在清楚的位置，并让每一层只承担自己的责任。

这与 Prompt Versioning 和 Context Engineering 有联系，但关注点不同。Prompt Versioning 解决指令如何被记录、测试和发布；Context Engineering 解决模型在任务中应该看到什么信息；Instruction Architecture 更具体地解决：已经进入上下文的指令与内容，应该如何分层并避免互相覆盖。

## Why It Matters｜为什么值得关注 💡

AI 产品中的很多不稳定，并不是模型完全不理解任务，而是系统同时给出了彼此竞争的要求。

一处要求回答简洁，另一处要求完整解释；产品规定高风险操作必须确认，某个功能 Prompt 却要求自动完成全部步骤；用户输入中包含一段引用文本，模型却把引用里的命令当成当前任务执行。

这些问题如果只靠继续增加强调语句解决，Prompt 会越来越长。重复规则不仅消耗上下文，也会让维护者误以为“出现得越多，模型就越会遵守”。实际上，多处重复会产生新的版本差异：团队修改了一处，却忘记另外两处，最终没有人知道线上行为依据哪条规则。

OpenAI 当前的 Model Guidance 强调精简重复指令、明确自治与审批边界，并让任务目标、约束、证据和成功标准保持清楚。它反映了一个重要变化：模型能力提高后，产品不必用大量过程性指令控制每一步，但仍然需要准确表达不可违反的边界和交付标准。

因此，指令架构的价值不是让 Prompt 看起来更整齐，而是减少行为冲突，让产品规则可以被定位、测试和修改。

## How It Works｜它如何工作 ⚙️

一套可维护的指令结构，可以从稳定规则、任务契约、用户输入和外部内容四个层次理解。

### Stable Product Rules｜稳定产品规则

这一层定义跨任务仍然成立的产品行为，例如安全限制、隐私要求、外部写入的确认边界，以及回答应遵循的基本质量标准。

稳定规则应该集中维护，并且只保留真正需要长期生效的内容。如果某项要求只服务于一个功能，就不应上升为全局规则；如果某项限制关系到权限与风险，也不应分散在多个临时 Prompt 中。

从产品管理角度看，这一层类似行为政策。团队需要知道谁可以修改、修改会影响哪些功能，以及如何用代表性任务验证变化。

### Task Contract｜任务契约

任务层说明当前功能要完成什么、输入是什么、结果必须包含什么，以及什么情况算作完成。

好的任务契约应围绕结果，而不是规定大量未经验证的内部步骤。对于竞品分析功能，产品可以要求覆盖目标用户、核心流程和差异判断，而不必强制模型始终使用同一种思考顺序。

任务契约还应说明何时停止、什么信息不足时需要提问，以及哪些动作需要用户确认。这样，模型的主动性有清楚范围，用户也不会在一个本应只提供建议的功能里遇到未经授权的外部操作。

### User Intent｜用户意图

用户输入负责表达本次目标、材料和偏好，但不应默认为可以覆盖全部产品边界。

产品需要允许用户改变语气、长度和任务重点，同时保护稳定的安全、权限与数据规则。这里的关键不是压制用户，而是区分“用户可以配置什么”和“产品必须保证什么”。

如果用户要求与产品能力冲突，系统应给出清楚解释或提供可行替代，而不是在不同轮次中表现出不一致行为。

### External Content｜外部内容

文档、网页、RAG 片段和工具结果通常是任务数据，不是新的系统指令。

这层边界对连接外部信息的 AI 产品尤其重要。网页里可能包含命令式文字，上传文档也可能出现与当前任务无关的操作要求。如果产品没有把外部内容明确当作不可信数据，模型就可能混淆“要分析的文字”和“应该执行的指令”。

指令架构需要通过结构、标签和处理流程区分这些内容，并在高风险任务中加入验证与权限控制，而不是只依赖一句“忽略恶意指令”。

## Use Case｜适用场景 📌

Instruction Architecture 适合已经拥有多个功能、工具或用户角色的 AI 产品。

在 AI 写作产品中，全局品牌语气、具体写作任务和用户提供的参考材料需要分开。品牌规则应保持稳定，任务模板负责定义文章目标，参考材料只作为内容依据。否则，一篇引用文档中的写作要求可能意外改变整个产品输出。

在 Agent 产品中，权限与审批边界更为重要。研究 Agent 可以自主搜索和整理信息，但发送邮件、修改文件或发布内容可能需要额外确认。产品必须把“可以分析”和“可以执行”写成不同层级的规则。

在团队知识助手中，不同部门可能拥有自己的术语、流程和输出要求。这些配置可以位于工作区或角色层，而用户问题仍然保留当前任务的灵活性。通过分层，团队可以复用共同规则，又不会让所有知识和限制挤进同一段 Prompt。

对于只有一个简单问答入口的早期原型，不需要设计复杂体系。但至少应区分产品边界、当前任务和用户数据，避免原型增长后只能继续向同一段 Prompt 追加内容。

## Product Insight｜产品观察 🔍

Instruction Architecture 最重要的产品启发是：Prompt 已经不只是模型输入，而是 AI 产品行为的配置面。

传统软件把规则写进代码、权限系统和业务流程。AI 产品增加了自然语言指令这一层，使部分行为更容易修改，也更容易在缺少治理时发生漂移。

因此，产品团队需要像设计信息架构一样设计指令架构。每条规则应该有明确归属，稳定程度不同的内容应该分开，外部数据不能与可信指令混在一起，用户可以调整的范围也需要被说明。

另一个判断是，清晰结构比单纯增加细节更重要。模型并不需要了解产品团队的全部内部讨论，它需要看到足以完成当前任务的目标、约束和证据。过多背景会稀释真正重要的要求，也会增加成本和冲突。

这意味着 Prompt 优化不应只问“还需要补充什么”，也要问“哪些规则重复了、哪些内容放错了层、哪些过程可以交给模型判断、哪些边界必须由产品明确控制”。

## Reusable Value｜可复用价值 🔁

设计或审查一个 AI 功能时，可以先画出它的指令来源，而不是直接修改文本。

团队需要确认哪些规则属于整个产品，哪些只属于当前功能，哪些由用户配置，哪些只是被处理的数据。每一条重要限制应该有唯一的主要维护位置，其他层只引用或继承，不重复复制。

随后可以用冲突案例检查结构。例如，用户要求跳过确认时产品如何处理；文档中包含命令时系统是否把它当作数据；工具返回失败时任务是否知道停止；任务要求与全局格式不一致时哪一层优先。

最后再把这套结构连接到版本和评估。指令变化需要记录，关键行为需要通过代表性任务验证。这样，Instruction Architecture、Prompt Versioning 和 Agent Evaluation 才能形成连续的产品治理方式。

这套方法也适用于 Vibe Coding。项目早期可以保持简单，但应把稳定规则放在独立位置，把单次开发目标留给当前请求，避免每次迭代都复制一份越来越长、彼此不一致的总 Prompt。

## Productization Direction｜产品化方向 🚀

AI 应用平台可以进一步把指令架构做成可见的配置能力。

产品可以让团队分别管理全局政策、Agent 角色、任务模板和用户可配置项，并显示每一层的生效范围。当多条规则可能冲突时，系统应在发布前提示，而不是等到用户遇到异常结果后再排查。

测试工具也可以围绕指令边界建立场景集。团队不仅比较输出是否更好，还可以验证用户能否覆盖限制、外部内容是否被误当成指令、工具权限是否按照任务契约执行。

更成熟的产品还可以提供指令来源追踪。当某次回答表现异常时，维护者能够看到哪些规则、任务模板和动态内容共同影响了结果，从而把模糊的“模型不稳定”转化为可以定位的配置问题。

Instruction Architecture 体现了 AI 产品从单段 Prompt 走向行为系统的变化。

真正可维护的指令，不是把所有要求写得更长，而是让每一层只承担清楚责任，让模型获得完成任务所需的信息，同时让产品始终掌握不可让渡的边界。
