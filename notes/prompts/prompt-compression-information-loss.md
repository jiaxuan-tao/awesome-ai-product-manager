# Prompt Compression｜在成本、延迟与信息损失之间做取舍 🗜️

- Source｜来源：Microsoft Research / LLMLingua GitHub Repository
- Type｜类型：AI 产品方法观察 / Prompt Compression / Context Management / Cost & Latency
- Link｜链接：https://github.com/microsoft/LLMLingua

当 AI 产品开始处理长文档、多轮对话、检索结果和大量工具返回值时，上下文会迅速变长。更长的 Prompt 能够为模型提供更多信息，但也会增加输入成本、首字响应时间和上下文窗口占用。

一种直觉做法是不断扩大上下文窗口，把所有可能有用的信息都交给模型。问题在于，信息更多不等于任务表现一定更好。重复内容、低相关片段和冗长表达会占用有限的注意力，也可能让真正重要的事实更难被模型识别。

Prompt Compression 关注的是如何在请求进入主模型前，缩短上下文并尽量保留任务所需的信息。

从产品视角看，这不是简单的文本压缩，而是一项需要承担信息损失风险的决策：

> 产品必须知道哪些内容可以被缩短，哪些内容必须原样保留，以及节省的成本是否值得可能发生的质量下降。

---

## What It Is｜它是什么 🧩

Prompt Compression 是对输入上下文进行筛选、重写或 Token 级压缩，使模型在更短的输入中获得完成任务所需的信息。

压缩可以发生在不同层次。最简单的方式是删除重复段落和明显无关内容；更进一步，可以先对长文档生成摘要，或者只保留与当前问题相关的片段；像 LLMLingua 这样的研究项目，则尝试识别对模型任务贡献较低的 Token，在保持主要信息的前提下压缩 Prompt。

Microsoft 的 LLMLingua 系列使用较小的模型判断不同内容的重要性，并提供针对长上下文和任务无关压缩的不同方法。项目公布的实验结果说明 Prompt 可以在部分任务中被显著缩短，但这些结果来自特定数据集、模型和压缩配置，不能直接视为所有产品都能获得的固定收益。

Prompt Compression 与 Prompt Caching 解决的不是同一个问题。缓存保留原始上下文，只在重复请求中复用已经处理的稳定前缀；压缩则主动改变模型实际看到的内容。前者主要面对重复计算，后者直接处理输入规模，因此压缩需要更严格的质量验证。

---

## Why It Matters｜为什么值得关注 💡

上下文成本会随着产品进入真实使用阶段被放大。

一次长文档分析可能只是偶发开销，但当知识库问答、研究 Agent 或客服助手每天处理大量请求时，每次多发送几千个 Token 会持续增加费用。较长输入还会延长预填充阶段，使用户更晚看到第一个结果，并减少同一服务能够同时处理的请求数量。

上下文窗口也不是无限资源。历史对话、检索文档、系统规则和工具结果不断累积后，产品必须决定哪些信息继续保留。若只按时间机械截断，可能删掉早期形成的关键约束；若全部保留，又可能让成本和延迟失去控制。

Prompt Compression 值得关注，是因为它把“模型应该看到多少信息”从被动限制变成主动策略。产品不再只问能否放进上下文，而需要判断每类信息对当前任务的边际价值。

但压缩也可能制造一种隐蔽故障：请求仍能正常返回，语言也可能很流畅，只是某个数字、否定条件、角色关系或例外规则已经在压缩过程中消失。相比明确的接口错误，这类信息损失更难发现，也更容易被误认为模型本身判断失误。

## Compression Strategy｜如何设计压缩策略 ⚙️

### Separate Content by Sensitivity｜按信息敏感度分层

不同内容不应该使用同一种压缩比例。

系统规则、权限边界、输出格式、用户明确提出的限制条件和当前问题，通常具有较高敏感度。对这些内容的轻微改写，都可能改变产品行为。它们更适合原样保留，或者只删除可以确定的重复内容。

检索文档、长对话历史、会议记录和工具返回的说明文字，通常拥有更大的压缩空间。但产品仍需保护其中的实体名称、数字、日期、引用位置、否定表达和条件关系。对法律、金融、医疗或合同内容而言，即使一段话看起来冗长，也不能仅凭语言重复就判断它没有价值。

### Choose the Right Compression Level｜选择合适层级

产品可以先从风险较低的粗粒度压缩开始，例如去重、过滤低相关文档和限制同类检索片段数量。这类处理保留了原始段落，方便解释和追踪。

摘要压缩能够进一步减少长度，但摘要本身已经是一次生成结果，需要验证事实覆盖和引用对应关系。Token 级压缩可以获得更高比例，却可能输出人类难以直接阅读的文本。LLMLingua 的 Responsible AI 说明也明确提示，压缩后的表达可能不便于人类理解。

因此，压缩强度不应只是一个全局参数。产品可以根据任务风险、输入类型和当前上下文预算使用不同策略，并为高风险请求保留不压缩路径。

### Preserve Evidence｜保留证据与映射

如果压缩后的文本直接替代原文，团队在结果出错时很难判断信息在哪一步丢失。

更可靠的设计是保留原始内容、压缩版本和二者之间的来源映射。用户最终看到引用时，应尽量回到原文，而不是引用一段机器压缩后的表达。这样既能减少模型输入，也不会让压缩层破坏证据链。

## Use Case｜适用场景 📌

Prompt Compression 更适合上下文较长、信息存在明显冗余，而且任务可以通过代表性样本验证的产品。

在 RAG 应用中，系统可以先过滤低相关文档，再压缩保留下来的片段，使模型获得更集中的证据。这里需要分别观察检索是否找对内容，以及压缩是否保留了回答问题所需的事实，不能把两个阶段的错误混在一起。

在多轮助手中，可以把早期对话整理成结构化状态或阶段摘要，同时原样保留最近消息与用户长期约束。相比无限追加历史，这种方式更容易控制会话成本，但必须避免把暂时结论错误地固化成长期记忆。

在 Agent 工作流中，浏览器页面、日志和工具结果可能非常长。产品可以抽取与下一步决策相关的状态，同时保留原始结果供复查。若工具输出包含错误码、文件路径或交易标识，则应设置强制保留字段。

一次性短 Prompt、输入本身已经高度结构化，或压缩模型运行成本接近节省收益的场景，不一定值得引入压缩层。增加一个处理步骤也会增加延迟、基础设施和故障点，不能只计算主模型减少了多少 Token。

## Product Insight｜产品观察 🔍

Prompt Compression 最重要的产品启发，是上下文管理不能只追求“装得更多”，而要追求“保留对任务有用的信息”。

当上下文窗口扩大时，团队容易把信息选择责任全部交给模型。但真实产品仍需要明确的信息结构：哪些是不可违反的规则，哪些是用户事实，哪些是当前任务证据，哪些只是可被替换的背景说明。只有先建立这些边界，压缩才不会成为盲目删减。

压缩策略也不应完全隐藏。普通用户不需要理解 Token 和压缩模型，但在文档、研究或高风险任务中，产品应允许用户查看引用原文、发现材料是否缺失，并在必要时选择使用完整上下文重新运行。

另一个容易忽略的问题是，压缩目标与业务目标并不相同。压缩率高只说明输入变短，不说明用户任务完成得更好。某个策略节省一半输入成本，却让关键任务成功率下降，可能比不压缩更昂贵，因为用户需要重试、人工检查或承担错误结果。

因此，产品需要把压缩看成一种带有质量预算的运行策略，而不是单纯的成本开关。

## Evaluation & Productization｜评估与产品化方向 🧪

验证压缩策略时，可以让原始 Prompt 和压缩 Prompt 在同一组任务上运行，比较最终答案、关键事实覆盖、引用正确性、格式通过率、输入成本和响应时间。

测试集应包含容易被压缩破坏的案例，例如多个相似实体、带否定条件的要求、精确数字、跨段落关系和低频但重要的例外。平均任务得分之外，还要设置不可丢失字段和高风险案例的发布门槛。

产品还可以记录每次请求采用了什么策略、原始与压缩 Token 数、哪些片段被删除，以及最终任务是否成功。当线上出现问题时，这些信息能够帮助团队区分检索错误、压缩损失和主模型错误。

在平台层面，可以发展出上下文预算管理器：应用为不同任务定义最大成本、必须保留区域和允许压缩的内容类型，系统再根据当前输入动态选择去重、检索、摘要或 Token 级压缩。

更成熟的能力还应包含自动回退。当压缩结果未通过结构校验、关键字段缺失，或模型对答案表现出明显不确定时，系统可以使用较低压缩率或完整上下文重新运行，而不是继续把不完整信息交给后续步骤。

Prompt Compression 说明，AI 产品的成本优化不能与质量管理分开。真正有价值的压缩，不是让 Prompt 尽可能短，而是在可验证的任务结果下，减少不必要的信息处理，并让被删除的内容、保留的依据和失败后的恢复路径都可以被理解。
