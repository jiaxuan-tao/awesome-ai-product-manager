# Tool Retry & Idempotency｜让 Agent 重试时避免重复执行 🔄

- Source｜来源：AWS Builders’ Library - Making retries safe with idempotent APIs
- Type｜类型：AI 产品工具调用观察 / Tool Retry / Idempotency / Execution Reliability
- Link｜链接：https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/

用户让 Agent 创建一条任务，工具调用等待一段时间后超时。Agent 认为操作失败，于是再次提交。过一会儿，用户发现系统里出现了两条相同任务。

这里的关键问题是，超时只说明调用方没有及时获得结果。外部系统可能尚未处理，也可能已经完成写入，只是响应没有成功返回。把这两种情况都当作失败，会让自动重试放大副作用。

AWS 的参考文章讨论了分布式 API 如何通过幂等机制支持安全重试。本文借用这一工程基础，进一步分析 Agent 工具调用中的状态表达、操作身份和恢复体验；这些 Agent 场景是产品延伸，不是原文对 AI 系统的专门论述。

---

## What It Is｜它是什么 🧩

幂等可以理解为：同一次操作被重复请求时，不产生额外的预期业务副作用。例如，重新提交同一次任务创建请求，应能识别原操作，而不是每次都新增任务。

这种保证通常需要工具或服务端实现。常见方式是由调用方提供稳定的请求标识，服务端记录它与执行结果的关系，再按照约定处理重复请求。是否支持、有效范围、保留期限和参数冲突处理，都属于接口契约。

它不意味着任意两次内容相同的请求都应该合并。用户可能真的希望创建两条相同任务。系统需要区分“继续同一次操作”和“发起新的操作”，不能只看文字或参数是否一样。

对 Agent 产品而言，操作身份应由应用可靠保存。仅在 Prompt 里写“不要重复”，无法在网络中断、进程重启或多个执行者同时工作时建立完整保证。

---

## Why It Matters｜为什么值得关注 💡

自动重试可以帮助用户越过短暂故障，但工具获得写入能力后，错误恢复本身也会改变外部状态。创建工单、发送消息、发布内容或启动付费作业，都可能因为重复执行带来额外成本。

一个会主动推进任务的 Agent 更容易遇到这种问题。它可能把“没有得到结果”解释为“需要再做一次”，也可能在重新规划时用另一个工具执行相同目标。即使每个工具各自有重试限制，整条任务仍可能重复产生同一种业务效果。

因此，产品需要管理完整操作过程，而不能只检查一次调用有没有报错。对用户来说，真正重要的是原操作是否生效，以及下一步会不会重复改变数据。

如果系统没有足够证据，表达“执行结果待核实”比宣称失败更准确。这个状态需要对应查询、等待或人工核对入口，否则它只会成为另一个让用户无法行动的提示。

## Recovery Design｜如何设计恢复路径 ⚙️

### Identify the Operation｜保留同一次操作的身份

可以把一项用户目标拆成几个有外部副作用的操作，并分别记录身份。例如，“整理反馈并创建任务”包含资料分析和任务创建；分析可以再次运行，但创建操作应关联到已确认的交付对象。

重试时，需要沿用原操作身份和已核定参数。若用户改变了任务内容、收件人或目标位置，应重新判断这还是原请求的恢复，还是一项新操作。模型不能为了绕过错误随意更换标识，否则去重约定会失效。

操作记录还应跨会话保留。用户关闭页面后回来，系统应能找到原执行记录；重新打开聊天不应自动把“继续”变成第二次创建。

### Reconcile Before Repeating｜先核实，再决定是否重做

遇到超时或断线后，可以先根据已有操作标识查询状态。确认完成后返回原结果，仍在处理时继续等待，明确未执行时再按工具契约恢复。

查询本身也有局限。外部系统可能延迟显示新记录，“暂时查不到”不一定证明没有执行。没有可靠查询接口时，产品应承认不确定性，避免把一次空搜索当成安全重试的充分证据。

如果接口提供有效的幂等保证，可以按其约定重试。如果不提供，尤其是发送消息或发布内容这类难以撤销的动作，系统应暂停自动重做，让用户核实已有结果。换一个工具再次点击同样的按钮，也不能消除重复风险。

### Bound the Retry｜给重试设置范围

恢复策略需要按错误类型区分。输入不合法应修改输入，权限不足应解决权限，暂时不可用才可能适合等待后重试。重复发送同一错误参数，只会增加耗时。

重试还应有次数、总耗时和成本上限。应用、工具 SDK 和后台任务若分别自动重试，次数可能叠加，因此需要明确由哪一层负责恢复，以及整项操作还能投入多少。

用户取消时也要说明边界：停止继续重试，不等于外部系统已经撤销已接受的请求。界面应保留原操作状态，直到能够核实结果或明确交还处理责任。

## Use Case｜适用场景 📌

在内容发布工具中，可以把“生成草稿”和“提交发布”分开。草稿生成失败后重新生成通常较容易处理；发布超时后应查找原发布记录，不能因为看不到成功提示就立即再发。最终反馈应指向实际文章或提交记录，便于用户核对。

在任务管理工具中，用户可能连续点击按钮，也可能在聊天中重复说“创建一下”。产品需要结合当前操作记录识别可能的重复意图，而不是默认把每句话都变成新任务。同时应保留明确的“再创建一条”能力，让用户有意重复时可以表达清楚。

在批量处理中，部分项目成功、部分项目失败尤其常见。恢复范围应落到具体项目，已经完成的项目保留结果，仅继续处理符合重试条件的部分。把整个批次重新提交，可能让一次小故障变成大量重复记录。

这些场景可以采用不同实现，但共享同一个产品要求：用户应能分辨是在等待原操作、恢复原操作，还是即将发起新操作。

## Product Insight｜产品观察 🔍

### 重试按钮是一项行为承诺

“重试”看起来只是一个常见按钮，但用户通常会理解为继续完成刚才的事。如果按钮实际上会重新创建对象、再次发送内容或重新计费，产品就需要明确说明。

界面可以根据实际状态使用“查询执行结果”“继续未完成项目”或“重新创建”等更准确的动作名称。文案的基础必须是真实执行语义，不能用更好看的提示掩盖系统对结果的不确定。

在 Agent 聊天中也一样。“我再试一次”应建立在工具允许安全重试的依据上。用户不需要阅读技术日志，但应知道原动作是否可能已经完成，以及下一步将怎样处理这种可能性。

### 幂等保证有边界

一个接口接受幂等标识，不代表整条 Agent 工作流就不会重复。去重记录可能有期限，也可能只覆盖单个账号、某类操作或某个服务。跨工具、跨服务的后续动作，仍然需要各自的状态管理。

例如，创建任务得到去重保护，随后发送通知却未必受到同一保护。产品评估应逐个检查外部副作用，而不是给整条流程贴上“支持幂等”的标签就结束。

已有 Tool Result Contract 关注工具结果代表什么，MCP Tasks 关注长任务的可查询状态，Agent Loop 关注继续与停止。本篇补充的是：在恢复过程中，怎样保持操作身份并限制重复副作用。它们可以配合使用，但不能互相替代。

## Reusable Value｜可复用价值 🔁

为写入型工具设计一份恢复约定时，可以记录操作标识如何生成和保存、何时查询状态、哪些错误允许重试、何时需要用户核实，以及重复请求如何返回已有结果。这些约定应能被程序执行，也应能转化为用户可理解的反馈。

验证时，应刻意模拟“服务已写入，但客户端没收到响应”，而不只测试请求发送前就失败的简单情况。还可以检查重复点击、会话恢复、部分批次成功，以及用户修改参数后再次提交的行为。

观察指标可以包括重复记录数量、待核实操作的处理时长、误报失败次数和用户额外核对成本。只看重试成功率，可能把“最终成功但多执行了一次”算成好结果。

对 Vibe Coding 项目，可以先从一个有外部写入的高频动作开始，把记录、查询和恢复走通，再扩展到完整工作流。关键是让产品清楚保存“这次操作到底发生了什么”，并据此决定下一步，而不是把恢复责任全部交给模型猜测。
