# Tool Result Contract｜让 Agent 正确理解外部工具返回值 🧾

- Source｜来源：Model Context Protocol Specification - Tools
- Type｜类型：AI 产品方法观察 / Tool Result / Output Schema / Agent Tooling
- Link｜链接：https://modelcontextprotocol.io/specification/2025-11-25/server/tools

工具调用常被理解成一条简单链路：Agent 选择工具，传入参数，工具返回结果，模型继续回答。

但在真实产品里，“工具已经返回”并不代表 Agent 已经正确理解结果。返回内容可能为空、过期、部分成功，也可能混合说明文字、结构化数据、文件链接和错误信息。如果这些状态没有明确表达，模型就可能把失败当成功、把提示当事实，或者在缺少数据时继续给出确定结论。

Tool Result Contract 关注的是工具与 Agent 之间的结果约定：工具返回什么结构，各字段代表什么，错误和部分结果如何表达，以及下游可以在什么范围内继续使用。

---

## What It Is｜它是什么 🧩

MCP Tools 规范允许工具返回文本、图片、音频、资源链接和嵌入资源等内容，也支持通过 `structuredContent` 返回结构化对象，并使用 `outputSchema` 描述预期结构。

从产品角度看，这些机制共同构成工具结果的接口。Agent 不只需要一段“可读文字”，还需要知道哪些字段可以用于后续判断、哪些内容只是展示材料、当前调用是否成功，以及结果是否满足原始任务。

一个完整契约通常包含四部分：结果结构、业务状态、证据来源和后续动作。它不要求所有工具使用同一种格式，但要求同一个工具的结果含义保持稳定，并能被客户端、模型和后续工作流共同理解。

---

## Why It Matters｜为什么值得关注 💡

工具输入通常比工具输出更早得到重视。团队会认真定义参数类型、必填字段和权限，却让工具在执行后返回一段自由文本。这样做在 Demo 中看起来灵活，进入多步骤任务后却会产生新的不确定性。

例如，搜索工具返回“未找到相关结果”，模型可能把这句话总结成“没有这项信息”；数据库工具只返回前 100 条记录，模型可能误以为这是完整数据；写入工具返回请求已接收，Agent 可能将其描述为保存成功。

这些错误并不一定来自模型能力，而是结果契约没有区分“没有”“未知”“尚未完成”和“只返回一部分”。当工具结果会驱动下一次调用或外部动作时，这种模糊会沿着任务链路不断放大。

---

## Contract Elements｜结果契约包含什么 ⚙️

### Output Structure｜输出结构

稳定字段能让系统知道结果中哪些内容可以计算、筛选或继续传递。`outputSchema` 的价值不仅是方便开发者读取 JSON，也是在工具和下游之间建立可验证的共同理解。

结构化结果仍可以同时提供适合用户阅读的文本，但两者职责不同：结构用于程序和 Agent 判断，文本用于解释和展示。产品不应依赖模型从说明文字中反复猜测字段含义。

### Business Status｜业务状态

技术请求成功和业务任务成功不是同一件事。工具需要区分调用失败、权限不足、无数据、部分完成、等待处理和完整成功。

如果只使用一个笼统错误字段，Agent 很难决定下一步是修改参数、请求授权、稍后重试，还是根据已有部分结果继续。清楚状态能够把失败变成可处理分支。

### Provenance and Freshness｜来源与时效

返回事实、网页内容或业务数据时，结果应尽量携带来源标识、时间范围和必要的完整性说明。这样，Agent 才能判断信息是否适合回答当前问题，也能在最终界面中保留核验入口。

### Continuation｜后续处理

分页标记、继续查询的游标、可重试提示和结果数量限制，都属于契约的一部分。它们告诉 Agent 当前结果是不是终点，而不是让模型凭文本长度猜测任务是否完成。

## Use Case｜适用场景 📌

在网页搜索中，工具结果可以区分页面标题、地址、摘要、抓取时间和正文状态。若某个页面无法读取，也应明确这是单个来源失败，而不是整个搜索没有结果。

在企业数据查询中，结果需要说明权限过滤、查询时间范围、总记录数和本次返回数量。用户看到的“销售额下降”必须能够追溯到具体数据范围，而不是来自一个没有边界的数字列表。

在文件写入或业务操作中，工具应区分“已验证参数”“请求已提交”和“外部系统已确认完成”。Agent 只有在获得最终成功状态后，才能向用户承诺动作已经生效。

在多工具工作流中，上游工具的结构化结果还会成为下游工具的输入。稳定契约能减少模型在中间进行不必要的文本转换，也降低字段丢失和含义漂移。

## Product Insight｜产品观察 🔍

现有 Tool Calling UX 更关注用户如何看到工具选择、参数、权限和执行反馈；Structured Outputs 更关注模型最终回答如何成为可验证数据。Tool Result Contract 位于两者之间：外部系统完成一次调用后，Agent怎样获得可信、可继续处理的结果。

这个中间层决定了 Agent 是否真的“知道发生了什么”。如果工具只返回一句自然语言，模型可能表现得很流畅，却无法可靠区分业务状态。结构清楚并不意味着界面必须展示原始 JSON，而是产品能够基于稳定状态生成更准确的反馈。

好的结果契约还会减少无效重试。当系统知道失败来自权限、参数、限流或上游服务时，就能选择对应恢复方式，而不是让模型不断重复同一次调用。

---

## Reusable Value｜可复用价值 🔁

设计工具时，可以先列出所有可能结果，而不只是成功样例。团队需要确认：空数据和错误是否不同；部分结果是否可用；结果是否有数量或时间限制；用户能否看到来源；下一步需要什么条件。

随后再决定哪些信息进入结构化字段，哪些信息用于用户说明。状态、标识、时间和可继续处理的游标应优先结构化；面向人的解释可以作为补充，而不应成为唯一事实来源。

最后把结果契约纳入评估。测试不应只检查工具能否返回，还要验证 Agent 是否会在空结果时停止推断、在部分结果时说明限制、在失败时选择正确恢复动作。

---

## Productization Direction｜产品化方向 🚀

Agent 工具平台可以为工具提供结果 Schema 编辑、样例预览和兼容性检查。工具发布前，系统验证实际返回是否符合声明结构，并提示缺少错误状态、来源或分页信息的问题。

运行时可以把结果契约转化为统一状态组件。用户看到的是“已找到 23 条，本次展示 10 条”“缺少访问权限”或“操作已提交，等待外部确认”，而不是无法理解的原始工具消息。

可观测平台还可以记录每类结果触发了什么后续动作，识别 Agent 在哪些状态下最容易误判、重复调用或过早宣布完成，从而持续优化工具设计。

---

## Product Observation｜进一步观察

Agent 的可靠性不只取决于是否选对工具，也取决于工具是否用清楚的方式表达现实状态。

输入 Schema 让工具知道应该做什么，结果契约让 Agent 知道实际发生了什么。只有两端都清晰，工具调用才能从一次技术连接变成可验证、可恢复的产品能力。
